# 权限模式（Permission Mode）

> 状态：第一、二期已实现（引擎判定 + 桌面端界面）。`request_user` 工具与 §4 规格待实现。

引擎（`kalo-harness`）此前对工具调用**不做任何授权判定**：模型说 `bash: rm -rf build`，引擎就执行。桌面端唯一的闸门是启动时的 project trust（信不信这个目录），粒度是「整个项目」而不是「这次操作」。

本文定义 **权限模式**：用户在会话界面选一个档位，引擎在每次工具执行前按档位放行、弹审批或拒绝。

## 一、用户可见的三个档位

| 界面标签 | key | 一句话 |
| --- | --- | --- |
| 只读 | `read-only` | 只看不改。要改动时逐次弹审批 |
| 工作区（默认） | `workspace-write` | 工作区内自由读写；越界写要审批 |
| 全自动 | `full-auto` | 不打扰，只挡住少数不可挽回的操作 |

档位是**会话级**的：每个会话记住自己的档位，随时可切；新会话用全局默认档位（初始为「工作区」）。

## 二、判定规格

### 2.1 判定输入

一次工具调用的命运由四个输入决定：

```ts
type PermissionDecision = "allow" | "ask" | "deny";

decide(
  mode: "read-only" | "workspace-write" | "full-auto",
  call: { tool: string; input: Record<string, unknown> },
  workspace: string,                 // 会话 cwd 的规范化真实路径
  grants: PermissionGrant[],         // 本会话已给出的追加授权
): PermissionDecision
```

**工作区**取会话 cwd 的规范化真实路径。路径比较必须 Windows 安全：先解析 `..` 与符号链接、盘符与路径大小写不敏感、**按路径分段比较而非字符串前缀**（否则 `D:\work` 会误匹配 `D:\work-old`）、支持 UNC 路径。

`~/.kalo/` 下的用户数据目录（memory / knowledge / sessions / attachments）**不算工作区**，走「工作区外」分支。

### 2.2 主判定表

| 操作 | 只读 | 工作区 | 全自动 |
| --- | --- | --- | --- |
| `read` / `grep` / `glob` / `ls` / `find` | 放行 | 放行 | 放行 |
| `write` / `edit`，目标在工作区内 | **审批** | 放行 | 放行 |
| `write` / `edit`，目标在工作区外 | **审批** | **审批** | 放行 |
| `bash` | **审批** | 放行 | 放行 |
| `request_user`（见 §4） | 放行 | 放行 | 放行 |
| 命中危险指令红线（见 §3） | 拒绝 | 拒绝 | 拒绝 |
| 写入受保护路径（见 §3.2） | 拒绝 | 拒绝 | 拒绝 |
| 其他工具（MCP / subagent / 扩展注册） | 放行 | 放行 | 放行 |

三条要点：

**只读档的写操作是「审批」而不是「拒绝」。** 用户明确要求「需要编辑时弹 UI 审批」——这个档位的定位是「我要逐个过一遍模型的改动」，不是「禁止一切改动」。所以审批通过后该次写入真的会执行。

**只读档的 bash 是「审批」。** 引擎无法静态区分 `ls -la` 与 `rm -rf`，一律拒绝会让只读档连跑测试都做不到，一律放行则档位名字是谎言。交给人一次一次判断。

**工作区档的 bash 是「放行」。** 这是让该档位可用的前提（`git`、`npm test`、`cargo check` 是高频操作，逐条审批等于不能用）。诚实的后果见 §7：bash 可以写到工作区外，所以「越界写需审批」在工作区档下是**约束模型的默认行为，不是不可绕过的边界**。

**表外的工具一律放行。** MCP server 提供的工具、subagent、其他扩展注册的工具，判定表无法知道它们的副作用（参数名、是否涉及文件全不可知）。选择放行而不是「未知就拒」：后者会直接搞砸所有 MCP 集成，而真要门禁它们需要每个工具声明自己的副作用元数据——那套机制目前不存在。这是本期的已知缺口，写在这里而不是隐瞄。

### 2.3 无 UI 时 `ask` 等于拒绝

print / json 模式、后台任务、定时任务没有可询问的人（`ctx.hasUI === false`）。此时 `ask` **立即判定为拒绝**（fail closed），返回明确理由，不挂死等一个永远不会来的回答。

这意味着定时任务如果需要写文件，必须跑在「工作区」或「全自动」档下——这是正确的默认，不是缺陷。

## 三、红线：与档位无关的硬拒绝

「全自动」不等于「什么都干」。有一层与档位无关的底线，三个档位都拒绝，**且不提供审批放行**。

理由：一个弹窗点「允许」无法让人真正评估 `rm -rf /` 的后果，把它做成可审批只是给灾难加一道形式手续。用户真要执行这类命令，应当自己在终端里手动执行——那是一次明确的人类行为，不是 agent 行为。

### 3.1 危险指令红线（Tier A）

只收**不可挽回且几乎没有合法 agent 用途**的模式。清单必须保持极短，每一条要有真实案例支撑，否则会变成误报机器。初始清单：

| 类别 | 模式（示意，实际用规范化后匹配） |
| --- | --- |
| 根/盘符递归删除 | `rm -rf /`、`rm -rf ~`、`rd /s /q C:\`、`Remove-Item -Recurse -Force C:\` |
| 磁盘与分区 | `format`、`diskpart`、`mkfs.*`、`cipher /w` |
| 引导与系统注册 | `bcdedit`、`reg delete HKLM\...`、`sc delete`（系统服务） |
| 全盘接管权限 | `takeown /f C:\ /r`、`icacls C:\ /grant ... /t` |
| 进程炸弹 | `:(){ :|:& };:` 及等价形式 |

**Windows 是默认契约**：`bash` 工具在 Windows 上经由 shell 执行（且 `shellPath` 设置允许用户换 shell），命令文本里既可能出现 POSIX 形式也可能出现 `cmd` / PowerShell 形式，匹配器两类都要覆盖。

匹配的局限必须写在实现注释里：shell 文本存在引号、变量展开、别名、`&&` 串联、base64 编码等无穷变体，**红线是防手滑的减速带，不是安全边界**。

### 3.2 受保护路径

以下路径的**写入**在所有档位拒绝：

- `~/.kalo/agent/auth.json`（凭证）
- `~/.kalo/agent/settings.json`、`trust.json`（引擎自身配置与信任决策）

模型没有正当理由改写自己的凭证与信任状态；这些应当由用户通过设置界面修改。模型误改 `auth.json` 会导致会话直接不可用，属于高频真实footgun。

## 四、`request_user` 工具（待实现，本文只定规格）

**当前引擎没有这个工具，本期也未实现。** 用户明确要求它在「工作区」档下可以弹出，本节先把规格记下来，实现排在后续。

它与权限审批是**两个方向**的交互：

| | 发起方 | 语义 |
| --- | --- | --- |
| 权限审批 | 引擎（因为档位判定） | 「模型想做 X，准不准？」 |
| `request_user` | 模型（主动） | 「我需要你的信息/决定才能继续」 |

### 4.1 规格

```ts
// 工具名：request_user
{
  question: string;            // 要问的问题
  kind?: "text" | "choice";    // 默认 text
  options?: string[];          // kind = "choice" 时必填
}
// 返回：用户的回答文本；或明确的「无人可问」/「用户取消」错误
```

行为：

- 三个档位都放行——它不改变任何状态，是纯询问，不需要授权;
- `ctx.hasUI === false` 时**不阻塞**，立即返回错误结果 `"No user available to answer in this run"`，让模型自行决定是继续还是收尾。这与权限审批的 fail closed 语义一致：不挂死；
- 用户取消（关闭弹窗 / 中止本轮）返回明确的取消结果，不是空字符串——空字符串会被模型当成有效答案;
- 底层直接复用 §5.2 的 extension UI 通道（`kind: "text"` → `input`，`kind: "choice"` → `select`），因此桌面端无需新增 UI。

### 4.2 与审批弹窗的关系

两者共用桌面端的同一个模态队列，但**视觉上必须可区分**：审批弹窗是「引擎在拦你的模型」，`request_user` 是「模型在问你」。前者带工具名与目标路径/命令，后者只有问题文本。用不同的标题前缀与图标区分。

## 五、审批交互

### 5.1 弹窗内容

弹窗要让人在两秒内做出判断，所以必须显示**具体做什么**，而不是「bash 请求执行」：

- `write` / `edit`：目标路径（工作区外的路径要显著标记）+ 改动规模（新增/删除行数或写入字节数）
- `bash`：完整命令文本（长命令折行显示，不截断关键部分）

完整 diff 预览留给后续迭代——第一期先保证信息足够判断，不追求好看。

### 5.2 选项与授权粒度

| 档位 | 选项 |
| --- | --- |
| 只读 | 允许一次 / 拒绝 |
| 工作区 | 允许一次 / 本会话允许同类 / 拒绝 |
| 全自动 | 不弹（除红线，红线不可审批） |

**只读档没有「本会话允许同类」。** 一旦允许了一类操作，这个档位就不再是只读，档位名字会变成谎言。用户如果嫌逐次审批烦，正确做法是切到「工作区」档——切档是一次显式的、界面上可见的决定，比从弹窗里悄悄拿到持久授权更诚实。

工作区档「本会话允许同类」的粒度：

- `write` / `edit` → **工具名 + 目标目录**，此后该目录下同工具放行；
- `bash` → 工作区档 bash 本就放行，此选项不出现。

不做整条命令记忆（一次一条毫无意义），不做「全部放行」（那等于切档）。

### 5.3 中止与超时

- 权限弹窗**不设超时**：等人是正确行为，自动超时会变成「静默失败」，比阻塞更难排查;
- 用户中止本轮（Ctrl+C / 桌面端「停止」）→ 弹窗随 agent 的 `signal` 关闭，本次调用判定为取消（按拒绝处理）;
- 后台会话弹出审批时，桌面端给一条 toast 提示需要切换到该会话处理（现有机制已具备）。

## 六、状态与持久化

### 6.1 会话条目

两类 `CustomEntry`（不参与 LLM 上下文，随会话日志持久化）：

```ts
/** customType: "permission-mode" */
interface PermissionModeEntry {
	mode: "read-only" | "workspace-write" | "full-auto";
	source: "default" | "user" | "flag";
}

/** customType: "permission-grant" */
interface PermissionGrantEntry {
	tool: string;                                    // write | edit
	scope: { kind: "dir"; path: string } | { kind: "reset" };
}
```

### 6.2 语义

- **有效档位 = 最后一条 `permission-mode` 条目 ?? 会话创建时 pin 的默认值。** 日志本身就是状态，会话重载不需要额外恢复机制。
- 会话创建时若日志中没有任何 `permission-mode` 条目，pin 一条 `source: "default"`；**已有条目的会话（resume）保持原值**，不套用当前全局默认。否则用户改一次默认档位就会篡改所有历史会话的语义。
- 切到当前档位是 **no-op**，不写条目，避免日志噪音与界面抖动。
- 切换档位**追加一条 `{ kind: "reset" }` 使此前所有授权失效**：授权是在旧档位语义下给出的，换档后不应继承。用追加而非删除，保持日志 append-only。

### 6.3 全局默认

`Settings`（`~/.kalo/agent/settings.json`）新增：

```ts
defaultPermissionMode?: "read-only" | "workspace-write" | "full-auto";  // default: "workspace-write"
```

**只在会话创建那一刻读取。** 改设置影响下一个新会话，不影响任何已存在会话。

### 6.4 为将来的 `custom` 预留形状

本期只有「档位」一个开关，不存在「匹配不上任何档位」的状态。但把当前档位的类型定为 `PermissionModeName | "custom"`，界面选择器按「选项列表 + 当前值，当前值可能不在选项里」实现：

- `custom` 是**派生态**，用户不能主动选中；
- 将来若引入第二个独立开关（如 OS 沙箱强度），只需补派生逻辑，前后端契约不用改。

代价极小，买到向前兼容。

## 七、模型可见性

档位注入系统提示（`before_agent_start` 返回 `systemPrompt` 追加；多扩展链式、append-only，不重写前缀，保住 KV cache）：

```
read-only:        Permission mode: read-only. Every file write and shell command
                  requires the user's per-operation approval. Batch related changes and
                  explain them before writing, so the user has fewer prompts to review.
workspace-write:  Permission mode: workspace-write. Writes inside the workspace and
                  shell commands run without approval; writes outside the workspace
                  require approval. Prefer staying inside the workspace.
full-auto:        Permission mode: full auto. Tool calls run without approval. A small
                  set of irreversible operations is refused outright and cannot be
                  approved.
```

只读档的提示里明确要求模型「批量化改动并先解释」——这是唯一能减少审批噪音的手段，写进提示比让用户忍受更有效。

切换档位时**不**向 transcript 注入额外消息：下一轮系统提示已体现新档位，中途注入会打乱桌面端消息呈现。

被拒绝时模型收到一条正常的 error toolResult，理由要能指导它改道：

```
Blocked by permission mode "read-only": the user rejected the write to D:\project\x\a.ts.
Do not retry the same write; explain what you intended and ask how to proceed.

Refused unconditionally: "rm -rf /" matches the dangerous-command list and cannot be
approved in any permission mode.
```

## 八、引擎实现

### 8.1 接入点：`tool_call` 扩展事件

`packages/agent/src/agent-loop.ts` 的 `prepareToolCall` 在**参数已 schema 校验、执行尚未开始**时调用 `config.beforeToolCall`：

```ts
if (beforeResult?.block) {
	const result = createErrorToolResult(beforeResult.reason || "Tool execution was blocked");
	if (beforeResult.terminate === true) result.terminate = true;
	return { kind: "immediate", result, isError: true };
}
```

三个性质使它适合承载权限判定：

- 钩子是 `async` 且接收 agent 的 `signal`，**在其中 await 一个审批弹窗是被支持的用法**；
- 阻断产生一条正常的 error toolResult，`reason` 进入模型上下文，模型能改道而不是整个 run 崩掉；
- 并行工具执行时 `prepareToolCall` 仍**顺序**执行（先串行 preflight 再并发跑），所以一批工具不会同时弹出多个审批框。

这个槽位已被 `packages/coding-agent/src/core/agent-session.ts` 占用，但它转发成可多路复用的扩展事件 `tool_call`（第一个返回 `block: true` 的处理器胜出）。**权限模式注册 `pi.on("tool_call")`，不抢 `beforeToolCall` 槽。**

### 8.2 询问通道：复用现有 extension UI

`ExtensionUIContext` 提供带 `signal` / `timeout` 的对话框：

```ts
select(title: string, options: string[], opts?: ExtensionUIDialogOptions): Promise<string | undefined>;
input(title: string, placeholder?: string, opts?: ExtensionUIDialogOptions): Promise<string | undefined>;
```

RPC 模式把它序列化为 `extension_ui_request`；桌面端 `chat-store.ts` 的 `handleExtensionUiRequest` 已把 `select` / `input` 压入 `extensionQueue`，`ChatView.tsx` 已有模态队列渲染，回复走 `respondExtension` → `extension_ui_response`。

**审批弹窗与 `request_user` 都不需要新增 sidecar 消息类型。** `ctx.hasUI` 为 `false` 即 fail-closed 判据。

### 8.3 为什么做成内置扩展

- 上游 `packages/coding-agent/README.md` 明确 "Pi does not include a built-in permission system"，`docs/usage.md` 指向「以扩展方式实现权限弹窗」。写进 core 会显著推高 vendored 引擎同步上游的成本。
- `agent-session.ts` 已 3345 行，远超本仓库 800 行上限，不应继续扩张。

### 8.4 文件结构（已实现）

```
kalo-harness/packages/coding-agent/src/extensions/permission/
  index.ts        接线：tool_call / session_start / before_agent_start / /permission 命令
  policy.ts       纯函数 decide()：档位主判定表
  danger.ts       纯函数：危险指令红线
  paths.ts        纯函数：工作区内外判定 + 受保护路径（Windows 安全的路径比较）
  state.ts        纯函数：foldMode / foldGrants，从会话日志折叠出状态
  prompt.ts       纯函数：系统提示贡献与三种拒绝理由文案
  types.ts        档位名、会话条目、决策类型
```

除 `index.ts` 外全部**零 I/O、纯函数、可单测**；权限判定的正确性全落在这五个文件里。`index.ts` 只负责接线，不含判定逻辑。

`state.ts` 是实现时从 `index.ts` 拆出的：「这个会话处于何种档位」本质是一个对日志的 fold，把它做成纯函数后，RPC 层也能直接复用它汇报状态（见 §9.1），避免在引擎里维护第二份权限状态。

注册进同目录 `../index.ts` 的 `builtInExtensions`（排在首位，使判定先于其他扩展的 `tool_call` 处理器）。

TUI 侧命令 `/permission`：无参报告当前档位与可选档位，带参切换；参数有自动补全。引擎还提供 `--permission-mode` 启动标志，优先于全局默认值。

## 九、桌面端

### 9.1 契约改动（已实现）

sidecar 契约只动了两处：

- `RpcSessionState` 增加 `permissionMode?: "read-only" | "workspace-write" | "full-auto" | "custom"`，`get_state` 返回；
- 新增 RPC 命令 `set_permission_mode { mode }`。

两个实现上的要点：

- `get_state` 的值用 `foldMode(session.sessionManager.getEntries())` 现算，**不在 RPC 层缓存**——权限状态归扩展所有，第二份副本只会多一个不同步的风险。
- `set_permission_mode` **转发给扩展自己的 `/permission` 命令 handler**，而不是另写一套切换逻辑，于是「切档同时清空授权 + 记两条条目」只有一个代码路径。扩展未加载时返回明确错误。

### 9.2 界面（已实现）

- `components/PermissionChip.tsx`：输入框旁的档位切换器，三个选项各带一句说明；`full-auto` 显橙色；`custom` 只展示不可选；`permissionMode` 缺失时整个 chip 隐藏（引擎没加载权限扩展，显示一个不生效的控件是说谎）。下拉底部带一行强度声明。
- 审批弹窗复用现有 `extensionQueue` 模态，不新建组件；`ChatView` 根据「审批：」标题前缀给它橙边框 + 橙色标题，与「模型在问你」区分；标题第二行起的详情（路径 / 命令）用等宽字体单独展示。
- `components/PermissionSettings.tsx` + 设置页新增「权限」tab：全局默认档位，文案明确写「只影响新建对话」。读写走新增的 Tauri 命令 `read_default_permission_mode` / `write_default_permission_mode`（`src-tauri/src/pi_config.rs`），它们 **只 patch `settings.json` 的单个字段**而不是整文件覆写，因为这个文件同时属于引擎和用户。

### 9.3 附带修正：一个错标的 chip

输入框原有一个标着「权限模式」、选项为「默认权限 / 全部放行」的控件，它实际调的是 `setSteeringMode`——**插话消息的投递方式，与授权毫无关系**。真权限档位上线后两个 chip 并存会直接误导用户，所以把它改回真实语义：重命名为 `SteeringChip`，标题「插话投递方式」，选项改为「逐条插话 / 一次全送」。`chat-store` 里一句写错的 toast（设置 steering 失败却报「设置权限模式失败」）一并改正。

## 十、安全强度声明

本设计实现的是**引擎侧的路径与命令判定**，不是 OS 级隔离。具体地说：

- 被放行的 bash 命令内部可以做任何事（`git` 后面可以跟 `-c core.sshCommand=...`）；
- 「工作区」档下模型可用 bash 写到工作区外（`echo x > C:\...`），绕过 write/edit 的路径判定；
- 红线匹配的是 shell 文本，存在引号、变量展开、别名、编码等规避空间；
- 判定基于工具参数，不拦截工具内部的间接文件访问。

即：**权限模式防的是「模型误操作」，不防「刻意的对抗性绕过」。** 前者真实且高频（模型自作主张删文件、改工作区外的配置、覆盖没读过的文件），后者需要 OS 沙箱（Windows ACL / job object），属于独立工程。

这个界限必须同时写进用户可见文案，不能让用户以为选了「只读」就绝对安全。

## 十三、未决问题

- **`bash` 在只读档的审批噪音**：一次 `npm test` 一个弹窗是可接受的，但模型习惯用 bash 做探索（`ls`、`cat`、`git status`）。是否给只读档一个「明显只读的 bash 命令白名单」直接放行？倾向**不做**：白名单同样是文本匹配，`git status && rm -rf x` 就穿了，反而制造虚假安全感。先按全审批上线，看真实噪音量再定。
- **红线是否可配置**：让用户往红线里加自己的模式是合理需求，但配置错一条就会莫名阻断。第一期写死，等有真实诉求再设计。
