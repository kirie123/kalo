# 工作段母气泡（连续思考/工具调用的可折叠容器）

状态：已实现（v1）。HTML 效果图：`doc/mockups/2026-09-13-work-segment.html`。

实现落点：

- `kalo-desktop/src/lib/work-segment.ts`（纯逻辑 + `work-segment.test.ts`）
- `kalo-desktop/src/lib/tool-labels.ts`（从 `ToolCallGroup.tsx` 抽出的纯标签逻辑，段头与行共用）
- `kalo-desktop/src/components/WorkSegment.tsx`（母气泡）、`TimelineItem.tsx`（从 `MessageList.tsx` 抽出，顶层与段内共用）
- `kalo-desktop/src/components/MessageList.tsx`（接线）、`index.css`（`.work-segment*` 样式）

**不涉及引擎契约，也不碰 `buildTimeline`**：历史会话仍按原样重建时间线，折叠只是渲染层的一层 view。

## 问题

当前对话区是一条**扁平流**：`Thought (856 chars)`、`执行了 1 条命令`、`读取了 2 个文件`… 每一条都是独立气泡，
一轮复杂任务能产生 20–60 条。用户要回头找关键信息（自己发的问题、agent 的正式回复、某次 diff）时，
必须手动翻过整段过程噪声。现象：

- 一屏里只有 1–2 条是"结论"，其余都是过程；
- 过程条目已经各自可折叠，但**折叠粒度太细**，折 30 次和不折一样累；
- 历史会话重新打开时，所有过程重新铺开，滚动距离没有任何压缩。

结论：缺的不是"每条能折叠"，而是**把一轮里连续的过程收成一个可折叠的母容器**（工作段）。

## 方案

### 1. 概念：工作段（work segment）

把时间线里**连续的过程型条目**收敛成一个 `segment` 渲染节点，由一个母气泡承载。

条目分类（在纯逻辑层判定）：

| 类别 | 条目 | 归属 |
| --- | --- | --- |
| 过程 | `toolGroup` | 段内 |
| 过程 | `assistant` 且正文文本全为空（只有 thinking 块） | 段内 |
| 过程 | `retry`（重试提示） | 段内 |
| 输出 | `assistant` 且含非空 text 块 | 段外（正常渲染） |
| 边界 | `user` / `compaction` / `changes` / `notice` | 段外，且切断当前段 |

**混合消息的处理**：一条 assistant 消息里同时有 thinking 和正文时，按"输出"处理（整条留在段外），
thinking 仍旧是它内部那行可折叠小气泡。不做消息内拆分——v1 不引入"虚拟条目"，避免 id、
memo、复制整轮文本（`buildTurnCopyText`）三处同时变复杂。

`changes`（本轮改动文件卡片）刻意留在段外：它是一轮的结论之一，折进去反而更难找。

### 2. 渲染层：`lib/work-segment.ts`（纯逻辑，可单测）

```ts
export type RenderRow =
  | { kind: "entry"; entry: TimelineEntry }
  | { kind: "segment"; id: string; entries: TimelineEntry[]; stats: SegmentStats };

export interface SegmentStats {
  steps: number;                 // 段内步数（thinking 块数 + 工具调用数）
  thoughts: number;
  tools: { name: string; count: number }[];  // 按出现顺序，用于摘要 chips
  running: boolean;              // 段内有 running 的调用
  error: boolean;                // 段内有 error
  lastLabel: string;             // 折叠态副行：最后一步做了什么
}

export function foldWorkSegments(timeline: TimelineEntry[]): RenderRow[];
export function isProcessEntry(entry: TimelineEntry): boolean;
export function segmentStats(entries: TimelineEntry[]): SegmentStats;
/** 逐元素引用比较，供 WorkSegment 的 memo 用。 */
export function sameSegmentEntries(a: TimelineEntry[], b: TimelineEntry[]): boolean;
```

- 只有**连续过程条目 ≥ 2 条**才成段；单独一条保持原样（不给一条 Thought 套壳）。
- `segment.id` = 段内第一条 entry 的 id ⇒ 流式过程中 id 稳定，折叠状态不会跳。
- 完全无副作用、不碰 IPC/DOM ⇒ 落在 `kalo-desktop/AGENTS.md` 允许并要求单测的纯逻辑层：
  `work-segment.test.ts` 覆盖"成段/不成段/边界切断/统计计数/running 传播"。

`MessageList` 只多一步：`const rows = useMemo(() => foldWorkSegments(timeline), [timeline])`，
然后按 `rows` 渲染；段内条目仍复用现有 `ToolCallGroup` / `AssistantMessage`，零改动。

### 3. 母气泡形态

折叠态（一行，默认）：

```
[✓]  思考并执行 12 步   [4 次思考] [读取了 5 个文件] [执行了 3 条命令]         ›
     最后一步：读取 kalo-desktop/src/lib/chat-store.ts
```

运行态（自动展开；折叠时显示活动预览）：

```
[◐]  正在工作 · 第 7 步   [1 次思考] [执行了 1 条命令]                        ⌄
     正在 npm run check
```

段头不显示耗时：`TimelineEntry` 里没有可靠的分段起止时间戳（`ToolCallRecord` 无时间戳），
宁可不显示也不编一个；要做得先在记录上补时间戳，属于另一个改动。

展开态：母气泡变成一个带左侧竖线（rail）的容器，里面就是今天的那些行，
标题行常驻顶部（`position: sticky`），滚到哪都能一键收起。

### 4. 默认折叠策略（这是体验的关键）

| 场景 | 默认 |
| --- | --- |
| 正在运行的那个段 | 展开（跟着 agent 看） |
| 本轮结束（`agent_settled`）后的段 | 自动折叠成一行 |
| 从会话历史回放出来的段 | 折叠 |
| 用户手动点过的段 | 记住用户的选择，自动规则不再覆盖 |

实现：状态留在 `WorkSegment` 内部 —— `const [manual, setManual] = useState<boolean | null>(null)`，
`open = manual ?? autoOpen`，`autoOpen = stats.running || 是最后一行且本轮未结束`。
段 key 是段内第一条 entry 的 id；切会话会重建时间线、拿到新的 entry id ⇒ 组件重挂载、manual 自然清空，
历史回放默认收起。

全局「过程默认折叠 / 展开」设置项和「全部收起」按钮 v1 未做（需要把状态提到 store），留作后续。

### 5. 滚动行为

- 自动折叠发生在本轮结束时，此时用户通常在底部：仍走 `stickToBottom` 逻辑，无跳动。
- 用户手动折叠上方某段会使内容变短、视口"上移"：折叠前记录段头相对视口的 `getBoundingClientRect().top`，
  折叠后用 `scrollTop += delta` 把段头钉回原位（与 `loadOlderHistory` 的 prepend 补偿同一套路）。

### 6. 性能

折叠态只渲染一行 DOM，长会话的节点数从 O(过程条目) 降到 O(轮数)，比现在更轻。
代价是 `foldWorkSegments` 每次 flush 重建数组 ⇒ 段组件用 `memo` + 自定义比较（比较 `entries` 各元素引用），
配合 store 已有的"只克隆被修改条目"策略，展开态的重渲染面和现在持平。

## 不做什么（v1 边界）

- 不做消息内 thinking/text 拆分（见上）。
- 不做全局折叠开关（见上）。
- 段内的单条工具组仍保留自己的组标题（「读取了 1 个文件」+ 具体行），层级偏深；
  要简化得改 `ToolCallGroup` 在 `calls.length === 1` 时的形态，属于另一个改动。
- 不做"按语义给段起名"（用 LLM 总结这段在干嘛）——留作 v2，成本与延迟都要另议。
- 不改引擎契约：纯前端渲染层改动，`pi-bridge` 不动。

## 验收

- 一轮 30 步的任务，收起后对话区该轮只占 2 行（用户问题 + 段头）+ 正式回复。
- 切换会话、回放历史：过程默认收起，滚动距离肉眼可见变短。
- 运行中仍能实时看到 agent 在做什么（展开态，或折叠态的活动预览行）。
- 手动展开的段不会被自动规则重新收起。
- `npm test` 覆盖 `work-segment.test.ts`（11 例：成段/不成段/边界切断/统计/running 传播/id 稳定）；
  组件表现人工验证（TSX 不在 vitest 收集范围）。
- 历史会话不受影响：`buildTimeline` 与会话文件读写零改动，折叠纯发生在渲染层。
