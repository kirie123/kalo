# Harness 工具失败修复方案（同批竞态 / DSML 补齐 / Windows 质量）

日期：2026-10-03
范围：`kalo-harness` 内 `packages/agent`、`packages/coding-agent` 两个包
前置结论（同日复盘）：①默认并行执行下同一条消息里的文件操作竞态；②DSML 安全网对同名泄漏的遮蔽与可见性不足；③Windows 上 GBK 输出、`/tmp` 路径、MSYS 参数三类摩擦。

## 0. 总览

| 优先级 | 改动 | 主要文件 | 验收 |
|---|---|---|---|
| P0 | 文件工具同批有序列化 + 写盘原子化 | `tools/read.ts`、`tools/edit.ts`、`tools/write.ts`、新增 `tools/atomic-write.ts` | 同批 `[read, edit]` 不再假报错；`[write, bash 验证]` 能读到新内容；写盘期间的并发读不会读到空文件 |
| P1 | DSML 检测按调用块计数 + 提示上限、注入消息落转录 | `agent/src/dsml-tool-calls.ts`、`agent/src/agent-loop.ts` | 同名不同参数的泄漏调用能触发提示；注入消息出现在会话 jsonl |
| P2 | GBK 解码回退、`/tmp` 映射、bash 提示 | `tools/output-accumulator.ts`、`utils/paths.ts`、`tools/bash.ts` | GBK 字节解码为正确中文；win32 下 `/tmp/x` 与 Git Bash 指向同一目录 |

非目标（本方案不做）：

- 网关侧把思考通道的工具标记转换/剥离（根治点在网关，不在本仓库）。
- 两个 bash 调用之间的同文件竞态（无通用解法；靠工具说明引导「写 + 验证写在一条命令里」）。

## 1. P0：同批文件竞态

### 1.1 问题回顾（代码事实）

- 默认并行：`packages/agent/src/agent.ts:237`（`toolExecution ?? "parallel"`），coding-agent 未覆盖。
- 全批串行的开关：任一 tool call 声明 `executionMode: "sequential"` 即整批按发出顺序串行（`agent-loop.ts:532-535`）。
- `ask-user` 已用该机制（`extensions/ask-user/index.ts:155`）；`read/edit/write` 没声明。
- `edit/write` 有同路径互斥队列（`file-mutation-queue.ts`），但 read 不在其中；写盘用 `fs.writeFile`（truncate+write，非原子）。

由此产生两类假报错：read 读到写一半的空文件（`Offset N is beyond end of file (1 lines total)`）；同批 read 已返回内容但 edit 仍报 `File has not been read in this session`（readState 在 readFile 之后记录，edit 的守卫可能先到）。

### 1.2 方案对比

| 方案 | 覆盖范围 | 代价 | 结论 |
|---|---|---|---|
| A. 给 `edit`、`write` 标 sequential | 同批 read→edit 顺序、write→验证顺序 | 含 edit/write 的批整体串行 | **必做** |
| B. A + 给 `read` 也标 sequential | 再覆盖「bash 写文件 + 同批 read」 | 含 read 的批整体串行；「两个长命令 + read」同批时两个长命令不再并行（罕见） | **建议做**，如担心长命令并行可暂缓，留作后续开关 |
| C. coding-agent 默认 `toolExecution: "sequential"` | 全部同批竞态（含 bash↔bash） | 两套长测试同批等既有并行用法全部串行 | 不做 |
| D. 只做同路径协调器（read 等 mutation、mutation 等 read） | 只能防 truncation 可见性；**保证不了 read→edit 的发出顺序**（edit 先起跑时 read 还没登记，守卫仍会竞态） | 实现与测试成本最高 | 不单独做 |

结论：**P0 用 A（+B），原子写作为独立加固（对 D 也不冲突）**。

### 1.3 改动清单

1. 三个工具定义各加一行（并写注释说明为什么）：

```ts
// tools/edit.ts:325 附近（write.ts:259、read.ts:222 同）
return {
  name: "edit",
  ...
  // 同批里文件操作按发出顺序执行：read→edit（读后改守卫）、edit/write→bash（写后验证）。
  // 不标注时整批并行，read 可能落在 writeFile 的 truncate 窗口，守卫也可能早于 read 登记。
  executionMode: "sequential",
  async execute(...) { ... },
};
```

2. 新增 `tools/atomic-write.ts`，edit/write 的默认 `writeFile` 换用它：

```ts
import { randomBytes } from "node:crypto";
import { chmod, rename, stat, unlink, writeFile } from "node:fs/promises";
import { basename, dirname, join } from "node:path";

/** 同目录临时文件 + rename：并发读者只会看到旧内容或新内容，看不到 truncate 中间态。 */
export async function writeFileAtomic(path: string, content: string): Promise<void> {
  const dir = dirname(path);
  const tmp = join(dir, `.${basename(path)}.pi-${process.pid}-${randomBytes(4).toString("hex")}.tmp`);
  let mode: number | undefined;
  try {
    mode = (await stat(path)).mode;
  } catch {
    // 新文件：沿用默认权限
  }
  try {
    await writeFile(tmp, content, "utf-8");
    if (mode !== undefined && process.platform !== "win32") await chmod(tmp, mode);
    await rename(tmp, path); // Windows 上由 libuv 以 MOVEFILE_REPLACE_EXISTING 覆盖
  } catch (error) {
    await unlink(tmp).catch(() => undefined);
    throw error;
  }
}
```

   - `edit.ts:98` / `write.ts:46` 的默认 ops 里把 `fsWriteFile(path, content, "utf-8")` 换成 `writeFileAtomic`。
   - 失败时目标文件保持原样；临时文件清理失败只吞掉 unlink 错误。
   - 成功后 `readState.record` 的现有调用位置不变（rename 已让目标文件是新内容）。

3. 兼容与边界：
   - 临时文件在目标同目录，避免跨卷 rename。
   - 文件名以 `.` 开头、含随机数：不会被目录扫描误认为目标文件；`.gitignore` 不受影响（瞬时文件）。
   - POSIX 保留原 mode（可执行脚本场景）；Windows 跳过 chmod（rename 后 ACL 继承目录）。

### 1.4 测试

- 单测 `tools/atomic-write.test.ts`：覆盖写不丢 mode（POSIX）、同时写不产生半截文件（写 1MB 内容并在 rename 前轮询读，读到的只能是旧内容或完整新内容）、rename 失败时临时文件被清理。
- 工具定义单测（可在 `test/tools.test.ts` 或新增 `file-tool-ordering.test.ts`）：断言 `read/edit/write` 的 `executionMode === "sequential"`。
- 用 `test/suite/harness.ts` + faux provider 做一条批级回归：同一条 assistant 消息里发 `read` + `edit`，断言 edit 成功（不再 `File has not been read`）；同一条消息里发 `write` + `bash(cat)`，断言 cat 输出新内容。
- agent 侧已有并行/串行测试（`packages/agent/test/agent-loop.test.ts`），确认 sequential 分支行为不变。

## 3. P2：Windows 质量

### 3.1 GBK 输出解码回退（`output-accumulator.ts`）

现状：`new TextDecoder()`（UTF-8 非 fatal）硬解所有子进程输出（40、70、85 行），zh-CN 上 `taskkill`/PowerShell 的 GBK 输出变乱码。

方案：UTF-8 严格流式解码，失败即整条流粘性切换 GBK；写入临时文件的原始字节不变。

```ts
// 字段：decoder: TextDecoder; gbkDecoder?: TextDecoder; encoding: "utf-8" | "gbk" = "utf-8"
private decodeChunk(data: Buffer, streamEnd: boolean): string {
  if (this.encoding === "gbk" && this.gbkDecoder) {
    return this.gbkDecoder.decode(streamEnd ? undefined : data, { stream: !streamEnd });
  }
  try {
    return this.decoder.decode(streamEnd ? undefined : data, { stream: !streamEnd }); // fatal: true
  } catch {
    try {
      this.gbkDecoder = this.gbkDecoder ?? new TextDecoder("gbk");
      this.encoding = "gbk";
      return this.gbkDecoder.decode(data, { stream: true });
    } catch {
      return new TextDecoder().decode(data); // 运行时不支持 gbk：退回现状
    }
  }
}
```

- 构造 `fatal: true` 的 UTF-8 `TextDecoder`；流式模式下跨块被切半的多字节字符会被缓冲，不会误判。
- 已验证 Bun 1.3.11 与 Node 均支持 `TextDecoder("gbk")`；不支持时回退现状。
- 已知局限：一条流里混排 UTF-8 与 GBK 时，粘性选择会让后半段乱码；原始字节日志（`fullOutputPath`）不受影响，优先保证命令输出正文可读。

### 3.2 `/tmp` 路径映射（`utils/paths.ts`）

现状：`normalizeWindowsShellPath` 处理 `/d/...`、`/mnt/d/...`、`/cygdrive/d/...`，不处理 `/tmp`；Node 解析成 `<当前盘>:\tmp`，而 Git Bash 的 `/tmp` 实测等于 `os.tmpdir()`（两者都是 `%TEMP%`）。

方案：win32 下把 `/tmp` 与 `/tmp/*` 映射到 `os.tmpdir()`：

```ts
function mapWindowsPosixTemp(filePath: string): string {
  const match = /^\/tmp(?:\/(.*))?$/i.exec(filePath);
  if (!match) return filePath;
  return join(tmpdir(), match[1] ?? "");
}
// normalizePath() 内，win32 分支在 normalizeWindowsShellPath 之后调用
```

- 只匹配完整前缀 `/tmp`（`/d/tmp/...` 与 `D:/tmp/...` 不受影响）。
- 让 read/write/edit/glob/grep/ls 与 bash 的 `/tmp` 指向同一处。
- 测试：win32 下 `/tmp/a.txt` → `join(os.tmpdir(), "a.txt")`、`/tmp` → `os.tmpdir()`；非 win32 不变。

### 3.3 bash 工具提示（`tools/bash.ts`）

`bashToolSystemPromptContribution.guidelines` 增加平台条件项（仅 win32 注入，避免污染通用提示）：

- 给原生程序传 `/开关` 会被 MSYS 当路径转换（`taskkill /PID` → `C:/Program Files/Git/PID`），改用 `//PID`；
- `/tmp` 与 Node 工具一致（映射到系统临时目录），无需自行换算。

### 3.4 `PYTHONUTF8`（可选，默认不动）

中文 heredoc 喂 `py -3.12 - <<'PY'` 时脚本被按 GBK 解码（会话实测 SyntaxError）。建议先只在 bash 提示/文档里说明显式 `PYTHONUTF8=1`；是否在 `getShellEnv()` 对 win32 默认注入，单独评估（会改变用户脚本的默认文本编码行为，需明确同意后再做）。

## 5. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| sequential 让含文件工具的批串行 | 长命令与 read/edit 同批时晚开始 | 用 A（+B）；观测实际会话里长命令 + 文件工具同批的比例，异常再收紧 |
| 原子写在 Windows 上被 AV 短暂锁定 rename | 写失败 | 目标文件不被破坏；必要时对 EPERM/EACCES 加一次短重试 |
| GBK 粘性对混排流后半段乱码 | 输出可读性 | 记录局限；原始字节仍可查 |
| nudge 上限提到 8 | 极端模型反复解释时上下文变长 | 上限仍存在；观察后调整 |
| 修改 vendored 上游文件 | 未来同步 pi 冲突 | 改动集中在 kalo 已定制文件（readState/DSML）+ 3 处单行 executionMode，冲突面小 |
