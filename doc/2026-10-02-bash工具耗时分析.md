# bash 工具耗时分析（Kalo 会话 · Windows）

2026-10-02。分析对象：`~/.kalo/agent/sessions/--D--opensource-project-cowith--/` 最近 6 个会话（2026-09-30 ～ 2026-10-02），工作目录 `D:\opensource-project\cowith`。

## 结论速览

1. **单次 bash 的固定开销很小**：0.1–0.3s（sleep 标定法，n=49，中位 188ms）；`ls/cat/sed/tail` 类命令中位 0.10s。Kalo 也没有给引擎降优先级——`priority.rs` 只抬 UI/WebView，明确注释「不动 pi sidecar」。
2. **慢的是命令本身**，三类为主：
   - 长跑任务：pytest 单次 581s / 503s / 385s，electron 探针 129s，python 脚本 73s / 60s；
   - 主动 sleep 轮询：75–200s × 19 次（合计 795.7s，占单调用 bash 总时长 13%）；
   - Windows 上全仓库 grep：单次 6–23s（实测 20.4s，其中 sys=19.3s / user=1.0s，全是目录遍历）。
3. **并行批把快命令显示成慢命令**：同一 assistant 消息里的多个 tool call 并行执行，结果统一在批末写出（`agent-loop.ts::executeToolCallsParallel` 在 `Promise.all` 之后才创建 toolResult）。JSONL 里同批 toolResult 时间戳完全相同 ≈ 批内最慢那条。例：`ls` 与全仓 grep 同批 → 两条都记 17.9s。
4. **找到一个真实缺陷**：后台 job（`run_in_background` / 定时任务）用 `Git\usr\bin\bash.exe` 直跑，PATH 里没有 `/usr/bin`，`tail/rm/ls/stat/tee` 等 coreutils 全部 not found（exit 127），会话里实际发生并导致重试。前台 bash 用 `Git\bin\bash.exe` wrapper（会注入 `/mingw64/bin:/usr/bin`），所以前台正常。
5. 附带发现：system prompt 写 “Use bash for file operations like ls, rg, find”，但机器上没有 `rg`（`~/.kalo/agent/bin` 只有 `fd.exe`），会话里出现过 `rg: command not found`。

## 四条慢因与证据

### 1. 命令本身的长尾（主因）

pytest 单跑 6–10 分钟是真实执行时间；sleep 轮询是模型自选的等待方式（prompt 已写「不要 sleep 轮询」，仍用了 19 次）。与 Kalo 无关。

### 2. Windows 全仓库搜索（环境放大）

workspace 组成：`node_modules` 目录 135 个、`dist` 目录 588 个、`cowith-desktop/release` 1.8GB、根 `node_modules` 1.3GB；除根 node_modules 外还有 144,622 个文件。实测（同机、暖缓存）：

```
cd /d/opensource-project/cowith
time grep -rn "PI_CODING_AGENT" --include="*.ts" --include="*.md" . | grep -v node_modules | head -40
→ real 20.4s   user 1.0s   sys 19.3s     # 目录遍历开销
time grep -rn "PI_CODING_AGENT" --include="*.ts" --include="*.md" \
     --exclude-dir=node_modules --exclude-dir=.git --exclude-dir=.next --exclude-dir=dist .
→ real 3.4s                              # 结果相同
```

`grep -r … | grep -v node_modules` 是先扫后滤，不省任何遍历；`--exclude-dir` 让 grep 不下钻。20.4s → 3.4s，6 倍差距。装 ripgrep 会更低（rg 默认尊重 .gitignore，node_modules/.next 直接不入遍历）。

### 3. 每次 bash 的固定开销 ~0.1–0.3s（不是问题，但要有数）

用 49 条「只有 sleep N」的独立批标定：latency − N 的中位 = 188ms（min 105ms）。包含 shell 启动、spawn、输出采集、结果落盘。`Git\bin\bash.exe` 在 Windows 上是 44KB wrapper + 1.9MB 真 shell 两层进程，换来的是 PATH 正确。

### 4. 并行批「批末统一发出」的观感放大

`packages/agent/src/agent-loop.ts::executeToolCallsParallel` 并行跑同一条 assistant 消息的所有 tool call，在 `Promise.all` 完成之后才逐条创建/写出 toolResult → 同批结果在 JSONL 里时间戳一致，UI 上快的那个也要等到慢的结束；模型也要等整批才能继续。
实例：`ls agent-runtime/src/…`（快）与 `grep -rn "hasRenderSurface" …`（17.9s）同批 → 两条都记 17.9s；`read`（3ms）与慢 grep 同批 → read 也显示 grep 的耗时。6 个会话里这类「快+慢同批」共 195 批。

## 两个缺陷

### A. 后台 job 的 bash 缺 coreutils

`kalo-desktop/gateway/src/scheduler.ts::resolveBash()` 故意优先 `C:\Program Files\Git\usr\bin\bash.exe`（真 shell；注释说明原因：wrapper 会让 `child.kill()` 只杀 wrapper、真 shell 存活并占着 cwd）。但真 shell 直跑时**不会**把 `/usr/bin` 加进 PATH，wrapper（`Git\bin\bash.exe`）才会注入 `/mingw64/bin:/usr/bin`。本机复现：

```
PATH="/c/Windows/system32:/c/Windows" "C:\Program Files\Git\bin\bash.exe"     -c 'command -v ls'  → /usr/bin/ls ✓
PATH="/c/Windows/system32:/c/Windows" "C:\Program Files\Git\usr\bin\bash.exe" -c 'command -v ls'  → 没找到 ✗
```

会话证据（后台 job 经 `job_output`/读日志暴露）：

- bash-141：`make runtime-check 2>&1 | tail -60` → `tail: command not found`
- bash-142：重试改重定向落文件 → `make: command not found`，EXIT=127
- bash-144：`rm -f …` → `rm: command not found`（又废一轮）
- 更早会话还有 `ls / stat / tee` 的同类报错

（`make`/`bc` 是这台机器真没有，不算这条；`tail/rm/ls/stat/tee` 都是 Git 自带、只是没进 PATH。）

修法（最小改动，保留「用真 shell」的设计）：spawn job/定时任务时把 `dirname(resolveBash())`（`…\Git\usr\bin`）前置进 PATH（Windows 形式即可，MSYS 会转换）。引擎自带 bash 工具没这个问题——它走 `getShellConfig()`，优先 wrapper，所以前台正常；只有 gateway 的 job 与 scheduler 用真 shell 直跑。

### B. prompt 推荐 `rg`，但包里没有

`kalo-harness/packages/coding-agent/src/core/system-prompt.ts:106`：`addGuideline("Use bash for file operations like ls, rg, find")`。`~/.kalo/agent/bin` 只放了 `fd.exe`；会话里出现过 `rg: command not found`，模型随后退回 grep。建议随包带 `rg`（与 fd 同路径分发），或把 guideline 改成实际存在的工具并提示 `--exclude-dir`。

## 复现 / 验证方法

- 会话时间线：`entry.timestamp`（落盘）与 `message.timestamp`（assistant=开始流式；toolResult=完成）之差；同一 assistant 消息内多个 tool 的批耗时 = 批内最慢那条。
- 全库搜索对比：上文两条 grep 命令。
- 固定开销标定：统计「只有 sleep N」的独立批的 latency − N。
- 后台 shell：`run_in_background` 跑 `command -v head; command -v ls` 复现。
