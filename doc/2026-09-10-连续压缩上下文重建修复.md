# 连续压缩上下文重建修复

## 问题

会话 JSONL 采用追加写入，连续压缩会在同一分支上保留多个 `compaction` 节点。每个新摘要通过 `previousSummary` 吸收前一摘要，因此活动模型上下文只应包含最新摘要。

现有上下文重建把最新 `compaction` 放在首位，再附加 `firstKeptEntryId` 到最新压缩节点之间的全部条目。该区间若包含旧 `compaction`，旧摘要会再次进入模型请求，形成语义和 token 重复。

同时，token 高水位按消息数组倒序寻找压缩摘要。由于最新摘要被放在数组首位、重复旧摘要位于后方，旧摘要可能被误判为最新边界，使压缩前 assistant usage 再次参与估算，触发无必要的连续自动压缩。

## 上下文投影契约

会话文件继续保留完整追加历史，不迁移、不删除既有 `compaction` 节点。

`buildContextEntries()` 对当前分支执行以下投影：

1. 查找当前分支最新的 `compaction`。
2. 将该最新 `compaction` 作为唯一压缩摘要放入活动上下文。
3. 保留其 `firstKeptEntryId` 到该节点之前的普通消息、上下文可见条目和元数据。
4. 过滤上述保留区间内所有更早的 `compaction` 节点。
5. 保留最新 `compaction` 之后的条目。

该规则只改变发送给模型和运行时使用的投影，不改变 JSONL 存储、分支树、摘要迭代输入或桌面端历史展示协议。

## Token 边界

`estimateContextTokens()` 仍使用压缩后 assistant usage 的高水位抵御兼容 provider 的增量 usage，但压缩边界必须是消息集合中时间戳最大的 `compactionSummary`，不能依赖数组位置。

正常情况下，上下文投影只会产生一个摘要。按最大时间戳识别是防御性处理，用于兼容旧会话、扩展注入或调用方直接构造的消息数组。

边界之后的 usage 才能作为高水位候选；边界之前保留消息中的历史 usage 只能按本地消息内容估算，不能重新触发阈值压缩。

## 回归验证

必须覆盖：

- 连续两次压缩且第二次 `firstKeptEntryId` 位于第一次压缩之前时，活动上下文只有第二次摘要。
- 旧摘要对应的消息仍保留，但旧摘要节点本身不进入活动上下文。
- 消息数组含多个摘要且顺序不是时间顺序时，token 估算使用时间戳最大的摘要作为边界。
- 压缩前的大 usage 不得覆盖压缩后较小的真实 usage。

## 后续边界

本次不调整 `reserveTokens`、`keepRecentTokens`、摘要提示词或工具输出截断策略。完整请求预算、用户消息头尾保留和大型输出恢复指针属于后续独立改造。
