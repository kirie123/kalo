# 首次使用引导

2026-08-25

装完 Kalo 打开，看到的是一个空对话框。两件事没人告诉新用户：

1. **它能干什么。** README 里那四个纵深（投资分析 / 知识沉淀 / 数据自动拉取 / 演化）
   在界面上只是侧边栏四个图标，点进去才知道是什么。首屏只有「我们该做什么？」和六个
   快捷 chip。
2. **不配模型什么都跑不了。** 全新机器上 `agent/auth.json` 与 `models.json` 都不存在，
   模型选择器显示「暂无模型，请先添加」，发第一条消息撞的是引擎的 `No API key`。配置
   入口埋在 设置 → 模型 里，README 里那句「首次启动后填个 Key」在 app 内部无处可见。

做法：初次启动全屏引导五步——欢迎 + 四大纵深 + 配置模型（带连通测试）。

## 版式

覆盖内容区的绝对定位层，**盖在 TitleBar 之下**（`absolute inset-0` 挂在标题栏下面那个容器
里，而不是 `fixed` 盖住整个窗口），所以窗口仍然能拖能关——无边框窗口的拖动和关闭全靠那条
标题栏，糊住它等于把人关在引导里。自上而下：
eyebrow（小号 accent 字距拉开）→ 三张要点卡 → 大标题 → 副标题 → 底部 上一步 / 圆点 /
下一步，右上角「跳过」。全部走现有 token（`bg-base` / `bg-card` / `border-edge` /
`text-ink` / `text-dim`），明暗主题自动跟随，没有新 CSS 变量。

圆点可以直接点着跳步。左右方向键翻页只在前四步接管——第五步是表单，方向键在 select 和
input 里另有含义。Esc 任何时候等同「跳过」。

## 文案是数据，不是组件

前四步的 eyebrow / 标题 / 副标题 / 三张卡片全在 `features/onboarding/steps.ts` 的一张
表里，组件只负责渲染。这是 `quick-actions.ts` 立的规矩：领域知识只出现在数据表和 skill
的 markdown 里，不长进组件代码。加一步、改一句话都不用碰 tsx。

图标同理——`steps.ts` 只写图标的 key（`"folder"` / `"diff"` / …），SVG 集中在
`icons.tsx`，与 Sidebar 那批同风格（16×16、stroke 1.3）。

## 第五步：配置模型

三个区，全部复用已有机制，不新增任何落盘格式：

- **内置 Provider**：下拉 + 密码框，写 `auth.json`。选项复用 `SettingsPage` 里的
  `BUILTIN_KEY_PROVIDERS`（这次把它 export 出来，两处共用一张表——两份清单迟早会分叉）。
- **中转 / 本地模型**：直接开现成的 `ProviderEditModal`，它已经有 Ollama / LM Studio
  预设、baseUrl 归一化、占位 Key 那套。引导不重写一份简化版，因为简化版必然缺 compat
  开关，而缺了它的用户会以为 Kalo 接不了自己的中转。
- **选默认模型**：候选一律来自引擎（`listEngineModels`，走的也是下面那个一次性会话，
  发的是 `get_available_models`，零 token）。前端不硬编码任何模型 ID——模型列表跟引擎版本
  走，抄一份就一定会过期，而过期的下拉框比空下拉框更坑：用户会以为是自己填错了。
  选完调 `chatStore.setModel`。首启没有 session，它只落 `kalo.lastModel` 偏好就返回，零成本。

允许不配就走完——首屏照常提示无模型，用户随时能回设置页。

## 连通测试：跑真的那条路

「填完 Key 到底通不通」不能靠猜。三条不走的路：

- Rust 侧没有 `reqwest`，为一个测试按钮引入 HTTP 客户端不划算；
- webview 里直接 `fetch` provider 会被 CORS 挡；
- 自己拼各家的请求体 = 在 UI 层重新实现一遍 `packages/ai`，而且会和引擎真正发的东西分叉。

所以 `probe.ts` 起一个**一次性引擎会话**：`create_session` → `get_state` 退避探活 →
`set_model` → `prompt("只回复两个字：OK")` → 等 `agent_settled`。这跟 `MarketEnvCard`
是同一条原则——卡片上显示的东西必须是真正执行出来的，不是从路径推断的。引擎在 spawn 时
读 `models.json` / `auth.json`，所以刚保存的配置一定被这个新进程看到。

这套「起会话 → 干一件事 → 拆干净」在 `withEngineSession` 里，上面拉模型列表和这里测连通
共用一份，两处都不该各自记得要删会话文件。

发 prompt 前先 `set_auto_retry: false`：自动重试在真对话里是对的默认，在这里是错的——
一个填错的 Key 会先走完指数退避才肯认错，而用户正盯着一个转圈的按钮。

判失败看两处：`set_model` 直接返回 error（`Model not found` / `No API key`，映射成中文），
或者 assistant 消息的 `stopReason === "error"`——provider 的 401/429 走的是这条，原始报文
交给已有的 `formatApiError` 压成一行，再按状态码补一句「Key 无效」「被限流」之类的人话。
连不上（ECONNREFUSED / ENOTFOUND / fetch failed）单独一支，因为那不是 HTTP 层的事，
提示要指向 Base URL 和代理而不是 Key。60s 兜底超时。

收尾要**删掉测试会话文件**（`get_state` 报的 `sessionFile` 交给 `delete_session`）。不删的
话侧边栏会多出一条「只回复两个字：OK」，这比不做测试还糟。

一个容易踩的坑：`sendCommand` 的 promise 是靠 `resolveResponse` settle 的，而那个调用在
chat-store 的事件监听里，只认它自己的会话。这个一次性会话故意不在其中，所以监听回调里必须
自己调一次 `resolveResponse`，否则每条命令都会挂到超时。

按钮旁写明「会真的调一次模型，产生极少量 token」——花用户的钱得先说。

错误映射拆成纯函数 `explainProbeError` 配 vitest，是这个功能里唯一值得测的部分（其余全是
真进程和真网络）。

## 标记落 `~/.kalo/onboarding.json`

不放 localStorage：清缓存或换 webview 会重弹，而且用户没法手工调。文件长这样：

```json
{ "completed": true, "completedAt": 1756100000000, "version": 1 }
```

删掉文件就能重新走一遍——测试和用户都靠这个。Rust 侧 `onboarding.rs` 照抄 `mcp.rs`
的写法（缺文件返默认值、tmp + rename 原子写）。

「跳过」和「走完」都写 `completed: true`，两条路都不重弹。读失败（后端没起来，比如纯
vite dev）当作已完成——引导弹不出来只是少个功能，误弹是打扰。

`version` 本次只写不读，留给以后加步骤时决定要不要重弹。

已在用的老用户升级会被弹一次。这是选定的行为：标记以文件为准，不去反推「他有配置所以
一定看过引导」——那种猜测在装了 Kalo 但从没打开过的机器上是错的。

## 重看

帮助菜单加「使用引导」。重看时关闭只是关闭，不动标记也不动已有配置。
