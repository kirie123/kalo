# 上下文用量高水位估算

## 问题

上下文圆环展示来自引擎 `get_session_stats.contextUsage`。当前引擎使用“最近一条有效 assistant 消息的 provider usage + 后续消息估算”作为当前上下文长度。

部分 OpenAI-compatible 网关的 `usage.prompt_tokens` 语义不稳定：同一会话内有时返回完整请求上下文，有时只返回本次新增或局部计费 token。真实会话中可出现 `192687 → 604 → 547 → 202293 → 126`。这些响应之间没有压缩，但当前算法会让圆环随最后一条 usage 从高位跌回低位，并可能让自动压缩漏判阈值。

## 目标

- 未发生压缩时，上下文用量不因局部 usage 回报而大幅回落。
- 新的完整 usage 高于旧值时，继续采用更准确的新值。
- 压缩后允许上下文用量下降，不继承压缩前的高水位。
- 圆环展示与自动压缩使用同一口径。

## 方案

### 当前压缩边界内选择 usage 高水位

`estimateContextTokens(messages)` 不再选择最后一条非零 usage，而是：

1. 找到最新 `compactionSummary` 的时间戳。
2. 排除时间戳不晚于该压缩点的 assistant usage；这些是压缩后保留的旧消息，其 usage 仍代表压缩前上下文。
3. 对每条剩余 assistant usage 计算候选值：`calculateContextTokens(usage) + 锚点之后消息的本地估算`。
4. 选择候选值最大的 usage 作为锚点；相同值选择更靠后的消息。
5. 当前压缩边界内没有可靠 usage 时，回退为对全部当前消息进行本地估算。

公式：

```text
currentContext = max(providerUsageAt(i) + estimatedMessagesAfter(i))
```

高水位限定在当前压缩边界内，因此压缩后会重新开始计算。

### 自动压缩统一使用估算值

阈值检查不再优先直接使用当前 assistant 的非零 usage。无论该值是否为零，都从当前 agent 消息调用 `estimateContextTokens()`；只有消息列表尚未包含 usage 锚点时，才回退到当前 assistant 的直接 usage。

这样局部 usage 不会让圆环下降，也不会让阈值判断从高位误降到低位。

## 非目标

- 不在前端保存“最大百分比”；否则 UI 与引擎压缩判断会产生两套口径。
- 不修改 provider 的计费 token 统计。会话累计成本仍按每次原始 usage 汇总。
- 不假设所有 provider usage 都是错误的；完整 usage 仍作为优先于字符估算的锚点。

## 验证

- 连续 usage `4400 → 120 → 4650` 时，估算值不会在中间回落到 120。
- 高水位之后的 user/tool/assistant 消息会计入 trailing tokens。
- 压缩摘要之前的高 usage 不参与压缩后的高水位选择。
- 压缩后首个有效 assistant usage 建立新的锚点。
- coding-agent 与基础 agent harness 的同名估算函数保持一致。
