# 附件从「内联内容」改为「路径引用」

## 问题

加附件（点「+」/ 粘贴 / 拖入）后点发送，`sendPrompt` 会把附件**正文**拼进 prompt：

```ts
message += `\n\n【附件：${a.name}】\n${a.text}${a.truncated ? "\n…（内容已截断）" : ""}`;
```

两个后果：

1. 一份 pdf / xlsx 抽出来可能几万 token，一次性灌进上下文，而且此后每一轮都跟着历史重发。模型本来有
   `read` 工具，可以按需读、按需分页，没必要提前替它读完。
2. 这段正文原样进了用户气泡（`UserBubble` 直接渲染整条 text），于是气泡里躺着一整篇文档。

## 目标

发送时只给模型一个 `<attachments>` 标签：里面是附件**路径**，加一句「这是附件，自己去读」的提示。
用户气泡把这段标签渲染成文件 chip（图标 + 文件名，点击用系统默认程序打开），不显示为文本。

## 标签格式

拼在用户文本之后，用空行隔开：

```
<用户输入的文本>

<attachments>
用户附加了以下文件。这里给的是路径，不是文件内容；需要时请用 read 等工具自行读取。
<file path="D:\work\报表.pdf" />
<file path="C:\Users\fengqi\.kalo\attachments\7f3a-1\notes.md" />
</attachments>
```

- **不做 XML 转义**。Windows 路径本身不允许 `<>:"|?*`，解析用自己的正则而不是 XML parser，
  路径里的 `&` 原样保留即可。
- **不带 `name` 属性**。basename 就是名字，少一处要保持一致的信息。
- 前端唯一真源是 `src/lib/attachments.ts`：`formatAttachmentTag(paths)` 生成，
  `parseAttachmentTag(text)` 剥离并取回路径。chat-store 只生成，UserBubble 只解析。

解析走的是**消息文本本身**，不依赖内存态：会话由引擎回显 / 从 session 文件恢复时，
气泡里的 chip 一样能渲染出来。

## 三个取舍

### 图片保持内联

图片仍走 prompt 的 `images` 字段（`ImageContent`），不进标签。附图的目的就是让模型看见，
改成路径只会多一次 `read` 往返；而且粘贴的截图本来就没有磁盘路径。

顺带补上一个既有缺口：`UserBubble.userText()` 会把 `ImageContent` 过滤掉，所以粘贴图片后
气泡里什么都看不到。现在图片和文件并排渲染成 chip，图片 chip 是缩略图，点击放大。

### pdf / docx / xlsx / pptx 只给原始路径

引擎的 `read` 工具只支持纯文本和图片（`kalo-harness/packages/coding-agent/src/core/tools/read.ts`），
不解析 pdf / office。但 pi 是 coding agent，有 `bash` 和完整的代码执行能力，
自己写几行代码抽文本对它不是障碍——预先替它抽好，反而是把「读多少、怎么读」的决定权拿走了。

所以 Rust 里的抽取代码与依赖（`pdf-extract` / `calamine` / `zip`）一并删掉：
`extract_spreadsheet` / `extract_docx` / `extract_pptx` / `read_zip_entry` / `extract_runs` /
`find_tag` / `read_text_lossy`，以及只服务于它们的 `MAX_ATTACHMENT_CHARS` /
`MAX_ATTACHMENT_BYTES` / `TEXT_EXTS`。（`knowledge.rs` 有自己的同名 `truncate_chars`，不受影响。）

### 粘贴的文件持久落盘到 `~/.kalo/attachments/`

webview 的 `clipboardData.files` 只给名字和字节，没有磁盘路径（浏览器安全模型）。
要给模型一个可读的路径，就必须落盘。

`read_attachment_bytes` 因此改名 `save_attachment_bytes`：写入
`~/.kalo/attachments/<pid-纳秒-自增>/<净化后的文件名>` 并返回该路径，**不再删除**目录
（旧实现是落到 `%TEMP%/kalo-paste` 抽完就删）。目录名唯一，同名文件不会互相覆盖。

代价：`~/.kalo/attachments/` 只增不删。之所以不加 GC，是为了让历史消息里的路径长期有效——
一旦按时间清理，旧会话气泡里的 chip 就成了死链接。

## 后端行为

`AttachmentData` 的 `Text { name, text, truncated }` 变体换成 `File { name, path }`。

`read_attachment(path)`：

| 输入 | 结果 |
| --- | --- |
| 目录 / 不存在 | 报错 `not a file`（不变） |
| 图片扩展名，≤ 10MB | `Image`，读字节转 base64（不变） |
| 图片扩展名，> 10MB | **降级为 `File`**，而不是报「图片过大」 |
| 其他任何扩展名 | `File { name, path }`，不读内容 |

最后一行是行为变化：**不再校验扩展名白名单**。既然不读内容，`TEXT_EXTS` 那种白名单只会把
`.vue`、`.gradle`、无扩展名的 `Makefile` 这些模型本来读得动的文件挡在门外。
文件选择器仍保留「常用附件」过滤器，另加一项「所有文件」。

拖入**目录**仍然报错，没有 `<dir path>` 变体。

## 影响面

- Rust：`AttachmentData::Text` → `File`；`read_attachment_bytes` → `save_attachment_bytes`；
  删三个依赖和一批抽取函数。
- 前端类型：`AttachmentDraft` 的 `{ kind: "text"; text; truncated; sourcePath? }` →
  `{ kind: "file"; name; path }`（`path` 必填，不再需要 `sourcePath`）。
- `chat-store.sendPrompt`：附件正文拼接 → `formatAttachmentTag`。侧栏乐观标题改用用户实际输入的
  文本（否则会把整段标签当标题），空则退回附件名。
- `pushAttachment`：同一路径重复添加直接跳过，避免标签里出现两条同路径。
  不同目录的同名文件仍靠 `uniqueAttachmentName` 的 `(2)` 区分 chip。
- `ImageLightbox` 从 `InputBox` 抽成独立组件，输入框和气泡共用。
