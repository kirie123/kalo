# 高负载下界面响应与输入可见性（进程优先级 / 流式渲染降本 / 输出上限 / 打字即聚焦）

日期：2026-10-01
状态：已落地（桌面端 + Windows 进程优先级窄适配层；引擎协议零变化）

## 0. 现象与诊断

用户报告：让 Kalo 跑模型训练、等待一个很长的 bash 期间，**对话输入框"看着正常，敲字没反应"**，屏幕上没有任何对话框或消失的元素。当时机器 CPU 约 50% 被训练占用、`vmmem`（WSL）占用大量内存。

排查结论（证据链）：

1. **代码里没有"禁用"这条路。** 全项目唯一禁用对话输入框的开关是 `InputBox.tsx` 的 `disabled={chat.hasPendingAsk}`，而 `pendingAsk` 只由 `ask_user` 事件写入；那条路径必然渲染问题卡。用户确认没看到任何卡片 → 不属于"被禁用"，而是"界面没在响应"。
2. **Windows 侧记录到过真实挂起。** 事件日志里 `kalo.exe`（0.6.0）两次 Application Hang（id=1002，`AppHangXProcB1`＝跨进程挂起，即 WebView2 那侧无响应）：2026-09-15 20:41、2026-09-18 19:44。
3. **Kalo 自身有放大的渲染开销（实测）。** 流式输出时每个 delta 都把**整段累计 Markdown 重新解析一遍**（`AssistantMessage` 的流式块走 `MarkdownBlock`，`memo` 只挡得住已结束的块）。用本机真实依赖链（`remark-parse` + `remark-gfm` + `remark-math` + `remark-rehype` + `rehype-katex`）实测：

   | 正文长度 | 单次全量解析 |
   | --- | --- |
   | 20 KB | 37 ms |
   | 40 KB | 65 ms |
   | 80 KB | 141 ms |

   模拟流式（每 120 字符一个 delta、每次重解析整段）：20 KB 累计 2.5 s（均 15 ms）；40 KB 累计 16.2 s（均 49 ms、最差 136 ms）。store 侧 flush 频率约 20 次/秒 → 长回答流式期间主线程基本被吃满，输入事件送达但界面来不及回显。

   已排除的怀疑：256 KB 文本塞进 `<pre white-space:pre-wrap>` 只花 9–17 ms 布局（不是主因）；`job-status` / `job-done` 事件桌面端并未订阅。

4. **机器特性放大：** i9-13900KF（P+E 混合核）。Windows 会把非前台窗口的应用放进「效率模式」（EcoQoS：绑 E 核 + 限频）；当训练把线程铺满时，被压在后排的 UI 进程最容易先饿死；叠加内存压力时，空闲的渲染进程工作集被裁剪，切回来敲字要等换页——表现就是"画面还是那一帧、按键没人处理"。

本轮目标：**让"界面被机器负载饿死"不再直接变成"打不了字"，并把 Kalo 自身的放大器关掉。**

## 1. 方案总览

| 编号 | 内容 | 解决什么 |
| --- | --- | --- |
| A | UI 进程优先级 + 关闭 EcoQoS（Windows 窄适配层） | 机器被占满时 UI 仍拿到调度 |
| B | 流式文本块渲染降本（节流 + 超长降级纯文本） | 去掉每 delta 整段重解析 |
| C | 工具输出渲染上限 + 长会话布局隔离 | 长输出/长会话不再持续放大渲染与内存压力 |
| D | 输入可见性与"打字即聚焦" | "不能输入"永远不静默，按键不再丢到空处 |

引擎协议（NDJSON 命令、事件、工具面）**零变化**；因此桌面端与 sidecar 的契约不受影响。

## 2. A：UI 进程优先级与 EcoQoS

新窄适配层 `kalo-desktop/src-tauri/src/priority.rs`（Windows 专属；OS 差异只在这里，业务侧不感知）：

- **自身进程**：`SetPriorityClass(GetCurrentProcess(), ABOVE_NORMAL_PRIORITY_CLASS)`。
- **WebView2 子进程**：用 Toolhelp32 快照沿父进程链找出**本进程的后代**中 `msedgewebview2.exe` 的进程（browser / renderer / gpu-process / utility），逐个 `SetPriorityClass(..., ABOVE_NORMAL_PRIORITY_CLASS)`。
- **关闭 EcoQoS**：`SetProcessInformation(ProcessPowerThrottling, …)`，把 `PROCESS_POWER_THROTTLING_EXECUTION_SPEED` 置 0（即不限制执行速度），使其不被"效率模式"绑在 E 核并限频。
- **重扫线程**：WebView2 的 renderer/gpu 进程是懒创建、崩溃后会重建，所以起一个后台线程每 5 s 重扫一次；只对新增 pid 生效，成本可忽略（不做无条件重复调用）。
- **不动谁**：pi sidecar 与 gateway **不抬优先级**。它们和用户的训练任务是"同侪"（训练命令本身就是从引擎跑出去的），抬它们等于从用户任务里抢 CPU，违背这个改动的初衷。这条边界写进代码注释，防止后来者"顺手统一抬高"。

平台等价：macOS 侧 `#[cfg(not(windows))]` 为空实现（`taskpolicy`/`setpriority` 的等价做法需要单独评估，不在本轮）。两平台都保持"UI 进程不被自身逻辑拖慢"的业务语义，差异只落在适配层内。

失败处理：全部 best-effort。任何一步失败只 `eprintln!` 一次（不 panic、不打断启动、不弹用户可见错误）——这些是性能优化，不是功能前置条件。

## 3. B：流式文本块降本

现状问题：`AssistantMessage` 对 text 块一律走 `MarkdownBlock`；流式中最后一个块每次文本变化都触发一次完整 remark/rehype 解析（成本随长度线性增长，而 delta 持续到来 → 总开销随轮次平方增长）。

方案（纯逻辑进 `lib/`，组件只接线）：

新 `src/lib/stream-render.ts`：

```ts
/** 流式期间两次完整 Markdown 解析之间的最小间隔。 */
export const STREAM_PARSE_INTERVAL_MS = 300;
/** 超过这个长度，流式期间直接按纯文本渲染，结束时再做完整 Markdown。 */
export const STREAM_MARKDOWN_MAX_CHARS = 24_000;

/** 这一帧该按纯文本渲染，还是交给 MarkdownBlock？ */
export function shouldStreamAsPlainText(text: string, streaming: boolean): boolean;
/** 距离上次提交解析是否已经够久（节流判定，纯函数，便于单测）。 */
export function shouldCommitStreamParse(lastCommitMs: number, nowMs: number): boolean;
```

新组件 `src/components/StreamingText.tsx`：

- 流式中的块：每 `STREAM_PARSE_INTERVAL_MS` 才把「已累计文本」提交给 `MarkdownBlock`；超过 `STREAM_MARKDOWN_MAX_CHARS` 期间改渲染纯文本（`whitespace-pre-wrap`，保留 `streaming-cursor`）。
- `streaming` 变 false：立即用完整文本走一次 Markdown（保证最终排版与今天完全一致）。
- 只作用于**正在流式的最后一个** text 块；历史块不动（`MarkdownBlock` 的 memo 已经挡住）。

为什么不"流式一律纯文本"：短回答是绝大多数情况，一律纯文本会让代码块、列表、表格在流式期间变成半成品观感，体验退化明显。节流 + 超长降级把最坏情况压进阈值，同时保住常见情况。

## 4. C：工具输出上限与长会话布局隔离

**输出上限。** 现在 `ToolCallGroup` 把 `resultText(result) || resultText(partialResult)` 全量塞进 `<pre>`；前台 bash 结果上限 50 KB，`job_output` 单次最多 256 KB。新纯逻辑 `src/lib/tool-output.ts`：

```ts
export interface CappedOutput { text: string; truncated: boolean; hiddenChars: number; hiddenLines: number; }
/** 头尾保留（日志尾部信息量最大），中间省略并给出计数。 */
export function capToolOutput(text: string, opts?: { maxChars?: number; maxLines?: number }): CappedOutput;
```

默认 `maxChars = 20_000`、`maxLines = 400`。组件侧：被截断时显示一行「已省略 N 字符 / 共 M 行」+「显示全部」（卡片本地 state，展开只影响这一条）。

**长会话布局隔离。** 给消息行加语义类（`index.css`）：

```css
.msg-contain { content-visibility: auto; contain-intrinsic-size: auto 120px; }
```

让视口外的消息跳过布局与绘制，**不改 DOM、不丢数据、不动折叠与滚动锚定**。

边界：本轮**不做**虚拟滚动、不做 live timeline 截断——那会牵动工作段折叠、滚动锚定与历史分页三处逻辑，风险与收益不成比例。这一轮只做"降本"，不做"重构"。

## 5. D：输入可见性与打字即聚焦

**D1 禁用态可见。** `hasPendingAsk` 时输入卡片整体降低不透明度 + 边框转为强调色，并在卡片内加一行说明：「模型在等你回答问题：回答上方问题或点「我直接说」后恢复输入」。今天的禁用态与正常态**没有任何视觉差异**（`className` 里没有 `disabled:`，placeholder 只在空输入框显示），这是"看着正常却打不了字"最容易骗人的地方。

**D2 空态也渲染问题卡。** `AskUserPanel` 今天只在 `ChatView` 渲染；空会话走 `EmptyState`（只渲染 `InputBox`）。于是"时间线为空 + 有待答提问"时会出现：输入框被禁用、却没有问题卡、也没有任何提示。`EmptyState` 里在 `<InputBox />` 之前挂上 `<AskUserPanel />`，接管永远可见。

**D3 打字即聚焦。** `InputBox` 挂一个 document 级 `keydown` 监听，满足**全部**条件才接管按键：

- 可打印单字符（`e.key.length === 1`），无 `Ctrl`/`Alt`/`Meta`（允许 `Shift`：大写与中文输入法都要用）；
- `document.activeElement` 是 `body` / `documentElement`（**没有任何元素被聚焦**时）；
- 当前没有待答提问（`hasPendingAsk` 为 false）、没有扩展模态弹窗（`extensionQueue` 为空）；
- 没有整屏覆盖层：`OnboardingOverlay` 与 `ExtensionModal` 加 `data-kalo-modal` 标记，存在则不接管。

命中时：`preventDefault()` → 聚焦输入框 → 把该字符插入（走与 `onChange` 相同的 state 路径，光标落在末尾）。

为什么限定"没有任何元素被聚焦"：这是最小惊讶边界。点在按钮/下拉上、输入法组字中、面板里正在输入时都不接管；只在"用户明明在敲字、但按键掉进了空处"时兜住。

**D4** 与 `ask_user` 的既有语义不冲突：提问接管期间（`hasPendingAsk`）D3 不生效，答案输入框的 `autoFocus` 行为保持原样。

## 6. 明确不做

- 不把"提问期间禁用输入"改成"输入进队列"——那会改动 `doc/2026-09-07-ask-user-向用户提问工具.md` 的交互语义（"我直接说"是唯一出口），需要单独评估。
- 不给 pi sidecar / gateway 提优先级（见 §2 边界）。
- 不做虚拟滚动、不截断 live timeline（见 §4 边界）。
- 不改引擎侧任何代码，不新增引擎协议；`pi-bridge` 契约不变。
- macOS 不做优先级等价物（本轮只保证空实现不报错）。

## 7. 验证

纯逻辑单测（vitest，`src/**/*.test.ts`）：

- `stream-render.test.ts`：纯文本判定（长度阈值 × 流式状态）、节流判定（间隔边界）。
- `tool-output.test.ts`：未超限原样返回、超限保留头尾与计数、空串、恰好等于上限。

人工验证（组件行为，按 `kalo-desktop/AGENTS.md` 的测试边界不做组件测试）：

1. 跑一个占满 CPU 的任务，同时看输入框打字是否跟手（A+B 的效果）；
2. 让模型写一段长回答（> 24 KB），流式期间界面可交互，结束后排版与今天一致；
3. `job_output`/大 bash 输出卡片：显示头尾 + 「已省略 N 字符」，点「显示全部」能看到全文；
4. 空会话里触发一次提问：问题卡可见，不再"静默禁用"；
5. 点一下消息区（不点输入框）后直接敲字：字符落进输入框；
6. 打开引导层/扩展弹窗时敲字：不被抢焦点。

机器检查：`node scripts/check-changed.mjs`（含 tsc / vitest / cargo check / 行数 ratchet / 桥接契约）。
