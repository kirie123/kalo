# macOS `.app` / `.dmg` 打包与运行时资源定位

## 背景

`doc/2026-09-12-macos-平台支持.md` 把 macOS 做到了 `tauri dev` 可跑，并显式留下缺口：

> **macOS `.app` 打包未验证**。app bundle 把资源放在 `Contents/Resources/` 而不是
> 可执行文件旁，而 `sidecar::resolve()` 的第 2 步找的是「exe 旁 `binaries/`」
> （`Contents/MacOS/binaries`，不存在）。

本文补上这个缺口：让 `.app` 里的 sidecar 与内置 skill 能被正确定位，并产出 `.dmg`。

### 为什么这个缺口比「找不到」更危险

查找链的最后一步是 `CARGO_MANIFEST_DIR`——**编译期写死的绝对路径**。于是在
构建这台机器上，`.app` 里的 `sidecar::resolve()` 会绕过整个 bundle，解析回
`<repo>/kalo-desktop/src-tauri/binaries/`，并且**跑起来一切正常**。

换一台机器，那个路径不存在，才退化成「引擎未响应」。

也就是说：打包机是唯一一台无法复现该缺陷的机器。这条回退路径不仅是分发期的
bug，还让打包后的本机验证**全部失去意义**——无论 bundle 里资源是否真的到位，
本机验证都会通过。所以「release 构建里禁用 `CARGO_MANIFEST_DIR` 回退」既是修复，
也是让验证可信的前提。

## 契约变更

### 运行时资源根：新增 `resources.rs`

新增 `src-tauri/src/resources.rs`，作为「打包后资源根在哪」的**单一事实源**：

```rust
pub fn init(app: &AppHandle)      // setup() 里调用一次，存入 OnceLock
pub fn dir() -> Option<&'static Path>
```

值取自 Tauri 的 `app.path().resource_dir()`，不自己推算 `../Resources`——
bundle 布局是 Tauri 的契约，自己算就是把同一个假设抄第二份，日后必然漂移
（这正是 sidecar 命名契约当初要解决的那类问题）。各平台 `resource_dir()` 落点：

| 平台 | resource_dir |
| --- | --- |
| macOS（.app） | `Kalo.app/Contents/Resources/` |
| Windows（nsis） | 与 exe 同目录 |

Windows 侧因此**行为不变**：resource_dir 就是 exe 所在目录，等价于原来的第 2 步。

`init()` 必须是 `setup()` 的第一行：`gateway::autostart()` 紧随其后，而它会解析
gateway sidecar 路径。

### 查找顺序

`sidecar::resolve()`：

1. `KALO_PI_PATH` / `KALO_GATEWAY_PATH` 环境变量
2. `<resource_dir>/binaries/<name>` —— 安装后布局（新增）
3. `<exe 目录>/binaries/<name>` —— `init()` 未跑时的兜底
4. `<CARGO_MANIFEST_DIR>/binaries/<name>` —— **仅 debug 构建**

`internal_skills::source_dir()` 同构，顺序为：override → （debug）repo →
`<resource_dir>/internal-skills` → exe 旁 → 无。末尾原本还有一个无条件的 repo
回退，出于上文同样的理由收进 debug。

两处的纯逻辑都抽成接收 `resource_dir: Option<&Path>` 的内部函数
（`resolve_in` / `source_dir_in`），全局状态只在最外层薄封装里读，
使查找顺序可以用临时目录做真单测。

### bundle targets

`tauri.macos.conf.json` 的 `bundle.targets` 由 `["app"]` 改为 `["app", "dmg"]`。
`app` 只产出目录形态的 `Kalo.app`，不是可分发的安装包。

## 签名与公证（本次不做，记录路径）

产物只带链接器在 arm64 上自动加的 ad-hoc 签名（`codesign -dv` 显示
`adhoc, linker-signed`、`TeamIdentifier=not set`、`Sealed Resources=none`）。
它是二进制能在 Apple Silicon 上执行的最低要求，**不是分发意义上的签名**：
`spctl -a` 直接拒绝。

本机可直接运行；分发给他人时 Gatekeeper 会以
「"Kalo" is damaged and can't be opened」拦截——注意这句文案与实际原因无关，
它只表示缺少有效签名或带着 quarantine 属性。

- 自用/内测：接收方执行 `xattr -dr com.apple.quarantine /Applications/Kalo.app`
- 正式分发：Developer ID 证书 + `notarytool` 公证 + `stapler` 装订。
  两个 sidecar 是独立可执行文件，必须一并签名；bun 编译产物需要 hardened runtime
  配合允许 JIT 的 entitlement（`com.apple.security.cs.allow-jit`）。

## 验证

```bash
bun run build
```

产物：`kalo-desktop/src-tauri/target/release/bundle/{macos/Kalo.app,dmg/*.dmg}`

打包后必须验证的三点（前两点在本次修复前会被 `CARGO_MANIFEST_DIR` 回退掩盖）：

```bash
APP=kalo-desktop/src-tauri/target/release/bundle/macos/Kalo.app
ls $APP/Contents/Resources/binaries/pi-*-apple-darwin          # 引擎在 Resources 下
ls -d $APP/Contents/Resources/internal-skills                  # 内置 skill 在 Resources 下
```

第三点是资源真的从 bundle 里取的：release 构建没有 `CARGO_MANIFEST_DIR` 候选，
`Contents/MacOS/binaries/` 也不存在，所以只要能定位成功，来源只可能是 resource_dir。
用一个全新 HOME 启动，可以同时验证两条链路：

```bash
TMPHOME=$(mktemp -d); HOME="$TMPHOME" $APP/Contents/MacOS/kalo
# 期望 stdout：[internal-skills] installed 29 / ...   ← internal-skills 链路
# 期望 ps：    .../Contents/Resources/binaries/kalo-gateway-...  ← sidecar 链路
```

首次实测（0.6.0、aarch64）：29 个 skill 装入临时 HOME，gateway 由
`Contents/Resources/binaries/` 拉起后稳定驻留，bundle 内的
`pi-aarch64-apple-darwin --version` 返回 `0.84.1`。

端到端验收点同 `2026-09-12-macos-平台支持.md`：新建对话能流式回复；重命名会话
不弹「引擎未响应」；文件面板可展开预览；控制台无 `[kalo] gateway autostart skipped`。

## 排查提示：gateway 反复 `exited (code Some(0))`

gateway 的 jobs 端口是固定的，第二个实例抢不到端口便退出，父进程按崩溃重启，
日志表现为无限循环的 `[kalo] gateway exited (code Some(0)), restarting in 1s
(attempt 1)`（注意 attempt 始终是 1）。先确认没有第二个 Kalo 在跑：

```bash
ps -ax -o pid,ppid,command | grep "Kalo.app" | grep -v grep
```

`.dmg` 里有指向 `/Applications` 的符号链接，装过一次之后很容易出现
「构建目录里一个 + `/Applications` 里一个」同时运行。
