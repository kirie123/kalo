# 会话自动命名

日期：2026-08-21
状态：已实现

## 现状

标题链路早已接通，但**没有任何东西真正产生标题**。

扫本机 `~/.kalo/agent/sessions` 全部 61 个会话文件：`session_info` 条目数 **0**，每个会话 `name` 都是 `null`。所有标题都走「首条用户消息」兜底，侧栏长成这样：

```
name=null | title=我工作中需要开始接触LLM后训练，现在有这个slime/ 框架，你看一下分析一下，然后讲述给我，关于他的架构以及核心技术…
name=null | title=当前项目，会话标题功能貌似还没有，你出一个方案
```

上一期的手工重命名（`doc/2026-08-20-会话标题重命名.md`）实现完整正确，但它把「LLM 自动命名」明确划为非目标（该文档第 43 行）；harness 里也不存在任何自动命名逻辑。结果：除非用户逐个手工改名，标题永远是原始提示词。

**接口盘点：harness 侧能力齐备，desktop 侧已全部对接，缺的只是调用方。**

| 接口 | harness 位置 | desktop 对接 |
| --- | --- | --- |
| RPC `set_session_name {name}` | `src/modes/rpc/rpc-mode.ts` | ✅ `chat-store.ts` `renameSession` |
| `get_state` → `sessionName` | `docs/rpc.md` | ✅ `chat-store.ts` |
| 事件 `session_info_changed` | `src/core/agent-session.ts` `setSessionName` | ✅ `chat-store.ts` |
| 扩展 `pi.setSessionName()` / `getSessionName()` | `src/core/extensions/types.ts` | ❌ 无人调用 ← **本期补这个** |

## 目标与非目标

目标：首轮对话结束后引擎自动生成短标题写进 `session_info`。因为 `session_info_changed` 全链路已通，侧栏行、顶栏标题、磁盘扫描三者**零改动**自动一致——顶栏的 `chat.sessionName || cwdBasename(chat.cwd)`（`App.tsx`）终于不再恒为目录名。

非目标：
- 不改 desktop 任何一行（顶栏跟随自动命名）
- 不改 gateway、不改 RPC 协议、不改 `types.ts`（类型早已齐备）
- 不给历史会话批量补标题（要起引擎，代价过高）
- 不动手工重命名链路

## 方案：hidden 内置扩展 `session-namer`

### 为什么走引擎内置扩展

- `session_info_changed` → 侧栏/顶栏/磁盘的链路**已经建好**，扩展只要调 `pi.setSessionName()`，desktop 一行不用改。
- desktop 侧没有独立的 LLM 通道；RPC 只有 `prompt`（会污染会话历史）。引擎内可以直接复用已解析好的 model + auth。
- 走 TUI 的用户同样受益，不是 desktop 专属补丁。

### 触发条件（监听 `agent_settled`）

```
本会话已生成过 / 正在生成                → 跳过（模块级 WeakSet 按 sessionManager 去重）
无首条用户消息                          → 跳过
无可用 model（ctx.model 为 undefined）  → 跳过
已命名（getSessionName() 非空）         → 跳过（手工改名 / 恢复的会话永远优先）
用户消息数 !== 1                        → 跳过（只在首轮之后命名一次）
```

### 取素材

从 `ctx.sessionManager.buildContextEntries()` 取首条 user 消息与首条 assistant 回复，各截断 600 字符。回复很关键：两个字的提示词（「继续」「看看这个」）本身说明不了什么，但助手拿它做了什么通常能精确命名会话。

### 生成

不用 `createAgentSession`（subagent 那套是给多轮工具调用准备的，这里一次 completion 就够）。走 `ctx.modelRegistry.complete(...)`（内部 `ModelRuntime.complete` 已处理 auth/baseUrl/headers 解析），参数照 `createSummarizationOptions`（`compaction/compaction.ts`）：

```
maxTokens: 2048          见下「预算陷阱」，绝不能按标题长度设
reasoning: 不设置        标题不需要思考预算
cacheRetention: "none"   一次性请求，不写用不上的缓存
signal: 45s 超时
```

system prompt 约束：只输出标题本身，10-16 字，用对话所用语言，不要引号/句号/前缀。

#### 预算陷阱（真实踩过，务必别改回去）

第一版把 `maxTokens` 设成 64，「标题就几个 token，够了」。结果**一个会话都没命名成功**，而且完全静默。

用探针扩展（`-e` 加载，打 `onPayload` 日志）在真实引擎上抓到的现场：

```
model = deepseek-v4-flash  reasoning = false  thinkingLevelMap = (空)
maxTokens=64    PAYLOAD {"max_tokens":64}    ← 没有 thinking:{type:"disabled"}
                stop=length  textLen=0  thinkLen=64      ← 全被思考吃光
maxTokens=2000  stop=stop    textLen=14  thinkLen=1237
```

两层原因叠加：

1. **推理和正文共用 `max_tokens`。** 模型先吐 `reasoning_content` 再吐正文，预算不够就 `stop=length`、正文长度为 0。
2. **`thinking: {type:"disabled"}` 根本没发出去。** `openai-completions.ts` 里该分支的前置条件是 `model.reasoning && thinkingFormat === "deepseek"`；而用户 `~/.kalo/agent/models.json` 里这条是手写覆盖项，只有 `{id, contextWindow}`，`reasoning` 为 `false`，于是整个 thinking 分支跳过，provider 按自己的默认开着推理。会话里的 `thinking_level_change: off` 管的是主对话，管不到这个旁路请求。

思考量还不稳定（同一模型 24 ～ 1237 token 乱跳），所以「调小一点试试」是错的方向：**约束标题长度的是 `MAX_TITLE_CHARS` 的截断，不是 token 预算**。预算只负责别让正文被挤没。

更隐蔽的是失败形态：正文为空 → `sanitizeTitle("")` → `""` → 命中「净化后为空则放弃」的保护分支 → 什么都不写、不报错。保护逻辑本身是对的（空名会*清除*标题），但它把配置错误伪装成了「功能没生效」。

注意 `stopReason === "length"` **不能**直接丢弃：截断的标题仍然可用，交给净化截断即可。只在 `error` / `aborted` 时放弃。

### 净化 + 落库

LLM 输出不可信：可能带引号、带「标题：」前缀、多行、整段话。`sanitizeTitle` 依次做：多行时取最后一行 → 剥 `标题：`/`Title:` 前缀 → 剥首尾引号书名号 → 去尾部标点 → 压空白 → 截断 24 字。

**净化后为空则整个放弃，不做任何写入**——空名会 *清除* 标题（引擎 `getSessionName` 语义），绝不能因为命名失败而覆盖掉兜底标题。

### 失败与边界

- `agent_settled` 的 handler 是 `await` 的（`agent-session.ts` `_emitAgentSettled`），**必须 fire-and-forget**：`void (async () => …)()`。否则一次慢请求会拖住整个 run 的 settle，进而拖住 RPC 的 `checkShutdownRequested` 和 desktop 的 usage footer。
- 生成期间用户手工改名 → 写回前**二次检查** `getSessionName()`，非空就丢弃生成结果。
- `pi.setSessionName()` 走 `runtime.assertActive()`：会话若已被替换（newSession/fork/switch）会抛错 —— 整块 try/catch 吞掉。
- 中止的首轮（用户按停）也会触发 `agent_settled`，素材可能只有半句。可接受：无论如何都比原始提示词强，且有 24 字截断兜底。

## 顺带修掉扫描侧两个 bug（`kalo-desktop/src-tauri/src/sessions_store.rs`）

核对乐观行与磁盘行时发现的真实不一致：

**(a) 落盘瞬间标题跳变。** 乐观行 `promptTitle`（`chat-store.ts`）取**首行**；磁盘扫描 `parse_session_file` 把**整条消息压成一行**。同一会话在第一条助手消息落盘时，侧栏标题会从「首行」突变成「整段」。→ 新增 `fallback_title`，Rust 侧也取首个非空行。

**(b) 附件标签泄漏进标题。** `formatAttachmentTag`（`attachments.ts`）生成的 `<attachments>` 块，chat-store 侧剥离了，磁盘扫描没有。纯附件消息的磁盘标题会变成 `<attachments> 用户附加了以下文件。这里给的是路径…`。→ 新增 `strip_attachments`，剥掉**结尾处**闭合完整的 `<attachments>…</attachments>` 块（用户自己打出的字面 `<attachments>` 不受影响），剥完为空回退 "Untitled session"。

注意：`sessions_store.rs` 的「取最后一条 session_info / 空名回退 / 全文件扫描」语义上一期已经改对了，与引擎 `getSessionName()` 一致，**未动**。
