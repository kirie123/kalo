# kalo-desktop 距离生产级的差距：诊断与分期

日期：2026-08-19
状态：诊断完成，待排期
范围：`kalo-desktop/`（含 `gateway/`、`src-tauri/`），涉及引擎行为处标注 `kalo-harness/`

## 结论先说

代码质量本身不是瓶颈 —— 进程管理、错误驯化、崩溃恢复这几处的水平在生产线以上（见文末「已经达标的部分」）。真正的差距集中在三类：

1. **一处误导性的安全提示**：UI 声称了一个不存在的权限边界。
2. **不可运维**：日志在 release 里凭空消失、没有更新通道、没有 ErrorBoundary。三条叠起来的效果是「用户报问题查不到，查到了也推不出去」。
3. **护栏是点状的**：没有 CI；测试恰好绕开了最大最危险的两个文件（`chat-store.ts` 1871 行、`gateway.rs` 882 行）。

下面按「会不会伤到用户」排序，不按工作量排。每条都在代码里核过，给出文件与行号。

---

## P0 — 会真的出事

### P0-1 「权限模式」下拉框是假的

**现象**：[`InputBox.tsx:336-344`](../kalo-desktop/src/components/InputBox.tsx) 的 `<select>` 标着 `title="权限模式"`，选项写「默认权限 / 全部放行」，绑的是 `chat.steeringMode`。

**实情**：`steeringMode` 在引擎里是 `PendingMessageQueue` 的 drain 策略（`kalo-harness/packages/agent/src/agent.ts:125-154`）：

```ts
drain(): AgentMessage[] {
  if (this.mode === "all") { /* 排队的引导消息一次全给 */ }
  /* 否则一次只给第一条 */
}
```

它控制的是**用户插入的引导消息如何投递给模型**，和工具权限毫无关系。

进一步核了 rpc 模式：`packages/coding-agent/src/modes/rpc/` 下只有 `extension_ui_request / method: "confirm"` 这种给扩展自己弹框用的原语，**没有任何 bash / edit 的准入判断**。也就是说 Kalo 当前对用户 cwd 有无限制的 shell 执行与文件写入权。

**为什么是 P0**：这不是「缺一个功能」，是**声称了一个不存在的安全边界**。用户看到「默认权限」会以为自己开着保护，从而把 Kalo 指向比实际愿意承担风险更敏感的目录。缺失的功能只是能力上限低，虚假的功能会诱导错误决策 —— 后者严重得多。

**修法分两步，不要合并**：

- **立刻（半小时）**：把标签改对。它真正的语义是「引导消息投递：逐条 / 全部」。文案与 `title` 一起改，别留「权限」二字。
- **单独排期**：要不要做真的工具审批闸门。这需要引擎侧配合（rpc 增加一个 tool-approval 往返），是一个独立特性，不该塞在改标签这个 commit 里。

### P0-2 API Key 非原子写，掉电即全丢

**现象**：[`pi_config.rs:27-32`](../kalo-desktop/src-tauri/src/pi_config.rs) 的 `write_json_file` 直接 `fs::write` 覆盖 `auth.json` / `models.json`：

```rust
let text = serde_json::to_string_pretty(value)...;
fs::write(path, text).map_err(...)
```

写入过程中进程死掉 → 文件变成半个 JSON → 下次启动 `read_json_file` parse 失败 → 所有 provider Key 丢失，且**没有任何备份**。

**对照**：全仓 12 处 `fs::write`，只有 [`mcp.rs:56`](../kalo-desktop/src-tauri/src/mcp.rs) 用了 `.tmp` + rename。反讽在于知识笔记有 `.trash/` 兜底（还是「备份失败即阻塞写入」的强保证，见 `doc/2026-08-19-knowledge-notes-panel.md`），偏偏最不能丢的 `auth.json` 裸奔。

**修法**：把 mcp.rs 里那套 tmp + rename 抽成公用 helper（`files.rs` 或新的 `atomic.rs`），`pi_config.rs` / `memory.rs` / `knowledge.rs` / `sessions_store.rs` 全部改走它。几十行。

### P0-3 密钥明文，且 Rust 侧一处都没收权限

`auth.json`、`feishu.json` 明文存 API Key 与 app secret。

grep `set_permissions|0o600|PermissionsExt`：全仓**唯一**一处是 [`credentials.ts:61`](../kalo-desktop/gateway/src/credentials.ts) 的 `{ mode: 0o600 }`。Rust 侧零处。

**注意分清两件事**：

- Windows 上 `0o600` 本身没有意义，真正的答案是 DPAPI / Credential Manager —— 这是一个有实现成本的独立任务。
- 但 macOS / Linux 分支应该立刻跟 gateway 保持一致（P0-2 抽 helper 时顺手加 `#[cfg(unix)]` 的 mode 设置即可）。

## P1 — 发得出去，但收不回来

这三条必须一起看：单独修任何一条，收益都不完整。

### P1-4 没有更新通道

`src-tauri/Cargo.toml` 无 `tauri-plugin-updater`，`tauri.conf.json` 无 `updater` 段。0.1.0 装到用户机器上之后，任何修复都要用户自己重新下载安装包。

对一个要拉子进程、连外部 API、还在快速迭代的桌面端，效果等于「每个 bug 都是永久 bug」。

依赖签名与发布流程，适合作为一个独立里程碑，排在 P1-5 / P1-6 之后。

### P1-5 可诊断性是负的

- 代码里 30 处 `eprintln!`。
- release 构建是 `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`（[`main.rs:6`](../kalo-desktop/src-tauri/src/main.rs)）→ 没有控制台 → **这 30 处日志全部凭空消失**。
- 没有 `tauri-plugin-log`、没有日志文件、没有崩溃上报。

用户说「打开就闪退」，手上是零信息。这条和 P1-4 是一对：既不能收集问题，也不能推送修复。

**修法**：接 `tauri-plugin-log`，落盘到 `~/.kalo/logs/`，带 rotation；`eprintln!` 全量替换为 `log::warn!` / `error!`；设置页「关于」加一个「打开日志目录」按钮。

### P1-6 前端零个 ErrorBoundary

grep `ErrorBoundary|componentDidCatch|window.onerror|unhandledrejection`：全仓 **0 命中**。

某条历史会话的 payload 形状意外一点，`MessageList` 渲染期抛异常 → 整个 app 白屏，用户退不回去，而且（见 P1-5）不留任何痕迹。

**修法**：`main.tsx` 包一层 ErrorBoundary，fallback 给「出错了 + 复制错误详情 + 回到首页」；再挂 `window.onerror` / `unhandledrejection` 转发到 P1-5 的日志。

### P1-7 没有 CI

没有 `.github/`。`cargo test` / `tsc` / `vitest` 全靠人记得跑。

**已经有证据**：PR #1（非 Windows 上 `@mariozechner/clipboard` 绑定缺失导致构建断裂）是靠外部贡献者踩到才暴露的。一个跑 `bun run setup` 的 macOS job 能提前抓到。

**修法**：Windows 跑全量（`cargo test` + `cargo clippy` + `tsc` + `vitest`），macOS / Linux 只跑构建。半天。

### P1-8 安装包未签名

`targets: ["nsis"]`，无签名配置。Windows SmartScreen 会拦下载，用户看到「未知发布者」。

个人项目可以接受；一旦开始给别人用，这是第一道流失点。也是 P1-4 的前置。

## P2 — 覆盖面与护栏

### P2-9 实际只支持 Windows x64

sidecar 名是硬编码常量，不是从 target triple 推导：

- [`session.rs:141`](../kalo-desktop/src-tauri/src/session.rs) — `const SIDECAR: &str = "pi-x86_64-pc-windows-msvc.exe";`
- [`gateway.rs:39`](../kalo-desktop/src-tauri/src/gateway.rs) — `const SIDECAR: &str = "kalo-gateway-x86_64-pc-windows-msvc.exe";`
- `tauri.conf.json` 的 `bundle.resources` 同样硬编码这两个名字
- `scripts/ensure-engine.mjs` 里 `PI_EXE` / `GATEWAY_EXE` 也是

PR #1 让 macOS 上**能构建**，但产物名字仍然是 Windows 的。README 只写 NSIS，这点是诚实的；但「属于你自己的桌面 Agent」只覆盖 Windows，会砍掉很大一块想 fork 的人。

**修法**：把 triple 通过 `build.rs` 的 `env!("TARGET")` 传进来拼名字，`ensure-engine.mjs` 按 `process.platform` / `arch` 推导，`tauri.conf.json` 按平台拆 `resources`。中等工作量，且需要一台 mac 验证。

### P2-10 测试恰好绕开了最危险的地方

| 文件 | 行数 | `#[test]` / test 文件 |
| --- | --- | --- |
| `src/lib/chat-store.ts` | 1871 | **0** ← 核心状态机 |
| `src-tauri/src/gateway.rs` | 882 | **0** |
| `src-tauri/src/knowledge.rs` | 757 | 10 |
| `src-tauri/src/files.rs` | 734 | **0** ← 含 PDF / Excel / Word 解析 |
| `src-tauri/src/session.rs` | 427 | 7 |
| `src-tauri/src/internal_skills.rs` | 359 | 5 |
| `src-tauri/src/memory.rs` | 327 | **0** |
| `src-tauri/src/sessions_store.rs` | 237 | **0** |
| `src-tauri/src/session_paging.rs` | 135 | **0** |

前端只有 5 个测试文件（`session-rows` / `text-diff` / era 的 `gate` `fold` / gateway 的 `channel` `scheduler`）。

值得注意的是 `features/era/` 有 `gate.test.ts` + `fold.test.ts`，是全仓最规范的一块 —— **那个标准应该是基线，不是例外**。

**优先补**：`chat-store.ts` 的事件归约（这是 bug 密度最高的地方）、`files.rs` 的三种文档解析（拿畸形样本喂）、`session_paging.rs` 的分页边界。

### P2-11 无单实例保护

没有 `tauri-plugin-single-instance`。开两个 Kalo 窗口：

- gateway 那边有 `feishu.lock` 挡住第二个实例，但**第二个窗口的网关功能会静默不可用**（用户看不出为什么）。
- 同时两边都在写 `~/.kalo/knowledge/`、`memory/`、`agent/schedules.json`，没有任何协调。

**修法**：接 `tauri-plugin-single-instance`，第二次启动聚焦已有窗口。顺带修掉 gateway 静默失效。

### P2-12 CSP 关着

`tauri.conf.json` 里 `"csp": null`。渲染的内容是模型输出的 markdown 加远端图片。

react-markdown 默认不放行 raw HTML，所以**当前不构成漏洞**；但把 CSP 整个关掉是白送的攻击面。加一条 policy 是纯配置活。

## 已经达标的部分

这些不需要动，且应该当成其余部分的参照标准：

- [`proc.rs`](../kalo-desktop/src-tauri/src/proc.rs) 的 `wait_released` / `kill_tree`：注释交代了「不能跨 `wait` 持锁，否则 killer 永远等不到那把锁」和「Windows 上必须杀进程树，否则孙进程（工具调用起的 shell、python）存活」。这是真踩过才写得出来的。
- 25 处 `unwrap` / `expect` 基本全在 `#[cfg(test)]` 内，业务路径几乎没有 panic 点。比例好于多数 Tauri 项目。
- `chat-store` 有引擎崩溃恢复（从磁盘 session 文件重建），不是假装没事发生。
- [`error-format.ts`](../kalo-desktop/src/lib/error-format.ts) 专门驯化 provider 的错误 JSON：一行摘要 + 可展开原文。
- Tauri command 上标注了「为什么 `async` / 为什么故意不 `async`」（`send_command` 保持同步以保留前端发令顺序）。这种把取舍写进注释的习惯很少见。
- `features/era/` 的目录隔离与测试覆盖，是本仓的正面样板。

## 分期

| 阶段 | 内容 | 量级 | 产出 |
| --- | --- | --- | --- |
| **S0** | P0-1 改标签（不含真权限闸门） | 0.5h | 不再误导用户 |
| **S1** | P0-2 原子写 helper + P0-3 unix mode + P1-5 日志 + P1-6 ErrorBoundary | 1 天 | 第一次具备「用户报问题能查」 |
| **S2** | P1-7 CI（Win 全量 / mac 构建） | 0.5 天 | S1 的成果不会退化 |
| **S3** | P1-8 签名 + P1-4 更新通道 | 独立里程碑 | 「能给别人用」的分水岭 |
| **S4** | P2-10 补 `chat-store` / `files.rs` 测试、P2-11 单实例、P2-12 CSP | 中 | 护栏成面 |
| **S5** | P2-9 跨平台产物、P0-1 的真权限闸门（需引擎配合） | 大 | 覆盖面与能力上限 |

**S0 → S1 → S2 的顺序不要打乱**：S2 是 S1 不退化的前提，S1 是后面所有排查的前提。S3 依赖 P1-8，别倒过来做。

## 风险与注意

- **P0-1 的两步一定要拆开**。改标签是纯收益、零风险；做真权限闸门要动 rpc 协议、要设计「记住这次选择」的持久化、要处理无头会话（定时任务里没有人可问）—— 混在一起会让一个半小时的修复卡在一个两周的特性上。
- **P0-2 抽 helper 时注意 `knowledge.rs` 已有的 `.trash/` 语义**：原子写和「覆盖前备份」是两个正交的保证，helper 只管前者，不要把备份逻辑吸进去。
- **P2-9 需要真机验证**，纸面改完不算完；在没有 mac 的情况下最多做到 CI 能构建（S2 已覆盖），别声称支持。
- **P1-5 的日志要注意不落密钥**。`pi_config` 的写入路径会经手 `auth.json` 的内容，替换 `eprintln!` 时逐个确认打的是路径不是内容。
