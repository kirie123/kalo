# 主动任务工作台原型

日期：2026-11-01。状态：第一期源码闭环已实现并通过专项验证，尚未重建安装包或做真实模型端到端验收。当前实现范围以文末「第一期实现契约」为准，上半部分描述完整目标方案。

## 目标与交付范围

在 Kalo 的会话、自动化、数字专家与成果预览之上增加统一工作台。用户打开时先知道哪件事需要自己、做一个什么决定、完成后去哪里看结果。执行过程留在原会话，运行正常的任务不逐条打扰。

原型阶段交付界面演示与落地设计；随后的第一期实施增加桌面入口、任务服务、进程宿主和引擎扩展。独立 HTML 原型仍使用演示数据，其按钮只改变本地界面，不启动真实任务。

可直接用浏览器打开 [工作台交互原型](mockups/2026-11-01-proactive-workbench.html)。预览包装提供图标与界面运行支持，首次加载这些资源需要网络；业务演示不连接任何后端服务。独立预览会在浏览器内保留演示状态，不写入 Kalo 数据目录。

## 信息结构

保留左侧窄导航与工作空间侧栏，新增「工作台」入口。工作台侧栏包含：

- 需要你：待回答、待验收、运行失败、结果投递失败。
- 全部任务：处理中、等待外部更新、已结束，以及需要用户的任务。
- 主动规则：规则范围与关闭／仅观察／自动执行三个模式。
- 事件记录：收到什么、为什么忽略或接单、归到哪个任务。

主区域使用任务列表与详情双栏；详情默认打开可用结果或需要回答的问题，授权与执行记录折叠。窄屏依次排列，所有主要动作保持可达。已有对话入口保持可直接发起工作，自动化入口继续管理时间触发配置，工作台承接每次执行的结果。

导航角标只统计需要用户的任务；运行中数量单独展示，不合并为红点。相同任务可以在总列表中出现，但需要用户的原因按固定优先级只呈现一个，角标等于对应列表长度。

## 任务生命周期

任务是用户目标的长期记录；会话是上下文；一次运行是执行尝试。这三者用 ID 关联，不互相替代。

显示状态依次判定：

1. 已结束：用户验收、停止，或明确的业务完成条件满足。
2. 交付失败：结果已生成，但目的地未确认接收。
3. 等你回答：存在未解决的结构化问题。
4. 待验收：可交付结果已准备好，需要用户审阅。
5. 需要恢复：最近一次运行失败或中断，尚无新的恢复请求。
6. 排队中／处理中：已有有效运行或待启动尝试。
7. 等待外部更新：无正在计算的运行，仍在等已有任务的输入。

「生成完成」不等于「用户验收」，「消息入队」不等于「投递成功」。待验收是否必须由人确认由任务验收条件决定，不强制把所有普通聊天结束都转成待办。

原型可操作路径：选择任务 → 查看结果 → 确认收下；选择问题 → 给出范围 → 继续执行；失败 → 重试；处理中 → 二次确认停止。原型的重试只进入处理中，不用计时器伪造真实执行完成。

## 接单、授权与追问

入口事件统一表达为来源、来源内唯一 ID、原会话、发起人、发生时间、内容与受信范围。先做确定性来源过滤与去重，再按任务关联分流；只有有必要判断意图时才请求模型。

已关联任务的追问优先回到原任务；只用于背景阅读的事件不能扩大授权，超范围追问退回接单判断。用户明确停止后撤销该任务的继续执行资格；新事件不能静默恢复它。

接单时冻结授权快照：用户明确委托或命中的规则、规则版本、允许读写范围、可用能力、交付目的地与验收条件。恢复运行前重验规则是否仍有效；规则被关闭或发起人权限撤销后，不能继续沿用旧授权启动下一次运行。

规则模式只控制规则推断出的新工作，不拦截用户当前的明确委托：

| 模式 | 收到符合规则的事件 | 可见结果 |
| --- | --- | --- |
| 关闭 | 不接单，不创建运行 | 记录未接单原因 |
| 仅观察（默认） | 判断是否值得执行，但不创建任务或运行 | 事件记录展示拟执行内容与命中理由 |
| 自动执行 | 范围与授权检查通过才创建任务 | 任务出现，保留决策证据 |

模式切换显示授权范围后保存；观察记录不在切换后自动回放，用户可以明确选择某条事件重新评估。外部文本作为数据，不允许改写规则、权限、执行目标或通知目的地。

## 界面场景

原型沿用 Kalo 清昼皮肤的浅灰侧栏、克制边线、绿色选中态与成果右栏：

- 「每周研究摘要」：定时触发，已生成摘要，打开后能预览并确认收下。
- 「整理财报资料」：用户主动委托，年份范围不明确；选择本年度或近三年后任务回到处理中。
- 「文件预览回归检查」：执行失败，失败原因与重试入口同处一屏。
- 「整理知识笔记」：正在运行，不产生需要用户的角标。
- 「资料更新后整理差异」规则：可试跑演示事件，分别验证关闭、观察和自动三种决策；重复事件去重。

所有数字、文档和日志均是界面演示，不能理解为真实仓库测试结果或真实研究报告。来源与规则版本放入详情，默认展示行动及交付物。

## Router 与 Worker 的运行组织

以下是完整目标方案，独立 HTML 原型没有这些执行能力。第一期已同步修改 Gateway、Rust 进程宿主与 harness 扩展，具体已实现子集见文末；外部事件、规则、专家选择、输入队列与 outbox 仍是后续工作。

### 进程与状态所有权

采用一个任务控制服务、多条任务执行会话：

```text
桌面委托 / 定时触发 / 来源事件
             ↓
Gateway：事件入库 → Router → 任务事务 → 调度队列
                       ↑                     ↓
             受限 pi 路由评估          Rust WorkerHost
                                             ↓
                               pi Worker A / pi Worker B
                                             ↓
Gateway：运行回执 → 问题 / 成果 / outbox → 桌面与原会话
```

- Gateway 是任务业务状态的唯一写入者，拥有事件、决策、任务、授权快照、输入、运行尝试、问题、结果和投递回执。
- Rust 的 WorkerHost 拥有真实 pi 进程与任务运行映射，负责启动、就绪探测、输入投递、取消、退出与重启后对账；不自行决定任务完成。
- Router 决定事件归属与拟执行范围，不能执行用户业务工作，也不直接写库。Worker 执行任务，通过结构化报告提出状态变化，最终状态由 Gateway 校验后落库。
- 前端读取投影，通过带动作 ID 的命令回答、验收、重试或停止；不能直接改任务状态。

### Router：确定性路由在前，模型判断在后

Router 由普通代码和按需运行的受限 pi 评估会话组成。每个工作空间一条逻辑路由队列，同一来源会话同时最多一个评估；模型只拿当前事件、有上限的上下文、规则版本与相关任务摘要，不装载所有 Worker 的完整历史。评估采用独立短会话，事实从数据库重建；第一版无需常驻全局「总管聊天」。

处理顺序：

1. 以来源 ID + 来源事件 ID 去重，检查来源、发起人和工作空间范围。
2. 结构化问题回答按 questionId 直达原任务；结构化停止指令校验操作者后走控制服务，不等待 Router 模型。
3. 确定关联的追问投递到原任务输入队列；背景订阅只增加上下文。目标有歧义时才交模型判断，不能单靠关键词附到最新任务。
4. 已授权定时委托直接创建本次任务；规则事件在关闭模式停止，在观察／自动模式进行规则匹配与必要的语义评估。
5. 模型只提交结构化候选：create、attach、ignore、clarify 或 stop。create 携带标题、目标、验收条件、expertId、范围建议、依据事件及规则 ID；attach/stop 指向已有 taskId。clarify 形成可持久回答的问题，不启动业务 Worker。
6. Gateway 重新校验候选的规则版本、接单模式、任务归属、停止证据与实际授权；观察模式的 create 只记录 wouldCreate。有效接单在一个事务中创建 Task、Mandate、初始 Input 与 dispatch effect。

Router 工具只开放候选上下文读取、限定的任务摘要查询、规则读取和路由提交。模型不可选择任意 cwd，不得拥有 bash、文件写入、外发或修改规则的工具。能力限制落实到工具注册与执行 gate；仅在提示词中写「只负责路由」不构成约束。

规则、来源权限或任务版本在评估期间变化时，拒绝旧结果并重评；模型输出无效或超时记 unavailable，有限重试后成为可处理的系统问题。数据库事务不跨越模型调用。

### Worker：一项委托一个上下文，一次执行一个 runId

Task 持有长期目标与授权；Worker session 持有执行上下文；Run 记录一次启动／恢复尝试。taskId 稳定，重试生成新 runId，sessionFile 是可恢复的引擎历史，processSessionId 是当前进程句柄，四者分开保存。

初始任务包包括目标、验收条件、原始请求、授权快照引用、工作空间 ID、专家配置、允许工具、预算、输入序号与交付目的地。任务包保留用户原意，Router 不额外发明实现要求。由宿主把工作空间 ID 解析为受管目录；代码任务使用隔离工作树或明确的仓库写锁，资料任务使用独立产物目录。不同 cwd 不等于 OS 文件系统隔离。

Worker 的业务工具之外新增任务协议工具，名称暂定：

- `task_report`：报告 progress、ready、waiting、blocked、failed，携带结果引用与验收证据；工具被绑定到当前 taskId/runId，模型不能指定其他任务作为报告目标。
- `task_ask`：持久保存 questionId、选项、问题及目标会话，返回已登记回执；当前轮结束后释放执行槽。用户回答按 questionId 写入 Input，并按需要恢复原 sessionFile。
- `task_handback`：将超出原授权的追问退回 Router；以 inputId 记录一次退回，防止 Router 与 Worker 互相投递形成循环。

后台会话现有的 `KALO_UNATTENDED=1` 会禁用交互式 `ask_user`；因此 `task_ask` 必须是新的持久问题通道，不能在后台保留一个等待 UI 的 Promise，也不能假设现有 ask_user 已能覆盖该流程。

Worker 内部多轮工具调用由 pi 负责。输入到达时先落 Input 队列，同一任务串行消费；运行中使用已经验证的排队续写适配，不能并发发送两个普通 prompt。每个 Input 分别记录已交给引擎、已被当前轮读取、处理确认三个状态。仅 stdin 写入成功或 session_started 不算业务输入已处理。

Worker 可报告 ready，但必须待相关轮次及已登记后台子任务结算、结果引用有效后才能进入可验收状态；进程退出码 0 或助手停止生成不能单独代表业务成功。对于有测试验收条件的任务，缺少对应证据仍为未完成。

### 调度、停止与恢复

第一版采用一个 Gateway 调度器、保留一个 Router 评估槽、两个业务 Worker 执行槽。数值是初始默认值，后续按机器资源校准；等待用户或外部事件不占活动执行槽。每个 Task 最多一个启动中／活动 Run；跨任务公平排队，工作空间写冲突由锁或隔离目录处理。

Worker 的子 agent 属于原 Task，默认不产生顶层任务；预算和并发应计入原 Task。第一版任务 Worker 先关闭嵌套派生，等共享预算与取消传播完成后再开放，不能让 N 个 Worker 各自无限扩成 N 组子 agent。

dispatch effect 重放必须复用 runId；Rust 按 runId 返回同一个启动结果。一次有效重试才分配新 runId。所有回报带 taskId、runId、generation 与递增 seq；Gateway 校验活动归属并去重，旧尝试的迟到回报不能覆盖新尝试。

停止时先持久撤销运行资格并更新 generation，再请求 Rust 中止进程树；Worker 进入 cancelling，确认退出后为 cancelled，无法确认时显示控制失败，不能假装已经停止。任务工具和后续工具调用的执行 gate 拒绝撤销的资格；已经发生或正在执行的外部副作用不承诺撤回。Windows/macOS 的进程树处理继续走现有窄适配层。

Gateway 重启后先向 Rust 查询仍存活的 Worker，核对 runId 与代次后认领，避免重开一个仍在运行的任务。进程存活未知时保持 recovering，不凭超时直接启动第二个执行器。应用整体退出后的孤立 Run 记 interrupted，不自动重放写操作；用户明确恢复时校验授权并读取原 sessionFile，再创建新 Run。历史会话只读打开不触发恢复。

### 实现目录与消息边界

新增模块按职责拆开，不继续加大现有 gateway/main.ts、Rust gateway.rs 或 scheduler.ts：

```text
kalo-desktop/gateway/src/orchestrator/
  model.ts         任务、运行、授权与消息类型
  store.ts         SQLite 事务、唯一约束与版本校验
  intake.ts        来源过滤、去重与事件归属
  router.ts        确定性路由 + 模型评估适配
  policy.ts        接单、续跑、工具与外发授权
  scheduler.ts     槽位、队列、恢复与取消协调
  reports.ts       输入确认、问题、结果及运行报告
  outbox.ts        有目的地和确认状态的消息投递
  views.ts         工作台只读投影

kalo-desktop/src-tauri/src/task_workers.rs
  WorkerHost：通过 PiProcess 管理专用进程和会话恢复

kalo-harness/packages/coding-agent/src/extensions/task-runtime/
  Router/Worker 工具配置、执行 gate、报告与持久问题适配

kalo-desktop/src/features/workbench/
  列表、详情与用户动作
```

Store 采用 Gateway 单写的独立 SQLite 库，将事件接单与 dispatch/outbox 同事务提交；不复用已有 schedule 的 lastResult 或 job 的 reported 作为任务真相。锁住同一数据根的控制服务实例。Bun 打包后的 SQLite 可用性与迁移需在 Windows/macOS 安装包验证。

新增 Worker 协议与原有 session_request 分离，至少涵盖 start、input、cancel、inspect，以及 started、input_received、input_read、report、settled、exited 回报。命令携带 requestId/runId/generation，回报携带相应关联键；start 接受 role、工作空间、授权引用、模型与可选 sessionFile，禁止前端借此注入任意启动环境。

引擎扩展通过已鉴权、绑定到该进程的宿主适配通道访问任务服务；不把模型提交的 taskId 或来源会话 ID 当作身份凭据。具体 wire schema 与注册方法在实施前同步写入协议类型、bridge contract 检查及 harness 扩展文档，以上命令为设计能力名，不宣称现有 RPC 已支持。

### 最小闭环验收

先实现「用户委托 → Router create → 独立 Worker → task_ask → 工作台回答 → 原 session 续跑 → 成果 → 验收」。随后验证重复事件、重复 start、Gateway 重启保留存活 Worker、应用退出中断、停止与迟到回报竞态、观察模式零 Worker、跨任务回答隔离。外部来源和嵌套 agent 均放在此闭环稳定之后。

## 分期落地安排

### 第一期：把已有工作变得可见

新增统一任务投影，聚合会话中的问题、已声明成果、定时执行结果与后台中断。原会话仍是执行事实来源；状态无法读取时明确显示未知，不推断为成功。先落地需要你、详情预览、回原会话三个动作。

### 第二期：持久委托与可恢复执行

定义任务、运行、授权快照、输入、结果及投递回执。任务记录持久化在 Kalo 数据根下专属子目录，路径通过现有目录解析入口获取。以事务写状态和待执行效果；执行器回报后再推进状态。为每次动作加入幂等键，给接收与处理保留独立回执。

退出后没有执行器的在途任务标为中断；重新打开只是读取，不自动重跑写操作。用户恢复后创建新的尝试，并保持原任务与会话关联。保留现有后台任务进程寿命，不宣传关闭应用后仍可计算。

### 第三期：有边界的主动工作

先接入定时与本地资料更新，运行观察模式检验误接单、重复触发、无价值打扰。之后再按来源增加外部事件适配器。外发能力独立授权，不因可以读取一个来源就获得向其发送消息的资格。

可靠投递采用 outbox，记录目的地、消息幂等键、pending/sent/failed、尝试次数与确认时间；支持退避与重试。只承诺可核实的至少一次语义，接收端用幂等键去重，不声称外部副作用恰好一次。

## 第一期实现契约（2026-11-01）

第一期只接工作台的明确委托，不自动接管已有聊天、定时任务或飞书；这些入口保持原行为。委托先进入受限 Router 会话，提交 create/clarify/ignore 决策；create 结算后排入独立 Worker。attach 由带 taskId/questionId 的用户动作确定，不让模型猜其他任务。自动规则与外部事件适配留在后续阶段，不在界面提供假开关。

新增 Tauri `workbench_request({request})`，请求 action 为 list/create/answer/retry/stop/accept；所有写请求带 actionId，create 带 prompt/cwd 与明确的 allowShell 开关（默认关闭）。网关收到 `workbench_request` 后返回 `workbench_reply`（requestId/ok/tasks/error），并发出 `workbench_changed` 通知。数据库位于 Kalo 数据根的 `agent/orchestrator/tasks.sqlite`，锁跟随 Gateway 的单实例入口；实例拿锁后才能打开库。

Gateway → Rust 的执行消息为 `task_worker_start`（runId/taskId/role/cwd/sessionFile/endpoint/token/allowShell）、`task_worker_prompt`（runId/prompt）、`task_worker_cancel`（runId）、`task_worker_inspect`。Rust → Gateway 使用 `task_worker_started`、`task_worker_failed`、`task_worker_inventory`；pi 原事件仍走已有 event/session_exit，sessionId 固定由 runId 派生。启动与首个 prompt 均按 runId 去重。引擎 task-runtime 在 session_start 向 context 提交协议版本、角色与会话路径；Gateway 仅在此握手和 Rust 就绪回执都成功后才发 prompt。旧 sidecar 缺少任务扩展时不投递用户委托，停止该进程并提示重建。

任务会话保存在 `agent/task-sessions/<taskId>/`，通过 `--session-dir` 指定，不进入普通聊天历史，避免从聊天入口并发恢复同一任务会话。回答要求原 sessionFile 仍存在；失败重试若尚未形成会话文件，则从已持久化的原始委托与执行记录重建，并明确记录上下文缺失；已有结构化回报却丢失会话时拒绝恢复。

恢复使用已落盘的 sessionFile；Worker 结束后关闭进程并释放槽位。Gateway 重启先请求 inventory。第一期采用保守恢复：旧 HTTP 端点已失效，撤销并终止存活旧执行，确认退出后显示需要恢复；不直接认领继续运行。排队任务可继续派发；曾启动但已丢失的进程标失败，等用户明确重试；不会凭超时启动同任务第二个执行器。

引擎注册 task-runtime 扩展：环境只由 Rust 注入 role/endpoint/token，令牌绑定到 Run，模型不能以 taskId 冒充身份。loopback HTTP 仅接受 bearer Run 令牌，开放 context/gate/decide/ask/report；返回会话记录路径由引擎 session manager 提供。每次工具执行前请求 gate，撤销或离线一律拒绝。Router 仅有 task_context/task_decide/task_ask；Worker 仅有本地文件工具和任务协议工具，可选 bash 必须由用户创建时单独启用。关闭嵌套 agent、后台 job、MCP 和外发工具。文件工具校验真实路径归属；allowShell 不构成 OS 沙箱隔离，界面明确说明其可执行本机命令。

ask/report/decide 使用工具调用 ID 去重；ask 登记后不挂起 UI Promise，后续业务工具被 gate 阻断，轮次 settled 后才呈现可回答状态。ready 必须有摘要，文件引用需确实存在且位于授权目录；agent_settled 且未出错才进入待验收。没有协议报告的自然结束视为失败，提示检查 sidecar 版本或重试，不猜测成功。等待问题时关闭 Worker，回答提交事务创建新 Run，续用原 sessionFile；Router 问题回答后恢复 Router 会话。

每个 Task 只允许一个活动 Run，同目录及互相包含的目录内业务 Worker 串行；这是任务服务内的并发约束，不会锁住用户的普通聊天或外部编辑器。初始上限为一 Router、两 Worker。每次执行最长 15 分钟，超时先终止进程，确认退出后显示失败；重试不会自动发生。stop 立即撤销工具资格，界面先显示停止中，收到真实退出才标已停止；超时不虚报成功。应用退出中断的任务需用户明确重试。

### 第一期间的职责和限制

| 层 | 实际文件 | 已实现职责 |
| --- | --- | --- |
| 共享契约 | `kalo-desktop/shared/workbench.ts` | 状态、任务投影和用户动作 |

当前 SQLite 保存任务 JSON 和动作去重表；Run 队列与任务在同一事务里创建，派发前持久记录 starting。尚未实现完整事件表、通用输入流水、外发 outbox 或 schema 迁移框架。不得将第一期看成完整主动代理平台。

本期使用配置中的默认模型，没有专家选择。`task_report` 只接受 ready/failed；ready 校验摘要和真实文件路径，但不会独立判断模型给出的测试证据是否充分，用户仍需验收。没有后台子 agent，也没有独立 OS 隔离；允许 bash 后，模型可以执行本机命令，工具门禁不是系统安全沙箱。文件路径检查会解析现有符号链接、`~` 和引擎支持的路径写法，但不承诺阻止其他本机进程在检查与执行之间替换文件。

工作台只呈现真实快照；服务离线保留当前页面已加载列表并显示错误，首次打开离线时没有本地快照，不伪造演示任务。原有 HTML 原型保留完整规则演示，与生产数据互不相连。
