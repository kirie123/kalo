## 2. 真 bug：并行文件竞态（P0）

### 机制（代码路径）

- `packages/agent/src/agent.ts:237`：`this.toolExecution = runtimeOptions.toolExecution ?? "parallel"` —— **默认并行**；编码 agent 未覆盖该值（`kalo-desktop` / `kalo-harness/packages/coding-agent` 都没有传 `toolExecution`）。
- `packages/agent/src/agent-loop.ts` `executeToolCallsParallel()`：同一条助手消息里的多个调用**并发执行**；结果按调用顺序统一落盘，所以转录里结果的顺序**不能反映执行的先后**。
- 只有 `ask-user` 标了 `executionMode: "sequential"`；`read` / `edit` / `write` 都没有。
- `edit` / `write` 走 `withFileMutationQueue(absolutePath)` 做同路径互斥，但 **`read` 不在这条队列里**。
- `edit` / `write` 底层是 `fs.promises.writeFile`（truncate + write，**非原子**）。

### 证据 A：read 读到「写一半」的空文件 —— `1 lines total`

会话 B 第 1975 / 1979 行（同一条消息里 `read` + `edit` 同文件）：

```
read { path: .../proactive-panel-watches.tsx, offset: 95, limit: 14 }
→ Offset 95 is beyond end of file (1 lines total)   ← 同会话内用 python 读同一文件得 143 行

read { path: .../lib/i18n/messages/proactive.ts, offset: 18, limit: 12 }
→ Offset 18 is beyond end of file (1 lines total)   ← 同会话内 python 读同一文件得 204 行
```

`read` 的实现（`packages/coding-agent/src/core/tools/read.ts`）是 `textContent.split("\n").length`；空文件的 `"".split("\n")` 恰为 `[""]`，长度 1 —— 即 **read 落在 edit 的 truncate→write 窗口里**。模型当时把它当成「weird harness artifact」跳过了，没有意识到是竞态。

### 证据 B：read 成功返回了内容，随后同批的 edit 仍报「has not been read」

会话 B 第 1988 行一条消息：`read(offset=124)` + `edit` 同文件；read 结果正常（第 1989 行返回了正文），edit 却报：

```
File has not been read in this session: ...process...
```

下一轮 `read` + `edit` 同文件却成功。机制：`edit` 的守卫读 `readState`（`file-read-state.ts`），而 `read` 记录 signature 发生在 `readFile` 完成**之后**；并发时 `edit` 的守卫检查可以先到。

### 影响

- 直接误报：2 次假「1 lines total」、2 次假「has not been read」（4 个会话共 16 次「not read」，其中 2 次同批有 read 兄弟，其余是名副其实的没读）。
- 间接误导：模型反复看到「写命令前脚跑、后脚文件不存在」，据此在会话里写下结论「**bash 写入是每调用沙箱、会被回滚**」「**只有最后一个调用执行**」——并把这些错误经验沉淀进了跨会话记忆，反过来指挥后续所有会话（本复盘的主线索）。

### 修复建议（按代价从小到大）

1. **全局串行化文件类操作**：给 `read` 也加 `executionMode: "sequential"`，或把 coding-agent 的 `toolExecution` 直接设为 `"sequential"`（Claude Code 即串行；代价是同一批里 bash 等并行调用也退化为串行，可接受）。
2. **或只让同路径的 read 等写入**：`read` 进 `withFileMutationQueue`（注意 read 队列不能把并发读也串起来，只对「正在被写」的路径等待）。
3. **写盘原子化**（独立收益）：写临时文件 + rename；这样即使并行，读者也只会看到旧内容或新内容，不会看到空文件。
4. 守卫在「同批存在未完成的 read」时等待其 signature 落地，而不是直接拒绝 —— 至少把错误信息改成可诊断的形状。

## 3. 「静默丢调用」的真相：DSML 写进思考通道（模型/网关侧，非 harness bug）

### 实测数据

- 4 个会话的结构化调用 **2636/2636 全部有结果**；「文件不落地」的 18 处缺文件路径**全部可追溯到「从未创建」**（思考通道泄漏 / 模型只在脑内「计划」），**0 例「write 报告成功但文件消失」**。
- 思考块内 DSML 标记（`<|DSML| invoke name="bash">` 形态）：B 会话 383/682 条思考消息、共 6808 处；A 283/665；C 16/97；D 13/39。
- 模型原话（会话 B，思考）：`**Conclusion: each bash call runs in a fresh sandbox/snapshot where writes are discarded afterward.**`、`this session's behavior: only the last tool call per message executes`、`bash writes → ephemeral (rolled back / sandboxed)` —— 与实测不符，是误判。
- 本次复盘会话里，作为分析者的我本人也触发了一次同样形态的丢包（把 bash 调用写进了思考通道），被引擎提示后重发成功 —— 现象可稳定复现。

### 安全网现状（2026-09-21 已实现，见设计文档）

- 检测：`packages/agent/src/dsml-tool-calls.ts` 按 **工具名集合**去重：丢了 `bash` 且同一消息里没有真正执行的 `bash` 才提示。
- 上限：`MAX_THINKING_CHANNEL_TOOL_NUDGES = 2`，**每次 run**（即每个用户回合）最多提示 2 次。
- 注入的提示消息只进模型上下文，**不落会话转录**（实测 4 个文件 user 角色 nudge 消息 = 0；`agent-session.ts` 只在 `message_end` 事件时持久化，而注入消息未 emit）。

### 盲区量化（若只修检测、不动上限）

| 会话 | 有泄漏标记的消息 | 会被同名遮蔽（不提示） | 理论上会提示 |
|---|---|---|---|
| A | 283 | 232 | 58 |
| B | 383 | 293 | 116 |
| C | 16 | 10 | 6 |
| D | 13 | 11 | 2 |

- **同名遮蔽率约 75%–85%**：模型经常「同一条消息里既泄漏一个 bash、又真的发一个 bash」，按名字去重就把泄漏那次吞掉了。
- 加上每 run 2 次的上限，实际提示量远小于泄漏量；用户看到的就是「模型自称在执行、其实什么都没跑」。

### 修复建议

1. 检测从「名字集合」升级为「**逐个 invoke 块**」计数（比如 name + 参数指纹），泄漏 3 个同名的就应提示 3 个。
2. 上限从「每 run 2 次」改为「每 N 轮」或按泄漏消息数节流；至少把上限暴露到设置里。
3. 把注入消息 `emit` 出来并持久化（UI 上标注为「引擎继续」）——既方便用户理解模型为何「自言自语」，也方便复盘。当前设计文档 §3 声称会进会话记录，实测不一致，需对齐文档或实现。
4. 根治仍在网关侧：思考通道的调用标记必须转换或剥离；引擎安全网只是兜底。

## 4. Windows 平台质量（P2）

1. **GBK 输出乱码**：`OutputAccumulator` 用 `new TextDecoder()`（UTF-8）解码一切子进程输出；zh-CN Windows 上 `taskkill` / PowerShell 等原生程序输出 GBK，乱码后模型读不懂错误。实例：`成功: 已终止 PID...` 显示为 `ɹ: ֹ PID...`。建议：UTF-8 解码失败时回退系统代码页，或对 cmd/powershell 包装 `chcp 65001`。
2. **`/tmp` 语义分裂**：`path-utils.ts` 的 `normalizeWindowsShellPath` 只归一化 `/d/...`、`/mnt/d/...`、`/cygdrive/d/...`，**不处理 `/tmp`**；Node 把它解析成 `<当前盘>:\tmp`（实测 `read /tmp/attached2.png` → `D:\tmp\attached2.png` ENOENT ×2），而 Git Bash 的 `/tmp` 是另一个目录。建议：Node 工具把 `/tmp` 映射到 `os.tmpdir()`，或至少在工具说明里写明差异。
3. **MSYS 参数路径转换**：`taskkill /PID 36464` 被 Git Bash 转成 `C:/Program Files/Git/PID`（模型随后改用 `//PID` 成功）。这是 MSYS 已知行为，不是 harness 缺陷；建议在 bash 工具说明里加一条提示（或提供 `MSYS_NO_PATHCONV=1` 的开关）。
4. **中文 heredoc 喂原生 Python**：`py -3.12 - <<'PY'` 的脚本经 stdin 被按 GBK 解码 → `SyntaxError: unterminated triple-quoted string`（会话 A 第 714 行）。模型后来用 `PYTHONUTF8=1` 规避。可考虑在 shell env 默认加 `PYTHONUTF8=1`（对 Python 无副作用，专治这一类）。

## 5. 非 bug 清单（正常语义 / 模型用法错误）

| 类别 | 次数 | 判定 |
|---|---|---|
| edit oldText 不匹配 / 目标重复 / 块重叠 | B 7、A 7 | 模型复制不准；工具报错质量高（closest match、多余字符提示），且有容错增强设计 |

| Command aborted | B 2、A 1 | 用户插话中断（停顿处紧跟用户消息） |

| PowerShell `$pid` 只读 / `git add` pathspec 不存在 / Python 中文句号语法错 / 空参数 edit `{}` | A/B/D 各 1 | 模型用法/生成错误；工具校验给出了正确报错 |
| 缺 PIL、临时文件被锁 | B 1+1 | 环境问题 |

**文件「丢失」归因（18 处）**：`insert-silent-tests.py`、`PROBE-42.txt`、`commit-msg2.txt`、`scroll-note{,2,3}.md`、`/d/tmp/*.txt` 等 —— 逐一回查「同一路径在更早的结构化调用里是否出现过」，结论全部是**从未创建**（对应调用只在思考通道里出现过，或纯属计划）。包括模型当时断言的「write 工具报 Successfully 但文件不存在」：那些路径在转录里根本没有结构化 write 调用。

| 优先级 | 改动 | 预期收益 |
|---|---|---|
| P0 | 同路径 read/edit/write 串行（或 coding-agent 默认 sequential；或写盘原子化） | 消除 2 类误报 + 「写命令后脚验证失败」的连环误导 |

| P2 | GBK 解码回退 / `/tmp` 映射 / bash 说明补充 MSYS 提示 / env 加 PYTHONUTF8 | 降低 Windows 中文环境摩擦 |

## 7. 复盘方法（可复用）

- 会话 jsonl 里：assistant 的 `toolCall`（含 id）与 `toolResult`（`toolCallId` / `isError`）按 id 配对，缺失即「未执行」；本批 4 个文件缺失为 0。
- 思考通道泄漏：对 `thinking` 文本跑 `dsml-tool-calls.ts` 的同款正则。
- 文件「丢失」：对每个 bash 报错里的缺失路径，回查更早的结构化调用是否提到过同一 basename —— 区分「真的丢」与「从未创建」的关键。
- 竞态判定：看同一助手消息里是否存在同路径的 read 与 edit/write；注意结果顺序不代表执行顺序。
