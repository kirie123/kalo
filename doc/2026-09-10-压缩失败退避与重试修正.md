# 压缩失败退避与重试修正

## 问题

生产会话截图中，一次会话内连续出现：

1. `上下文压缩失败：Auto-compaction failed: Turn prefix summarization failed: 400 {...Consumer Terms...}`
2. `上下文压缩失败：Auto-compaction failed: Turn prefix summarization failed: The operation was aborted.`
3. `上下文压缩失败：Compaction failed: Summarization failed: Upstream service temporarily unavailable`
4. 之后又一次进入「正在压缩上下文…」——失败 3 次以上仍在触发。

另一症状：压缩**成功**后（时间线出现「上下文已压缩」气泡），上下文圆环仍显示 88K / 200K（44%），用户认为刚压缩完不该这么高。

## 根因

### 根因一：retry 名单缺口

`kalo-harness/packages/ai/src/utils/retry.ts` 的 `RETRYABLE_PROVIDER_ERROR_PATTERN` 有 `service.?unavailable`，只匹配 "service unavailable" / "service_unavailable" 这类紧贴写法，匹配不了生产网关的 "Upstream service temporarily unavailable"。该瞬时故障因此被判为确定性错误，摘要请求一次也不内部重试，直接抛为压缩失败并计入熔断计数。

### 根因二：熔断计数盲区 + 无失败退避（循环触发的真实路径）

自动压缩失败计数（`_compactionConsecutiveFailures`）只覆盖两条路径：`_runAutoCompaction` 中 `compact()` 上抛异常、以及压缩成功但 `savingsRatio < 0.15`（`agent-session.ts` 的 catch 与有效性分支）。盲区：

- **手动 `compact()` 失败完全不计数**：手动路径的 catch 只发 `compaction_end` 错误事件，不触碰计数器（既有锁定语义：手动压缩不跳熔断）。截图第 3 条的前缀是 `Compaction failed:`（手动路径），不是 `Auto-compaction failed:`——用户在两轮自动失败后手动点了压缩，这次失败没有推进熔断。
- 信号中止（`abortCompaction()`、重试退避期被 abort）不计数；`prepareCompaction` 结构性 no-op 不计数；扩展 cancel 不计数（均为既有语义，保留）。

同时**没有退避**：压缩失败后上下文仍超阈值，而 `_checkCompaction` 有三个自动入口——`_handlePostAgentRun`（run 结束）、`prepareNextTurnWithContext`（每次 LLM 调用前）、`prompt()` 预检——每个后续 LLM 调用前都会立即重试压缩。

截图的确证路径：失败 1（400，不可重试，计数 1）→ 失败 2（aborted 以 error 形态上抛，计数 2）→ 失败 3（手动 compact，不计数，计数仍为 2 < 3）→ 熔断未跳闸，第 4 次自动压缩照常触发（「正在压缩上下文…」）。只要中间夹杂手动失败、信号中止或一次「有效成功」（savingsRatio ≥ 0.15 会清零计数），熔断永远到不了 3，用户看到的就是无限「正在压缩 → 失败」循环。

### 根因三：chars/4 对中文低估 3~4 倍（88K 的解释，成立）

`compaction.ts` 的 `estimateTokens` 用 `ceil(chars / 4)` 估算 token。英文约 4 字符 1 token，中文约 1 字符 1 token。`findCutPoint` 反向往旧攒 `keepRecentTokens`（默认 20000）预算时，中文会话实际保留约 6~8 万真实 token；加上摘要与系统提示，压缩后圆环显示 88K / 200K 与估算完全吻合。同一偏差存在于 `estimateContextTokens` 的 trailing 估算与无锚点回退、以及 `estimateMessagesTokens`（savingsRatio 计算）——三者都以 `estimateTokens` 为唯一计价入口。

## 方案

### 1. retry 名单补 `temporarily.?unavailable`

`RETRYABLE_PROVIDER_ERROR_PATTERN` 增加 `temporarily.?unavailable`，覆盖 "Upstream service temporarily unavailable"、"503 temporarily unavailable" 等写法。不添加裸 `upstream`：该词会出现在非瞬时语境（如配置/鉴权文案），误标为可重试会放大故障面。

既有锁定测试「Upstream service temporarily unavailable 不重试」随语义更新为「可重试」（这是本次要修的行为）。

### 2. 自动压缩失败退避

计数口径不变（保留全部被测试锁定的语义）：

- 计入：自动压缩中异常上抛（`compaction_start` 之后）、压缩成功但无效（savingsRatio < 0.15）。
- 不计入：信号中止、prepare 结构性 no-op、扩展 cancel、overflow 二次失败（`_overflowRecoveryAttempted` 拦截）；手动 `compact()` 失败不计入、不跳熔断；手动有效成功清零计数并复位熔断。

新增退避：

- 每次计入失败时记录锚点 `_autoCompactionBackoffAnchor = agent.state.messages.length`；计数清零时（有效自动压缩、有效手动压缩）一并清除锚点。
- `_checkCompaction` 入口（三个自动触发点共用）增加门禁：失败计数 > 0 且当前 `agent.state.messages.length <= 锚点` 时，静默返回 false——不发 `compaction_start`/`compaction_end`，不刷错误事件。
- 效果：一次失败后，必须有至少一条新消息进入上下文（用户输入、助手回复、工具结果）才会再尝试；同一 turn 内剩余的 LLM 调用前检查全部静默跳过。选「消息数增长」而非「N 个 turn」或时间窗口，因为 RPC 无交互模式下它确定性强、无需定时器、可直接单测。
- 退避期间 overflow 恢复（Case 1）同样暂停：压缩刚失败过，立即对同一上下文再压一次大概率仍失败。
- 熔断不变：连续 3 次计数失败跳闸，跳闸后 `_runAutoCompaction` 入口静默返回 false，本会话不再自动压缩；有效手动压缩仍可复位。
- 手动 `compact()` 不经过 `_checkCompaction`，不受退避与熔断限制（用户显式要求）。

### 3. CJK 感知的统一计价

只改 `estimateTokens` 的单点字符计价：统计「加权字符数」——CJK 字符按 4 个字符权重计入（÷4 后 ≈ 1 token/字），其余字符按 1（维持 chars/4），图片块维持 4800 字符权重。覆盖码位区间：U+3000–U+30FF（CJK 标点、平/片假名）、U+3400–U+4DBF（扩展 A）、U+4E00–U+9FFF（CJK 统一表意文字）、U+F900–U+FAFF（兼容表意）、U+FF00–U+FFEF（全角形式）、U+20000–U+2A6DF（扩展 B，按码点迭代天然支持）。

共用链路自动生效：`findCutPoint` 的切割点预算累计、`estimateContextTokens` 的 trailing 估算与无锚点回退、`estimateMessagesTokens`（savingsRatio）、branch-summarization 的用量估算都以 `estimateTokens` 为入口。2026-09-08 文档的高水位语义（usage 锚点选择、压缩边界重置）不变，只改计价精度。

`packages/agent/src/harness/compaction/compaction.ts` 是镜像副本，同步修改（09-08 文档要求两边同名估算函数保持一致）。

### 4. 压缩边界时间戳核验

核验结论：`buildSessionContext` 经 `sessionEntryToContextMessages` → `createCompactionSummaryMessage(entry.summary, entry.tokensBefore, entry.timestamp)`，compactionSummary 消息带数值时间戳；`estimateContextTokens` 的 `getLatestCompactionTimestamp` 能找到边界，压前旧 usage（timestamp ≤ 边界）不参与锚点选择。该链路无缺陷，补测试锁定。
