# 统一检索 `recall`：SQLite FTS5 + trigram

日期：2026-08-18
状态：已确认（2026-08-19 定稿：路径以代码为准，autostart 前提已成立）

## 需求

今天「跨会话找东西」是断的：

| 语料 | 现状 |
| --- | --- |
| 会话日志 `~/.kalo/agent/sessions/**/*.jsonl` | **完全搜不了**。侧边栏「搜索」按钮是 `notImplemented`（`Sidebar.tsx:182`）；`list_sessions` 只读每个文件头部凑一个标题（`sessions_store.rs:126`），正文从不进内存 |
| 记忆 `~/.kalo/memory/` | 有 `memory_search`，全量读目录 + 手写打分（`extensions/memory/index.ts:230`），只给模型用 |
| 知识卡片 `~/.kalo/knowledge/` | 只有前端 client-side 过滤，匹配标题/tags/域，**不搜正文**（`KnowledgeSettings.tsx:42`） |

目标：三处语料一个索引、一个查询入口，**人和模型走同一条路**。路线定死纯关键词/全文，不引入 embedding（roadmap P1-R）。

## 结构决策

以下决策是同类实现反复踩坑后沉淀的，直接采用。

**直接采用的结构性决策**

1. **派生索引单独一个库**，绝不把 FTS 表塞进权威数据。索引损坏、重置、换分词器都不该危及原始日志。
2. **`application_id` + `user_version` 双保险**：不是本应用的库直接拒绝；是本应用但版本不匹配就整库重置。它甚至在动 `journal_mode` 之前就先拒绝陌生库——因为 pragma 是写操作。这条我们必须抄，`~/.kalo` 下面全是用户的真数据。
3. **revision 增量对齐**：每个源存一个修订号，与已索引的比对，只读变化的部分。重复查询、重开进程都不重读全量。
4. **查询整体当字面短语加引号**：`"` 写成 `""`，于是 `OR` / `NEAR` / `*` / 括号全部退化成数据，不是可执行语法。同时在进 SQLite 前拒绝 NUL。用户搜个 `a*b` 不该炸。
5. **排序用真实高亮区段数，不用 BM25**：`match_count DESC, document_length ASC, time DESC, id ASC, seq DESC`。理由很实在——两张填充内容不同的 FTS 表之间 BM25 分数不可比，而区段数和文档长度是同一把尺子。全序里带 id/seq 保证平局确定。
6. **摘要片段来自 `highlight()` 的真实位置**，不是重新找子串；标记字符用保留非字符，入库前先把源文本里的同款字符替换掉，避免撞车。
7. **对外不暴露相关性分数、不暴露后端标识**。游标是不透明的，绑定到「实例 + 范围 + 规范化请求 + 代际」，语料一变就失效。

**不采用的：分词器**

`unicode61` 对英文语料够用，但会否决 trigram，理由是「漏掉短于三字符的查询，且索引体积是 2.1 倍」。**这个结论对中文不成立**，实测（`bun:sqlite`，SQLite 3.53.0）：

```
unicode61  '梯度'    → 无匹配        # 「梯度累积把显存压下来」整串是一个 token
trigram    '梯度'    → 无匹配        # 少于 3 个字，trigram 用不上索引
trigram    '梯度累'  → [梯度累]积把显存压下来
trigram    '梯度累积'→ [梯度累积]把显存压下来
trigram    'rate war'→ learning [rate war]up   # 英文子串也能命中
LIKE '%梯度%'        → 命中           # 兜底可用
```

英文优先的语料里 `unicode61` 按空白切词够用，子串需求丢给扫描路径。我们是中文优先，**CJK 连排在 `unicode61` 下会被切成一个巨型 token，等于中文全废**——这正是 roadmap 里判定的根因。所以：

- **主索引用 trigram**，中英文都拿子串召回。
- **1–2 字查询**（trigram 的真实盲区）自动降级为 `LIKE '%q%'` 扫描同一张表的 content 列，实测可用。语料现在 1.6 MB / 46 个会话，扫描完全扛得住；等真扫不动了再说。
- 索引体积 2.1 倍的代价接受：换来的是中文能搜。

**不采用的：TEMP 实时覆盖层**

连接内 TEMP 表方案给「活跃会话」做覆盖，因为实时事件在 checkpoint 之前不算规范数据。我们没有这个问题——pi 是**每条事件 `appendFileSync` 落盘**（`session-manager.ts:1021`），jsonl 文件本身就是实时源。查询前把尾部增量读进来即可，整套 TEMP/遮蔽/重新显露的机制全部省掉。

## 归属：索引住在 gateway sidecar

三个候选：

| 方案 | 判断 |
| --- | --- |
| Rust（`rusqlite`） | 否。UI 能搜，但 pi 引擎是另一个进程，工具层够不着；且要新引一个 C 依赖 |
| harness 进程内（像 memory 扩展） | 否。UI 搜索得先起一个 pi；多个 pi 会并发写同一个索引路径——「一个进程独占一条派生索引路径」 |
| **gateway sidecar** | **是** |

gateway 已经是这个形状了：一个常驻进程持有运行时状态，对桌面走 NDJSON、对 pi 会话走 loopback HTTP（`jobs/server.ts`，凭据在 `~/.kalo/agent/jobs/endpoint.json`）。`bun:sqlite` 自带 FTS5 + trigram（已实测）。索引就是第二个「gateway 拥有的运行时」，和 job runtime 并列。

顺带：这条依赖让「网关必须始终在跑」变得更硬。前提已经成立——`autostart` 无条件 `ensure_spawned`，不再以飞书凭据为前提（`gateway.rs:873`），没有凭据时它只是报 disconnected 并照常服务 jobs。

## 数据模型

`~/.kalo/index.sqlite`（可随时删除重建）。

```sql
PRAGMA application_id = 0x4B414C4F;   -- "KALO"
PRAGMA user_version   = 1;

-- 源文件对账表：一行一个文件
CREATE TABLE sources (
  path          TEXT PRIMARY KEY,   -- 绝对路径
  scope         TEXT NOT NULL,      -- 'session' | 'memory' | 'knowledge'
  size          INTEGER NOT NULL,   -- 上次索引时的字节数
  mtime_ms      INTEGER NOT NULL,
  indexed_bytes INTEGER NOT NULL,   -- 已消费到的偏移（jsonl 追加用）
  generation    INTEGER NOT NULL
) STRICT;

CREATE TABLE state (
  singleton  INTEGER PRIMARY KEY CHECK (singleton = 1),
  generation INTEGER NOT NULL
) STRICT;

CREATE VIRTUAL TABLE docs USING fts5(
  text,
  scope        UNINDEXED,   -- session | memory | knowledge
  source       UNINDEXED,   -- 源文件绝对路径
  session_id   UNINDEXED,   -- scope=session 时的会话 id，否则 NULL
  cwd          UNINDEXED,   -- 会话所属项目，用于按项目过滤
  seq          UNINDEXED,   -- jsonl 行号 / 卡片段落序号
  kind         UNINDEXED,   -- user | assistant | thinking | tool_call | tool_result | card | memory
  time         UNINDEXED,   -- epoch ms
  title        UNINDEXED,   -- 会话标题 / 卡片标题，直接进结果不用回读
  cp_len       UNINDEXED,   -- 码点长度，排序用
  tokenize = 'trigram'
);
```

一个源文件被重新索引时，先 `DELETE FROM docs WHERE source = ?` 再重灌；追加场景（jsonl 变大且前缀未变）只灌新行、不删旧行。

## 提取：什么进索引

| scope | 文档粒度 | 说明 |
| --- | --- | --- |
| session | **一行 jsonl = 至多一个文档** | `message` 行按 role 拆出 `text` / `thinking` 内容；`tool_call` 取工具名 + 参数；`tool_result` 取文本结果 |
| memory | 一个 `.md` = 一个文档 | 标题 + tags + 正文 |
| knowledge | 一个 `.md` = 一个文档 | 同上 |

会话侧的取舍：

- **结构性行不产文档**：`session` / `model_change` / `thinking_level_change` / 流分片 / usage。
- **`tool_result` 截断到 2000 码点**再入库。整份文件读回来的内容全量入索引，收益低、体积爆炸；截断后仍能回答「我在哪个会话里读过这个文件」。
- **thinking 进索引**，但 `kind` 标出来，查询可以按 `kind` 过滤掉。
- 附件 base64、`data:` URL 一律跳过（正则识别长 base64 段直接丢）。

## 增量对齐

一次查询前跑一遍串行对账（serialized alignment，简化版）：

1. 扫三个根目录，拿到 `(path, size, mtime)` 列表。
2. 与 `sources` 逐条比：
   - 没见过 → 全量索引。
   - `size > indexed_bytes` 且 `mtime` 变新 → **从 `indexed_bytes` 偏移续读**（jsonl 只追加，`session-manager.ts:1021`）。
   - `size < indexed_bytes` 或前缀被改写（fork / compaction 会新开文件，理论上不该发生）→ 删掉该 source 的全部文档重灌。
   - `sources` 里有、磁盘上没有 → 删文档删行。
3. 全部改动在**一个事务**里提交；任一源读失败就不标记它为最新，事务失败整体回滚，下次查询自动重试。
4. 有改动则 `generation++`。

并发：sidecar 单进程单连接，天然串行；对账用一个 Promise 链排队，避免两个查询同时对账。

## 查询语义

```
recall(query, scope?, cwd?, kind?, limit?, cursor?)
```

- `query` 先 trim + 内部空白归一，再整体加引号成一个字面短语（引号转义：`"` 写成 `""`，`OR`/`NEAR`/`*`/括号退化成数据）；含 NUL 直接拒。
- **码点长度 ≥ 3 → FTS MATCH**；**< 3 → `LIKE '%q%'` 扫描**，两条路返回同样的结果结构，结果里带一个 `degraded: true` 让 UI 能提示「短词走的是扫描」。
- 过滤条件（`scope` / `cwd` / `kind` / 时间范围）编译成参数化 SQL，在排序前生效。
- 排序：`match_count DESC, cp_len ASC, time DESC, source ASC, seq DESC`。`match_count` 由 `highlight()` 结果里的标记对数得出。
- 摘要片段：`highlight()` 的真实位置 → 去标记 → 归一空白 → 按码点截到 200，命中点居中。
- 分页：不透明游标 = `base64({fingerprint, offset, generation})`。`generation` 与当前不符就判定失效，让调用方重查——语料变了就不装作还能翻页。
- **不返回分数**，只返回排序后的列表。

结果条目：

```ts
{ scope, sourcePath, sessionId?, cwd?, title, kind, time, seq, snippet }
```

## 两个门面，一份实现

| 调用方 | 通道 | 形态 |
| --- | --- | --- |
| pi 会话（模型） | loopback HTTP，复用 `jobs/endpoint.json` 的 url+token，新增 `GET /recall` | 新扩展 `extensions/kalo-recall/`，出一个 `recall` 工具 |
| 桌面 UI | 已有 NDJSON：`{cmd:"recall", requestId, ...}` → `{type:"recall_reply"}` | Rust 侧转发命令 + 前端搜索面板 |

**不新建第二个 endpoint 文件**——同一个 server 加一条路由就够了。

模型侧只出**一个**工具 `recall`，`promptSnippet` 写清楚三个 scope 各是什么。`memory_search` 的收敛分两步：先让 `recall` 上线跑一阵，确认召回不比它差，再把 `memory_search` 改成 `recall(scope:"memory")` 的薄壳并标记 deprecated。**不在同一次改动里拆掉它**——记忆是用户资产，退路要留着。

技能里手写的 `rg` 命令同理，等 `recall` 稳定后再改提示词；`rg` 永远保留作为无索引时的兜底。

## UI

侧边栏「搜索」按钮接上，打开一个搜索面板（不是新页面，overlay）：

- 输入即搜（250 ms 防抖），结果按 scope 分组：会话 / 记忆 / 知识。
- 会话命中：项目 cwd + 会话标题 + 时间 + 高亮片段；点击 → 打开那个会话，并**滚动定位到命中的那条消息**（`seq` 就是行号，`buildTimeline()` 重建时能对上）。
- 记忆/知识命中：点击 → 打开对应的编辑弹窗（`MemoryEditModal` / `KnowledgeEditModal` 已存在）。
- 快捷键 `Ctrl/Cmd+K`。
- 短词降级时在结果上方一行小字说明。

## 边界情况

- **网关没跑**：模型侧 `recall` 报「检索服务不可用」（与 `job_*` 同一套文案）；UI 侧搜索面板显示同样的提示，不静默返回空结果。
- **索引正在建（首次）**：46 个会话 1.6 MB，首建是秒级，不做进度条；但对账超过 2 秒的话返回一个 `building: true`，UI 显示「正在建立索引」。
- **schema 升版**：`user_version` 不匹配 → 整库重置重建。索引是可丢弃的，不做迁移。
- **陌生库**：`~/.kalo/index.sqlite` 存在但 `application_id` 不是 KALO，或有不认识的表 → **拒绝并报错，绝不动它**。
- **权限**：POSIX 上以 0o600 创建（Windows 无意义但代码一致）。
- **删除会话**：`delete_session` 后应触发一次对账（或等下次查询自然发现文件没了）。
- **搜索结果泄漏**：索引里有会话全文，即用户的一切。它和会话日志同权限、同目录树下，不新增暴露面；但**绝不能进备份/同步的默认清单**，文档里标注可安全删除。
