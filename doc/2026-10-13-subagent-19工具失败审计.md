## 长期陷入重复的原因及不确定性

**记录直接证明：**首次空参数错误后曾补齐参数恢复成功（L38–L46），工具并非全程不可用；L47 之后 339 次调用全部失败（263 次互斥错误 + 76 次空 bash），无成功调用、无 job_output、无新的执行证据。错误每次明确要求 Drop timeout，后续却始终保留该字段或退化为空对象，错误反馈没有转化为有效调用。调用/回执持续增加，形成“有活动但无进展”，最终没有自动收敛而由 abort 结束。J 中没有 compaction 事件。

**尚不能确定：**空对象由模型生成、流式组装还是适配转换造成；timeout=0 是否被自动补默认值；模型实际收到的 schema 是否错误要求该字段。这需要请求原文或参数转换阶段的证据。不能只凭落盘参数归因某个模型或适配器缺陷。

“只认活动、不认进展的监控”与现象相符，但未核验 watchdog 实现/配置，不能指定某段代码为根因。开头三次过载之后已经成功执行工具，也不能把一小时重复的确定性参数错误归咎于过载。

## 审计时提出的可修复点与验收要求

以下保留审计时的问题与建议；后续已实现范围见文末，不代表全部建议均已落地。

1. **统一 schema、模型可见说明和运行时互斥语义。** 后台 timeout 应可省略，明确 0/null 的无超时语义与正数限制，转换层不得引入改变含义的默认值；前台模式单独校验。后续源码确定：后台缺省/null/0 均为无超时，正数继续拒绝，前台 0 仍非法。Windows/macOS 字段语义保持一致。
2. **确定性参数错误采用有限恢复预算。** 同工具、同规范化参数、同错误码连续复现时，终止该子任务并向父会话返回阻塞原因。不要把正常文件重读或 job 状态查询误判成失败循环；终止也要持久化回执。
3. **把进展与活动分开。** 成功执行或新证据推进进展计时；不断收到 schema 拒绝不应无限延长任务。增加连续失败次数、无进展时长与 token 预算的观测和停止策略。
4. **定位空参数与默认值来源。** 关联 provider 响应、解析后 toolCall、验证前参数，仅存脱敏字段集合、空对象标记及哈希。当前不能凭 JSONL 指认某一层损坏。
5. **状态和 token 分层呈现。** 区分执行前拒绝、命令退出失败、执行超时、模型过载和取消；input/output/cacheRead 分开展示。350 步或 token 增长不能替代任务进展。
6. **命令引用与资源收尾单独验证。** 外层契约修好后检查带空格路径、重定向及管道退出状态；临时资源启动后应能在超时和取消时定位并清理。脚本未启动时不得报告迁移验收通过。

优先修字段契约与重复失败终止机制，再定位空参数来源。业务迁移正确性应由父会话后续真实验证另行判断。审计与本轮文档同步均未修改业务代码。
