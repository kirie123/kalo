# ask_user：让模型主动向用户提问

## 问题

kalo 的 agent 遇到「必须由人决定」的岔路时，没有结构化的暂停方式。今天只有两条路，两条都不好：

1. **模型输出一段文本然后停。** 例如它写「你是要我改现有的 `chat-store.ts`，还是新建一个 lib 文件？」然后结束这一轮。用户下一条消息是**一个新的 user prompt**，不是「那次决策的结果」——模型要靠上文自己拼回去；选项没有任何结构（前端无法渲染成按钮），用户得手打「新建 lib」；如果模型同时想问三件事，它只能写成一段散文，用户回一段散文，双方都在猜。
2. **扩展调 `ctx.ui.select` / `ctx.ui.confirm`。** 这是给扩展写的对话框（例如危险命令确认），不是给模型的能力：模型不能调用它；单问题、选项只有一个字符串（没有说明文字）、不能多选、不能填自由文本；最要命的是**无 UI 时它静默返回默认值**（`select` → `undefined`，`confirm` → `false`），对确认框是合理的降级，对「问用户要哪个方案」就是拿一个凭空的答案继续往下跑。

具体的坏例子：用户说「把指标提取那套东西接进来」。合理的做法是先问「接成内置 skill 还是独立扩展？」「要不要顺带把 7 张规则表也搬过来？」——两个问题、每个 2~3 个选项、都有一句说明。现在的引擎做不到，模型只能选一条自己猜，或者停下来写一段话让用户重新组织需求。

本文档定义 `ask_user` 工具：一个面向模型的暂停原语，把「问人」变成一次普通的工具调用——调用时挂住，用户答完，答案作为工具结果回到 agent loop。

## 设计

### 1. 分层：能力接缝 / 面向模型的工具 / 前端提供方

三层，各自的职责边界写死：

```
ask-user 扩展（面向模型）        registerTool("ask_user")，校验参数与答案
        ↓ 调用
ExtensionUIContext.askUser（接缝）  提供方无关的请求/应答/错误词汇
        ↓ 由具体模式实现
rpc-mode 提供方（面向前端）        编码成 extension_ui_request，等 extension_ui_response
        ↓ NDJSON
桌面端 AskUserPanel（收集答案）     渲染问题、收集选择、回传一批答案
```

接缝层存在的理由：工具不该知道自己跑在 TUI、桌面端还是别的前端；前端不该知道模型 schema 长什么样。两边只共享「一批问题 → 一批答案」这个词汇。

### 2. 为什么不复用 `ctx.ui.select`

逐条列出差异，这些就是必须新建一条通道的原因：

| 需求 | `ctx.ui.select` | `askUser` |
|---|---|---|
| 一次问多个问题 | 不支持 | 支持（1~5 个） |
| 选项带说明文字 | 只有 label 字符串 | `{ label, description }` |
| 多选 | 不支持 | `multiSelect` |
| 自由文本「其他」 | 要另开一次 `input` | 同一次请求内的 `custom` |
| 稳定 id 回传 | 无（靠标题文本对齐） | 每问 `id`，答案里回传 |
| 无 UI 时 | 静默返回 `undefined` | **fail-fast 报错** |
| 答案进不进时间线 | 不进（对话里看不到问过什么） | 进（工具结果气泡） |
| 错误分类 | 无 | 稳定错误码 |

最后一条「无 UI 时 fail-fast」是关键：`ctx.ui.select` 在没有前端的会话里返回 `undefined`，扩展把它当「用户取消」处理，没问题。但模型问「删哪个目录」的时候，一个凭空的 `undefined` 会被工具翻译成某个默认选项，然后它真的去删。所以 `askUser` 在没有提供方时抛错，不返回默认值。

### 3. 接缝：`ExtensionUIContext.askUser`（可选方法）

在引擎的 `ExtensionUIContext` 上新增**可选**方法，纯增量：

```ts
/** One selectable answer offered to the user. */
export interface AskUserOption {
	/** User-facing label. Also the value returned to the model — there is no separate value field. */
	label: string;
	/** One sentence explaining the tradeoff or impact. */
	description?: string;
}

/** One question in an ask-user request. */
export interface AskUserQuestion {
	/** Stable question id, echoed in the answer. */
	id: string;
	/** The full question text. The only free-text slot: supporting detail belongs in option descriptions. */
	question: string;
	/** Short category tag, e.g. "鉴权" / "代码风格". Never a substitute for `question`. */
	header?: string;
	/** Choices the UI renders as a menu. Absent means free-text only. */
	options?: AskUserOption[];
	/** Whether more than one option may be selected. Defaults to single-select. */
	multiSelect?: boolean;
}

/** Answer to one question. */
export interface AskUserAnswerItem {
	/** The answered question id. */
	id: string;
	/** Selected option labels. Always an array, even for single-select. */
	selected: string[];
	/** Free-text "other" answer. */
	custom?: string;
}

export interface AskUserRequest {
	questions: AskUserQuestion[];
	signal?: AbortSignal;
}

export interface AskUserContext {
	/**
	 * Ask the user and wait for the answer batch.
	 * Absent on surfaces that cannot collect structured answers.
	 */
	askUser?(request: AskUserRequest): Promise<{ answers: AskUserAnswerItem[] }>;
}
```

`askUser` 声明为可选的原因：`ExtensionUIContext` 有四个实现（TUI、RPC、print/noOp、测试替身），只有 RPC 模式在本期实现它。可选方法让另外三个不动就能编译，工具侧用 `if (ctx.ui.askUser === undefined) throw` 给出明确错误，而不是拿到一个假装成功的桩。

**答案编码不变量**（前后端都必须遵守，是这条通道的核心契约）：

- `selected` 恒为 label 数组。单选也是数组（长度 0 或 1），这样单选/多选的答案是同一种形状，消费方不分支。
- 没有独立的 `value` 字段。label 既是给人看的文本，也是回给模型的值。多一个 `value` 就多一次「模型看到的和用户点的不是同一个东西」的机会。
- `custom` 是自由文本。**单选**问题里 `custom` 与 `selected` 互斥（有 custom 则 selected 为空）；**多选**问题里两者可共存（勾了两个选项再补一句说明）。
- 没有 `options` 的问题只收 `custom`。
- `{ id, selected: [] }` 且无 `custom` = **这一问被显式跳过**。不需要新词汇表达跳过。
- 不引入「推荐项」字段。想推荐就把它放第一个并在 label 里写「（推荐）」——前端不自动勾选任何选项，避免用户一路回车把模型的偏好当成自己的决定。

不引入展示意图（intent）字段：kalo 目前没有 plan 模式之类需要专门渲染的决策。答案编码与展示方式无关，将来要加富展示只影响渲染，不动协议。

### 4. 面向模型的工具：`ask_user`

新建内置扩展 `kalo-harness/packages/coding-agent/src/extensions/ask-user/index.ts`，注册进同目录 `index.ts` 的 `builtInExtensions`（hidden）。

**工具名用 `ask_user`，不是 `ask_user_question` 也不是 `AskUserQuestion`。** `packages/ai/src/api/anthropic-messages.ts` 有一张 stealth 映射表（`claudeCodeTools`），OAuth token 路径下会把工具名按**小写匹配**改写成 Claude Code 的规范大小写，表里含 `AskUserQuestion`。叫 `ask_user_question` 会被改写成 `AskUserQuestion` 发出去，而回来的 tool_call 名字要靠反查还原，多一层不必要的耦合。`ask_user` 不在表里，原样透传。（`todo_write` 当初避开 `TodoWrite` 是同一个原因。）

参数 schema（TypeBox，与接缝类型一一对应，蛇形命名给模型）：

```ts
const AskUserParams = Type.Object({
	questions: Type.Array(
		Type.Object({
			id: Type.String({ description: "本问的稳定 id，答案里会原样回传。" }),
			question: Type.String({
				description: "完整的问题正文，必填，以问号结尾。补充说明写进选项的 description，不要另起字段。",
			}),
			header: Type.Optional(Type.String({ description: "分类标签，最多 12 字……它只是个标签，不能代替 question。" })),
			options: Type.Optional(
				Type.Array(
					Type.Object({
						label: Type.String({ description: "简短选项文本；这也是回传给你的值。" }),
						description: Type.Optional(Type.String({ description: "一句话说明这个选项的代价或影响。" })),
					}),
					{ description: "给用户选的选项。推荐某项就放第一个并在 label 里写「（推荐）」。" },
				),
			),
			multi_select: Type.Optional(Type.Boolean({ description: "是否允许多选，默认单选。" })),
		}),
		{ description: "本次要问的问题，1~5 个。" },
	),
});
```

**一个问题只给一个自由文本位。** 早期版本除了 `question` 还有个 `detail`，结果是一条反复出现的失败：模型把整个问题写成 `header: "后端跑不起来"` ＋ `detail: "本机只有 Python 3.10.0a5……"`，主观上认为问题已经表达完整，于是省掉了必填的 `question`。schema 校验在 `execute` 之前就把**整批四个问题全部拒掉**，报错还会回显全部原始参数（实测约 2KB），白烧一个往返。三个都像「问题正文」的字段放在一起，模型必然会挑错位置。现在：

- `detail` 从工具契约里删除，补充说明只能写进选项的 `description`；
- `header` 约束为最多 12 字的分类标签（并在校验里强制），长度上就承载不了一句话；
- `question` 的描述写明「必填、以问号结尾」，工具 description 里再声明一次 `header` 不能代替它。

### 5.1 `prepareArguments`：兜底而不是报错

结构上收窄字段是主手段，但旧习惯不会一天消失。`extensions/ask-user/normalize.ts` 提供一个纯函数 `normalizeAskArguments`，挂在工具的 `prepareArguments` 上，**跑在 schema 校验之前**（`agent-loop.ts` 先 `prepareToolCallArguments` 再 `validateToolArguments`）：

| 模型写成 | 兜底后 |
|---|---|
| 只有 `header` + `detail`，无 `question` | `question = header + "\n" + detail`，并删掉 `header`（否则同一句话渲染两遍） |
| 有 `question` 又多给了 `detail` | `detail` 拼接到 `question` 末尾换行，不丢字 |
| 缺 `id` 或 `id` 为空白 | 按位置合成 `q1` / `q2`（答案本就按顺序校对，合成 id 和模型写的等效） |
| 一个问题里没任何问题形状的文本 | 原样放行，让校验报真正的错 |

它只搬运模型已经写下的文字，不凭空造问题、不造选项、不造答案。同一个契约里 `grep` 工具把弱模型爱写的 `query` 兜底成 `pattern`，是同一种做法。

`executionMode: "sequential"`：一次 assistant 轮次里模型可能并行发多个工具调用，两个提问同时弹窗会互相抢焦点。串行执行让第二次提问必然在第一次答完之后开始，前端因此**永远只需要处理一个 pending 提问**，不需要队列。

**入参校验（schema 表达不了的，在 execute 开头抛错）：**

| 规则 | 理由 |
|---|---|
| `questions` 长度 1~5 | 空批次没有意义；一次十几问是模型在偷懒，让用户替它做整套设计 |
| `id` 非空且批内唯一 | 答案靠 id 路由 |
| 每问 `options` ≤ 6 个 | 超过就不是选择题了 |
| `label` 非空、单问内唯一、≤ 40 字符 | 重复 label 无法区分选择；长 label 是把说明写错了位置（该用 `description`） |
| `question` 非空 | — |
| `header` ≤ 12 字符 | 长 header 就是模型把正文写错了位置，正是当初整批失败的那种形状；报错文案直接叫它把正文挪进 `question` |

抛错走 `isError` 工具结果，模型看得到原因，能在下一步自己修正。

**返回值：**

```ts
{
	content: [{ type: "text", text: JSON.stringify({ answers }) }],
	details: { questions, answers } satisfies AskUserDetails,
}
```

`content` 是给模型的（JSON，机器可读，不用它去解析散文）。`details` 带上**原问题 + 答案**，因为它会随 toolResult 进 session jsonl 并原样送到桌面端，前端据此把「问了什么 / 用户选了什么」渲染成气泡；历史重放走同一条路，resume 一个会话也能看到当时的问答。这与 `todo_write` 用 `details` 承载状态是同一套做法：引擎侧不留内存状态，`execute` 只做校验和转发。

**错误码（稳定分类，错误文本里带上码）：**

| 码 | 触发 | 给模型的指引 |
|---|---|---|
| `NO_ASK_CHANNEL` | 当前界面没有 `askUser` 提供方 | 当前界面无法向用户提问；自己作出最合理的选择并在答复里说明取舍，或把待决问题写进最终答复 |
| `ASK_CANCELLED` | 用户主动关掉提问，选择直接说话 | 用户不想回答这些问题，改为等他说；不要重复提问，停在这里 |
| `ASK_ABORTED` | 本轮被中止（用户点停止、引擎退出、提供方释放） | 提问未完成 |
| `BAD_ANSWER` | 前端回传的答案批次不合规 | 提问通道返回了不合规的答案，重试一次或换个问法 |

`ASK_CANCELLED` 单独成一类而不是复用 abort，因为它对模型的含义完全不同：abort 是「这一轮不要了」，cancel 是「问题我不答，但对话继续，你别再弹了」。把两者混成一个错误，模型会在用户关掉弹窗后立刻再问一遍。

**prompt 引导**（`promptSnippet` + `promptGuidelines`，没有 `promptSnippet` 的自定义工具不会出现在系统提示词的工具清单里）：

- `ask_user(questions)` — 需要用户确认、选择或补充信息时提问，答案作为工具结果返回
- 能自己查清的事不要问（读文件、跑命令能确定的，先去做）
- 一次问完相关的几个问题（≤5），不要连续弹多次
- 尽量给选项并为每个选项写一句代价说明；没有合适选项时才留自由文本
- 用户取消提问后不要重新提问，停下来等他说话

### 5. 子 agent 与无人值守会话：不给这个工具

有人在场，才有人能回答。两种没人在场的情况必须让工具**不存在**，而不是让它挂住：

**子 agent（`agent` 工具）。** 子会话是一次性委托，父调用在等它的最终答复；子会话里若有一次提问挂住，父调用一起卡到 10 分钟看门狗超时。现有实现已经天然隔离：子会话用 `noExtensions: true` 创建，只显式注入 `webfetch` 扩展，因此 `ask-user` 扩展不加载，`ask_user` 工具不存在；即便调用方在 `tools` 里显式写了 `ask_user`，注册表里也没有这个名字，工具直接报「不存在」。同时子会话没有绑定 `uiContext`，`ctx.ui` 是 noOp 实现，`askUser` 为 `undefined` —— 两道都不通。本设计只需**保持**这个性质：`DEFAULT_TOOLS` 不加 `ask_user`，子会话的注入扩展清单不加 `ask-user`。

子 agent 遇到需要人决定的岔路时，约定是把未决问题写进最终答复；父 agent 拿到后可以自己调 `ask_user`。这条约定写进 `agent` 工具的描述里，因为「向上转发提问」这条通道并不存在，不能让模型以为有。

**无人值守会话（定时任务 / IM 渠道）。** 桌面端和 gateway 都用 `pi --mode rpc` 起引擎，进程形态一样，但定时任务背后没有人盯着屏幕。区分方式：spawn 时传环境变量 `KALO_UNATTENDED=1`，由 gateway 的会话创建路径设置（`gateway.rs` 里 `process.source = "gateway"` 的那条路径）；`ask-user` 扩展启动时读它，为真则**不注册工具**。

为什么用环境变量而不是 RPC 命令：工具清单参与系统提示词前缀，注册必须发生在第一次请求组装之前；环境变量在 spawn 时就定了，没有时序窗口。Windows 下 `Command::env` 传子进程环境变量与 POSIX 行为一致，本处无平台差异，但环境变量名统一大写、只用 ASCII，避免 Windows 环境块的大小写不敏感带来意外覆盖。

IM 渠道（飞书）本期归入无人值守：那一端确实有人，但答案要走飞书卡片回传，属于另一条通道，本期不做。渠道会话的模型因此看不到 `ask_user`，行为退化为「把待决问题写进答复」，用户在飞书里看到问题后自己回一句。gateway 的进度渲染器不需要改动。

### 6. RPC 契约：复用 extension_ui 通道，新增一组变体

引擎与桌面端之间已有 `extension_ui_request` / `extension_ui_response` 这条带 id 关联的请求-应答通道（pending 表在 `modes/rpc/rpc-mode.ts`，前端在 `chat-store` 分发）。`askUser` 复用它，只加变体，不新开通道，也不新增 Tauri 命令（回传继续走既有的 `sendRawCommand` → `send_command`）。

**请求（引擎 → 桌面端）：**

```ts
| {
		type: "extension_ui_request";
		id: string;
		method: "ask_user";
		questions: AskUserQuestion[];
  }
```

**应答（桌面端 → 引擎），两个变体：**

```ts
| { type: "extension_ui_response"; id: string; answers: AskUserAnswerItem[] }
| { type: "extension_ui_response"; id: string; cancelled: true }   // 已有变体，复用
```

`cancelled: true` 复用既有变体：用户关掉提问卡与关掉别的扩展对话框在协议上是同一件事，区别只在引擎侧怎么翻译（这里翻译成 `ASK_CANCELLED` 抛错，而不是返回默认值）。

**rpc-mode 侧的提供方实现，与既有对话框的三点差异：**

1. **不用 `createDialogPromise`。** 那个辅助函数的语义是「取消 / 超时 / abort 都 resolve 成默认值」，对 `askUser` 全错。`askUser` 自建 pending 项：正常答案 resolve，`cancelled` reject `ASK_CANCELLED`，signal abort reject `ASK_ABORTED`。
2. **不设默认超时。** 人可能离开工位十分钟。要停就用既有的中止路径（用户点停止 → 本轮 signal abort → 提问 reject `ASK_ABORTED`），不靠计时器猜。
3. **答案批次在引擎侧校验。** 见下条。

**校验放引擎侧，不放前端。** 前端是可替换的不受信输入源（今天是桌面端，明天可能是别的客户端，也可能是手工注入的一行 NDJSON）。校验一次写在引擎，每个前端都不用重复实现，也不会各自实现出不同的宽松度。抽成纯函数 `validateAskUserAnswers(questions, answers)`，规则：

- 答案条数等于问题条数，且按顺序 id 一致（顺序一致意味着不需要建 map 做乱序匹配，也让「少答一问」无法伪装成「答了别的问」）
- `selected` 里每个 label 必须出自**这一问自己的** options
- `selected` 内部无重复
- 单选问题：`selected` 长度 ≤ 1，且 `custom` 与 `selected` 不同时非空
- `custom` 去空白后不得为空串（想跳过就别带 custom）

任一条不满足 → reject `BAD_ANSWER`。不做「尽力修正」：静默修正会让一个前端 bug 变成用户看不见的错答案。

**pending 提问的生命周期：**

- 引擎进程退出 → pending 提问随进程消失；前端在引擎退出处理里清掉本地 pending（见 §7）
- 本轮中止 → signal abort → reject `ASK_ABORTED`（前端同时清 pending）
- 前端重复应答 / 迟到应答 → pending 表里已删除，命中不到，静默丢弃（先到者胜）

### 7. 桌面端：输入区接管，不用模态

**渲染位置：输入区上方接管，不是居中模态。** 理由是回答这些问题往往需要回看上文（「你是要改 A 还是 B」——用户得先滚上去看 A 是什么）。模态盖住对话内容，等于强迫用户凭记忆决策；而且提问是对话的一部分，答案该留在时间线里，不该是一个弹一下就消失的窗口。既有的 `ExtensionModal` 服务的是扩展的短确认（危险命令 yes/no），保持不变。

**交互规格：**

- 一次显示一个问题（`第 2/3 问` 的进度指示），答完自动进入下一问
- 单选：点选项即选中并前进；多选：勾选后按「下一步 / 提交」
- 「其他…」展开为输入框；无 options 的问题直接显示输入框
- 「跳过本问」只跳过当前一问（编码为 `selected: []`），保留已答的
- 最后一问答完 → 提交整批
- 提问未结束时普通输入框禁用，但保留一个出口「我直接说」→ 发 `cancelled: true`，输入框恢复
- **接管的那一刻必须关掉输入区的斜杠/@ 补全弹层**：它绝对定位在输入卡上方（`bottom-full`），位置正好压在问题卡上；而禁用后的 textarea 收不到任何 change/select/key 事件，token 再也无法重算，弹层会永久留在屏幕上——用户看不见选项，也点不动输入框。补全弹层另外补一个「点输入区之外即关闭」的出口，避免同类卡死（`InputBox.tsx`）
- **不预选任何选项**，包括模型标了「（推荐）」的那个
- 中文输入法组字期间的回车只确认候选词，不提交（否则打拼音选词会误触提交）

**状态与分层。** `chat-store.ts` 目前 1989 行，已超行数基线，不允许再涨：

- 纯逻辑放新文件 `kalo-desktop/src/lib/ask-user.ts`：一个提问会话的状态机（当前问索引、每问的选中集合与 custom 草稿、推进/跳过/切换选项、能否提交、编码成 `AskUserAnswerItem[]`），以及一份与引擎侧同规则的答案自检（提交前先自查，不合规就不发，避免一次白跑的 `BAD_ANSWER`）。无 IPC、无 DOM。
- `chat-store.ts` 只加：`pendingAsk: AskUserPrompt | undefined` 状态字段、`extension_ui_request` 分发里 `method === "ask_user"` 的一个分支、`respondAsk(answers)` / `cancelAsk()` 两个薄方法（调 `sendRawCommand`）。
- 展示放 `kalo-desktop/src/components/AskUserPanel.tsx`，无业务状态，只驱动 `lib/ask-user.ts` 的状态机并回调。
- 时间线气泡：`ToolCallGroup.tsx` 加 `ask_user` 分支，从 `details` 读 `{ questions, answers }`，折叠态显示「向你提了 2 个问题」，展开显示每问与所选。

**后台会话（parked runtime）。** 提问挂在**发起它的那个 runtime** 的视图上，不是全局的；非活跃 runtime 收到提问时推一条 toast「后台会话在等你回答，切过去处理」。这与既有 `extensionQueue` 的处理一致。

**引擎退出。** 在既有的引擎退出处理里清空 `pendingAsk`：那次提问的对端已经不在了，留着一张答不出去的卡片只会骗用户。崩溃自动恢复重放的是磁盘上的会话，pending 提问不在磁盘上，不会复活。
