# 会话标题重命名

日期：2026-08-20
状态：方案（待实现）

## 现状

标题的展示链路分两段：

**1. 侧边栏标题**（`kalo-desktop/src-tauri/src/sessions_store.rs`）
`list_sessions` 扫 `%USERPROFILE%/.kalo/agent/sessions/<encoded-cwd>/*.jsonl`，每个文件：
- 读第一行 header（`type:"session"`）
- 扫前 100 行找 `session_info` / `session_name` 条目的 `name`，**取第一条非空**
- 没有则取第一条用户消息文本，截断 80 字
- 都没有则 "Untitled session"

**2. 标题栏标题**（`App.tsx` `barTitle`）
`chat.sessionName || cwdBasename(chat.cwd) || "Kalo"`，`sessionName` 来自引擎的 `get_state` 和 `session_info_changed` 事件。

**引擎侧能力已齐**（`kalo-harness/packages/coding-agent/`，无需改动）：
- RPC `set_session_name { name }`（`rpc-mode.ts:657`）→ `agent-session.setSessionName` → `sessionManager.appendSessionInfo(name)` 写一条 `session_info` 条目 → 触发 `session_info_changed` 事件
- 前端 `types.ts` 的 `RpcCommand` 已含 `set_session_name`，`PiEvent` 已含 `session_info_changed`，chat-store 已处理该事件（更新 `rt.sessionName` 与 pending 行标题）
- 引擎语义：`getSessionName()` 取**最后一条** session_info 的 name；空名 = 清除标题；RPC 层拒绝空名

## 缺口

1. **无 UI 入口**。侧边栏 `...` 菜单只有「删除会话」，标题栏标题不可编辑，无任何改名入口。
2. **历史会话无法改名**。改名必须走 `set_session_name` RPC，而历史会话没有活跃引擎；为改名起一个引擎进程代价过高。
3. **扫描与引擎语义不一致**。`sessions_store.rs` 取**第一条** session_info，引擎取**最后一条**——改两次名后侧边栏显示旧名。
4. **扫描只读前 100 行**。长会话后期改名，`session_info` 条目落在 100 行之外，扫描不到。
5. **空名边缘 bug**。`name = Some("")` 不会被 `.or()` 跳过，结果空标题（应回退到首条用户消息）。

## 目标与非目标

目标：
- 三种会话状态都能改名：活跃会话（引擎在池）、pending 会话（引擎已开未落盘）、纯历史会话（仅磁盘文件）
- 改名即时生效：侧边栏行、标题栏、下一次磁盘扫描三者一致
- 写入的条目与引擎 schema 完全一致，引擎重开会话时正常读取

非目标：
- 不提供「恢复默认标题」（引擎 RPC 拒绝空名；两条路径保持一致，UI 层拦截空输入 = 取消改名）
- 不改引擎、不改 gateway
- 自动命名（LLM 生成标题）不在本期

## 方案

### 1. 入口

**P0：侧边栏 `...` 菜单加「重命名」**（`Sidebar.tsx` `SessionMenu`，位于「删除会话」上方）。点击后行内就地编辑：标题文本变成 `<input>`，Enter 提交 / Esc 取消 / 失焦提交。pending 行也开放重命名（其 runtime 在池中，走活跃分支）。

**P1（可选增强）：标题栏标题可点编辑**。`barTitle` 在 chat 页时渲染为可点击/可编辑标题，复用同一提交逻辑。不阻塞 P0。

### 2. 执行路径（按会话状态三分）

统一入口 `chatStore.renameSession(path, name)`，内部按 runtime 是否在池中分派：

```
renameSession(path, name)
 ├─ 池中有 runtime（活跃 / pending）→ sendCommand(sessionId, {type:"set_session_name", name})
 │     └─ 引擎写 session_info + 广播 session_info_changed
 │           ├─ store: rt.sessionName / rt.pending.title 更新（已有逻辑）
 │           └─ 磁盘扫描自然读到新名
 └─ 纯历史会话（无 runtime）→ invoke("rename_session", { path, name })  [新增 Rust command]
       └─ 成功后调用现有 refreshProjects（App 已用 listSessions 刷新侧边栏）
```

- **活跃/pending**：复用 `set_session_name` RPC，类型和事件处理都在，不动引擎。唯一要补的是 chat-store 暴露 `runtimeForFile(path)`（`normPath` 匹配，语义同现有 `runningByFile` 身份稳定化）。
- **历史会话**：新增 Rust command `rename_session(path, name)`，直接向 `.jsonl` **追加**一条与引擎一致的 `session_info` 条目，不起引擎。追加而非改行：保持文件 append-only 特性，与引擎 `_persist` 的写入方式一致，也避免重写大文件。

### 3. 新增 Rust command：`rename_session`

位置：`sessions_store.rs` + 注册进 `main.rs` 的 `generate_handler!`（仿 `delete_session`）。

```rust
#[derive(Serialize)]
struct RenamedSession { /* 无返回值需求，Result<(), String> 即可 */ }

fn rename_session(path: &str, name: &str) -> Result<(), String>
```

步骤：
1. **校验**：复用 `delete_session` 的路径安全逻辑（canonicalize 后在 sessions root 内、`.jsonl` 后缀）。`name` trim 后非空，否则报错（与引擎 RPC 一致）。
2. **读最后一条 entry**：打开文件，定位最后一条 JSON 行的 `id` 作为 `parentId`（当前 leaf）。若文件只有 header 无条目，`parentId` 省略。
3. **生成新条目 id**：与引擎同款——`randomUUID` 取前 8 位 hex；扫一遍现有 id 集合去重（rename 是低频操作，全读一次可接受，正好一并拿到 parentId）。
4. **追加**：`OpenOptions::new().append(true)`，写一行与 `SessionInfoEntry` schema 一致的 JSON：

```json
{"type":"session_info","id":"<8hex>","parentId":"<lastId>","timestamp":"2026-08-20T12:00:00.000Z","name":"<name>"}
```

引擎加载时按行解析 entries，`getSessionName` 取最后一条——与侧边栏修正后的扫描一致。

并发说明：活跃会话必走 RPC（其文件可能正被引擎写），`rename_session` 只处理无 runtime 的文件，天然不冲突；追加用单次 write，正常路径下原子。

### 4. `sessions_store.rs` 扫描修正

`parse_session_file` 三处小改：

1. **名字取最后一条**：遍历时对 `session_info` 的 name 做**覆盖写**（`name = Some(n)`），遍历结束取到的是最新一条——与引擎 `getSessionName()` 语义对齐。`first_user_text` 仍取第一条用户消息。
2. **名字扫描放宽到全文件**：`session_info` 条目数量极少，改名可发生在任意位置；`first_user_text` 保留前 100 行优化，避免为大会话兜底标题多读全文件。实现：同一遍遍历，100 行内两种都找，100 行后只更新 name。
3. **空名跳过**：`session_info` 的 name 为 `Some("")` 时视为未设置，继续走 `first_user_text` 兜底（修复空标题 bug）。

### 5. 边界情况

- **改名进行中引擎退出**：RPC reject → toast 报错，行内编辑恢复原值（仿现有 prompt 失败处理）。
- **pending 行改名**：runtime 在池中，走 RPC；`session_info_changed` 更新 `rt.pending.title`（已有逻辑），落盘后磁盘行自带新名。
- **改名后立即打开该历史会话**：引擎按行加载 entries，最后一条 session_info 即新名，无状态不一致。
- **清空输入**：UI 层拦截（Enter 空串 = 取消），与引擎「拒绝空名」一致；不做「恢复默认」。

## 验证

- Rust：`rename_session` 路径安全（root 外 / 非 jsonl 拒绝）、空名拒绝、追加条目 schema 与引擎一致、parentId 正确、对 header-only 文件可用。
- 前端：改名三种状态分派正确（池中 / pending / 历史）；`session-rows` / chat-store 单测补充 rename 相关用例。
- 手工：活跃会话改名 → 行与标题栏即时更新；历史会话改名 → 侧边栏刷新即新名；长会话后期改名 → 重启 App 后仍显示新名；改两次名 → 显示最新名；引擎重开改名后的会话 → 标题一致。
- `tsc --noEmit`、`npm test`、`cargo check` 通过。
