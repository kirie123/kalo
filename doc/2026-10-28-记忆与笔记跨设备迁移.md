# 记忆与笔记跨设备迁移

日期：2026-10-28
状态：首版已实现；手动导出、导入、安全合并与撤销已接入。原生重启和文件对话框、macOS 实机验收尚待完成，自动同步另行设计。下方实施补充和文末记录描述本次交付边界。

## 实施约束补充（2026-10-28）

- 维护模式采用「准备迁移 → 用户结束任务并正常退出 → 下次启动进入数据管理」。不在普通运行中强制停止引擎；数据预检、导出和导入全部在维护窗口执行。返回普通模式时重启应用。维护标记持续保留，异常退出后不会意外启动后台任务。
- 独占数据目录锁由正常与维护模式共同持有；未完成事务使下次启动自动进入维护模式，恢复失败时禁止退出维护模式。
- 首版对缺失附件、外部文件、无法安全改写的本地引用采用阻止导出并定位的方式。用户先修复或移入个人附件目录再重试；不提供带缺失内容的部分包。正文中的普通路径和网页链接不属于附件收集对象。
- 活跃记忆冲突默认暂存；笔记可保留两份、保留本机或替换。冲突展示原文，支持比较完整 Markdown；不调用模型合并。
- 取消发生在预览阶段；提交阶段禁止离开，失败自动回滚。关闭窗口或进程异常退出由持久化日志恢复。备份不自动清理。
- 资料包不保存单独的 references 数组：导入时从原始 Markdown 重新解析引用并检查目标，避免信任清单中的第二份引用关系。导出时间字段为 `exportedAtMs`（UTC Unix 毫秒）。
- 资料包路径、隐含父目录及本机目标均检查大小写和 Unicode 碰撞。遇到碰撞直接定位并要求先改名；首版不自动转换非法文件名。路径最多 64 段、每段最多 255 UTF-8 字节；Markdown 单文件最多 16 MiB。
- 冲突记忆保存在 `transfers/conflicts/<事务>/memory/`，迁移记录显示位置；用户可在文件管理器查看，再通过记忆设置手动编辑生效。首版没有内嵌的记忆合并编辑器。
- 导出文件不覆盖同名备份。支持硬链接的磁盘通过同目录临时文件发布；FAT/exFAT 等不支持硬链接的磁盘采用独占新建并复制，成功提示前必须完成刷盘。这类磁盘在进程被强制终止时可能留下不完整的新包，导入校验会拒绝，不影响原文件。

## 1. 产品决策

提供一个可携带的「Kalo 个人资料包」，扩展名 `.kalo-data.zip`。用户在设备 A 导出，通过自己的文件传输方式带到设备 B，在 Kalo 内预览后导入。无需账号、服务器或模型调用，离线可完成。

首版以「合并到本机」为唯一导入模式：新增内容直接加入，重复内容跳过，冲突由用户决定，包中没有的本机内容保留。它适合换机、备份和偶尔往返传递；不承诺自动同步、传播删除或识别所有重命名。

入口放在「设置 → 数据管理」，提供「导出记忆与笔记」「导入资料包」「迁移记录」。笔记页与记忆设置页提供跳转入口，不各实现一套搬迁逻辑。

## 2. 当前实现与需要补齐的部分

以下结论以当前代码为准，未落地的历史设计不视为已有能力。

| 数据 | 当前实现 | 对迁移的影响 |
| --- | --- | --- |
| 个人记忆 | `memory.rs` 与引擎 memory 扩展读写 `~/.kalo/memory/<slug>.md`；包含 title、tags、created、updated 与正文 | 直接保存文件和未知 frontmatter 字段，避免经现有编辑接口重新序列化而丢字段 |
| 笔记 | `knowledge.rs` 读取 `~/.kalo/knowledge/`；目录决定分类，`_types/` 保存分类展示信息 | 保留分类结构、空分类目录和分类描述 |
| 图片 | `notes/images.ts` 通过 `save_attachment_bytes` 写入共享 `~/.kalo/attachments/`；正文使用绝对路径 | 必须收集被引用的附件，将包内引用改为相对路径 |
| 未保存内容 | `useNoteDocument.ts` 有串行保存队列与 localStorage 草稿 | 导出前需要保存并排空队列，不能只压缩磁盘目录 |
| 旧版本 | 笔记覆盖、删除前写 `.trash/`；记忆没有同等备份机制 | 导入自己维护统一事务备份，不依赖笔记回收目录 |
| 记忆生效 | 引擎在每次 `before_agent_start` 读取记忆索引 | 导入完成后下一轮可读取，不向正在执行的轮次热替换记忆 |
| 检索 | 桌面笔记搜索直接扫描文件；当前 gateway 下未发现 recall 实现 | 首版刷新列表与现有搜索即可，不把历史 FTS5 设计当作现有重建接口 |
| 专家记忆 | 专家定义目录有独立 `.kalo/memory` | 首版只迁移个人记忆，专家资产不混入个人资料包 |

## 3. 导出范围

默认勾选「个人记忆」「全部笔记」「引用附件」。支持只选其中一种内容；首版不提供逐篇筛选，减少跨笔记引用缺失。

| 内容 | 首版行为 |
| --- | --- |
| `memory/*.md` | 导出；存在 `memory/archive/**/*.md` 时保留归档层级，不提升为活跃记忆 |
| `knowledge/` 中现有扫描规则识别的笔记 | 导出，包括自建分类、嵌套目录与根目录笔记 |
| `knowledge/_types/*.md` 与分类目录 | 导出，不当成普通笔记 |
| 内容实际引用的本地图片与文件 | 收集并按内容哈希去重；不打包整个共享附件目录 |
| `knowledge/.trash/`、`.git/`、隐藏运行文件 | 首版不导出；界面标明不包含回收站与历史版本 |
| `INDEX.md`、`AGENTS.md`、`README.md` | 不作为笔记导入；导出预检列出被排除的保留文件。用户手写在这些文件里的内容不会静默计入已备份数量 |
| 会话、认证、API Key、模型设置、定时任务、工作目录、skills、专家配置、缓存与搜索数据库 | 不导出 |

资料包仅备份上述资产，不宣称是整个 Kalo 的完整备份。正文自身可能包含隐私或密钥，排除认证配置不等于内容脱敏。首版使用明文 ZIP，界面明确显示「资料包包含个人内容，未加密」；不把哈希校验描述为加密或身份认证。

受支持的记忆/笔记文件无法读取或解析时，预检展示路径与原因并阻止导出，修复后重试。不得使用当前列表接口的“跳过损坏文件”行为生成虚假的完整备份结果；首版不生成部分包。

## 4. 用户操作流程

### 导出

1. 在数据管理设置点击准备迁移，等待笔记保存队列排空，检查残留草稿。未保存草稿可返回笔记页恢复，或另存为恢复笔记；不得静默舍弃。
2. 用户结束任务并正常退出 Kalo，下次启动进入维护窗口。准备操作不主动停止任务。
3. 选择记忆、笔记范围，扫描引用并建立快照，展示条目数量、附件数量、预计大小与排除的保留文件。
4. 外部文件、缺失附件、不支持的链接导致导出停止并显示位置。先修复或复制进个人附件目录后再试。
5. 选保存位置，验证快照、生成包并完成最终文件写入，显示实际条目数与保存位置。

### 导入

1. 选择资料包，校验格式版本、路径、体积和哈希，在隔离暂存目录解析。
2. 显示来源导出时间、记忆/笔记/附件数量，以及「新增、相同、冲突、无法迁移」汇总。
3. 处理冲突，展示本机与导入内容的差异。默认不覆盖本机。
4. 点击「确认导入」，在已有维护窗口内重新计算本机状态。预览后发生变化则要求重新检查预览，不能沿用旧判断。
5. 建立事务备份，安装附件、内容与分类描述，验证并提交。失败按事务回滚。
6. 显示实际新增、跳过、替换、冲突暂存的数量；刷新笔记、记忆与搜索。提供「查看记录」与「撤销本次导入」。

导入成功不自动发起对话，不执行内容中的命令，不自动启动维护任务。记忆在后续对话中按现有规则参与索引注入。

## 5. 包格式 v1

ZIP 内固定布局：

```text
manifest.json
data/
  memory/<slug>.md
  memory/archive/<slug>.md
  knowledge/<分类>/<笔记>.md
  knowledge/_types/<分类>.md
  attachments/portable/<sha256>.<扩展名>
```

`data/` 相当于目标设备的个人数据根；文档路径保持原有相对位置，附件归入内容寻址目录。不保存源设备用户名、主机名或绝对根路径作为结构化元数据。

`manifest.json` 至少包含：

| 字段 | 契约 |
| --- | --- |
| `format` / `formatVersion` | 固定 `kalo-personal-data` / `1`；未知版本拒绝，并提示升级或重新导出 |
| `exportId` / `exportedAtMs` / `appVersion` | 随机 UUID、UTC Unix 毫秒、生成包的应用版本；不用于决定哪个内容更新 |
| `scopes` / `directories` | 选择的内容域与分类空目录清单 |
| `entries[]` | 每项包含 `kind`、`path`、`bytes`、`sha256`；路径为 `data/` 下的相对路径 |
| `warnings[]` | 被排除的保留文件等范围说明；只记录相对定位信息，源绝对路径留在本机错误提示 |

`sha256` 基于打包后真实字节，用于损坏检测；ZIP 中重复条目、清单外文件、清单缺项或字节数不符均拒绝。manifest 有独立体积与条目数上限，不能先无限制读入再检查。

保留 Markdown 的未知 frontmatter、原始日期和普通正文；只对可定位的文件引用做定点替换。包格式版本与应用版本分离。首版不向所有历史文件补写 UUID，不改变 memory 的解析/序列化契约。

## 6. 附件与链接迁移

### 相对路径

例如源笔记在 `knowledge/cards/学习.md`，图片来自本机绝对路径。导出后正文使用：

```markdown
![示意图](../../attachments/portable/<sha256>.png)
```

设备 B 保持相同数据根内布局，用户名和盘符改变也能解析。导出只转换快照副本，不修改设备 A 的笔记。导入也保留相对路径；以后新插入的绝对路径图片仍由下次导出重新收集，无需首版同时改造编辑器附件存储。

### 引用处理边界

- 使用有源码位置的 Markdown 解析处理内联链接、内联图片、引用式链接及其定义；保留标题、转义、空格、括号、URL 编码和片段。不得用正文全局字符串替换。
- 代码块、行内代码和普通文本里的路径不改写。HTML 属性、特殊 URI、无法解析的引用列入警告，不假装已经迁移。
- 本地普通文件链接与图片采用相同收集规则；目录、设备文件、符号链接、junction/reparse point 不跟随。UNC 网络文件不自动访问，用户可先复制到本地后重试。
- 个人数据根之外的引用阻止导出，提示先复制到个人附件目录。只自动收集 `attachments/` 的普通文件及 `knowledge/` 内的非 Markdown 附件；不会通过链接把认证或其他运行配置纳入资料包。网页 URL 保留，不自动下载，明确标注仍需联网。
- 指向本次已选笔记/记忆的链接使用包内目标；指向未选内容的链接提示范围缺失，不自动越过导出范围收集整库。
- `[[标题]]` 原样保留。存在同名标题时显示歧义提示，不猜测目标；不把双链解析功能当作本次迁移前提。
- `source_session` 等会话来源字段原样保存，但标为来源记录；首版没有带走会话，不保证能打开原会话。
- 缺失附件阻止导出并定位，不产生引用不完整的包。导入也检查每个可识别本地链接必须指向包内文件，不访问源设备绝对路径。
- 未识别语法与普通正文可能仍含源路径；预览说明其不具备可移植保证，不承诺自动脱敏。

附件文件名由内容哈希生成，扩展名采用规范化映射。相同字节只存一份；相同哈希位置已有不同字节时视为损坏并停止，不能覆盖。正文里的笔记链接在所有目标文件名分配完后统一重映射，避免“保留两份”后链接仍指向旧文件。

## 7. 冲突与重复导入

第一阶段以「内容域 + 相对路径」识别条目；相同标题不等于同一条目。比较内容时先生成与导出相同的可移植视图，消除本机附件绝对路径差异，再比较哈希。文件修改时间与 frontmatter 的 updated 仅供展示，不能用“更新的覆盖旧的”自动裁决。

| 情况 | 默认行为 | 可选行为 |
| --- | --- | --- |
| 目标路径不存在 | 新增 | 跳过 |
| 相同路径、可移植内容一致 | 跳过 | 无需处理 |
| 同路径笔记内容不同 | 保留本机，导入版本另存，文件名加稳定的内容哈希短后缀 | 保留本机并跳过；用导入版本替换 |
| 同 slug 活跃记忆内容不同 | 本机继续生效，导入版本存入 `~/.kalo/transfers/conflicts/<事务>/` 等待处理 | 使用导入版本替换；跳过；用户编辑合并后再写入 |
| 分类描述冲突 | 保留本机分类描述，在记录中保留导入版本 | 显式选择替换 |
| 包中不存在的本机内容 | 保留 | 首版不提供镜像删除 |
| 路径不同、内容相同 | 提示可能重复；不擅自删除或合并 | 用户选择跳过 |

记忆冲突不默认生成两个活跃 slug，防止相互矛盾的偏好同时注入。不同 slug 的语义矛盾无法靠文件哈希可靠识别，导入预览需提供完整记忆列表，首版不使用模型自动判断或改写。

导入记录保存「源相对路径 + 可移植内容哈希 → 本机最终路径 + 落盘哈希 + 处理决定」，不只记录 exportId。同一内容重新打包或重复导入时复用记录，并重新验证落盘内容；保留两份不能越导越多。路径已删除或内容已修改则重新进入预览，不能凭历史回执声称已导入。用户跳过的决定不永久屏蔽将来的显式重试。

首版不传播删除，也不自动识别跨设备改名。设备 A 删除一篇笔记后再导入 B，B 的原文件仍保留；界面需要直接说明这条规则。

## 8. 一致性、失败恢复与撤销

### 维护窗口

仅给 Rust 写接口加锁不足以保证一致性：引擎工具和后台脚本也可能直接写 Markdown。

首版采用应用级维护模式：正常模式完成保存与草稿检查并设置下次启动标记，由用户结束任务后正常退出；下次启动只挂载迁移与恢复界面，不启动引擎、gateway、定时任务和后台子进程。使用个人数据根的跨进程独占锁，阻止其他新版 Kalo 实例启动写入；正常启动同样必须遵守该锁。

这是新的启动行为，现有 shutdown 方法不能直接当作“暂停后安全恢复”。需新增维护启动参数、待执行操作记录和正常退出/重启流程；不自动强杀尚在工作的任务。单实例锁覆盖不到外部编辑器、旧版 Kalo 或独立脚本，界面要求暂停这些写入；操作前后复核文件集合和哈希，发现变化就中止或重新预览。不宣称能抵御任意外部进程的并发修改。

导出在维护窗口建立暂存快照，压缩只读快照；导出完成后用户可以返回普通模式。导入从重新验证计划到提交完成期间持续保持维护模式。返回普通模式时先关闭迁移入口，再释放数据目录锁，然后请求应用重启，避免新旧进程短暂重叠造成误报。

### 导入事务

事务目录设在 `~/.kalo/transfers/<transactionId>/`，与目标处于同一数据卷，包含不可变输入、计划、原文件备份、写入前后哈希与持久化日志。该目录不进资料包，也不进入知识与记忆扫描。

1. 预先计算暂存、备份、目标新增和安全余量需要的空间；不足时停止。
2. 在任何覆盖前，保存全部受影响旧文件和原本不存在的目标清单，备份失败则不开始写入。
3. 写入同目录临时文件，刷新文件数据，记录即将执行的步骤，再通过平台适配层安装最终文件。先安装附件，再安装内容，最后记录提交状态。
4. 多文件提交不声称天然原子；依靠日志实现失败回滚和崩溃恢复。恢复检查必须早于任何 sidecar、编辑器或搜索启动。
5. 日志未提交时检查每步真实文件哈希，恢复旧文件并移除此次新增且未被修改的文件。发现外部修改时停止自动回滚，保留备份并显示具体冲突，避免二次覆盖。
6. 提交后刷新界面；将来引入可重建检索缓存时再接失效/重建适配器，不随包复制索引数据库。

撤销使用相同维护模式。仅当目标仍符合本次导入后的哈希时恢复；导入后被用户编辑的文件要先显示冲突。附件采用保守清理：撤销可保留新附件，首版不自动删除可能已被其他内容引用的共享文件。备份默认保留最近 30 天，但只有用户从数据管理明确清理时才删除；未解决冲突与未完成事务禁止自动清理。

## 9. Windows / macOS 等价契约

- 数据根继续通过统一路径适配解析 `USERPROFILE`，回退 `HOME`；包内只用 `/`，不得以源绝对路径确定落盘位置。
- 拒绝绝对路径、盘符、UNC、空段、`.`、`..`、反斜杠、NUL、ADS 冒号、Windows 设备保留名、非法字符和结尾空格/点。对目标祖先逐级检查，拒绝链接与越界；检查必须覆盖尚不存在的叶子路径。
- 对 Unicode 规范化与大小写折叠后的路径做保守碰撞检测，两平台采用相同规则。包内有冲突时拒绝并定位；与本机冲突时预览分配安全的新名称并重映射引用，不静默覆盖。
- 导出遇到不可移植源文件名时同样提前报告，首版要求用户改名后重试，不等到另一台设备导入才失败。
- 路径长度按目标平台实际能力校验，错误定位到具体条目；不依赖长路径开关默认开启。
- 解压默认上限：10 万条目、单文件 512 MiB、累计解压 5 GiB、manifest 16 MiB。流式统计实际输出并检查剩余空间；不能只信 ZIP 头部大小。上限是首版产品限制，可在后续按真实需求调整。
- 不恢复 POSIX 执行位或源系统 ACL，不运行包内文件；新文件使用本机用户的数据目录权限。
- 临时文件、替换与日志落盘策略集中在文件系统适配层。Windows 目标被占用时明确失败并保留恢复材料；不能假设 rename 在所有平台都能覆盖已存在文件。
- 不调用外部 zip/unzip 或 shell 搬运用户路径；避免命令引用、编码与工具可用性差异。

## 10. 实现拆分与接口草案

下列模块与命令已接入桌面端；这些命令不属于引擎 RPC。

| 模块 | 职责 |
| --- | --- |
| `src/features/data-transfer/` | 导出范围、进度、预览、冲突处理与历史；IPC 放适配层 |
| `src/features/data-transfer/types.ts` | 前端类型与展示模型，不处理文件写入 |
| `src/lib/pi-bridge.ts` | 统一封装桌面命令，避免组件散落 invoke |
| `src-tauri/src/data_transfer/types.rs` | 格式版本与清单、计划、事务类型 |
| `src-tauri/src/data_transfer/references.rs` | Markdown 引用提取、路径映射与定点替换 |
| `src-tauri/src/data_transfer/plan.rs` | 哈希对比、冲突分类、最终路径分配与幂等规则 |
| `src-tauri/src/data_transfer/archive.rs` | ZIP 流式读写、配额与校验 |
| `src-tauri/src/data_transfer/transaction.rs` | 备份、日志、提交、恢复与撤销 |
| `src-tauri/src/data_transfer/platform.rs` | 目录锁、链接检查、文件替换与持久化的 OS 差异 |
| 应用启动层 | 草稿交接、维护模式重启、sidecar 启动 gate、事务恢复优先级 |

接口采用 prepare → preview → commit，避免一次 invoke 在长时间无反馈后直接覆盖。所有耗时命令在后台线程执行；单操作锁防止重入：

- `data_transfer_status()` / `data_transfer_arm({armed})`：查询状态、准备或取消下次启动进入维护模式。
- `data_transfer_leave()` / `data_transfer_recover()`：返回普通模式、重试恢复。
- `prepare_data_export({scopes})` / `prepare_data_import({path})`：返回 `operationId、mode、manifest、items、revision`。
- `resolve_data_import({operationId, decisions})`：重新规划并返回完整预览。
- `data_transfer_details({operationId, path})`：返回本机与导入版本原文，只用于文本比较。
- `finish_data_export({operationId, path})` / `commit_data_import({operationId, revision})`：保存包、校验计划版本并提交导入。
- `cancel_data_transfer({operationId})`：预览阶段清理暂存；提交中拒绝取消，失败自动回滚。
- `list_data_transfers()` / `undo_data_import({transactionId})`：历史与撤销预览。
- `data-transfer-progress` 事件：携带阶段、已处理数量和总数量；维护窗口同一时间只允许一个操作。

导出目标由原生保存对话框产生；源包只在 prepare 时接受路径，后续通过后端生成的 operationId 和计划版本访问暂存数据，不能让前端传任意解压目标。计划绑定暂存输入哈希和目标基线。关闭预览或成功提交后清理对应暂存；崩溃时留下的暂存仅供诊断，不自动执行。

首版不新增引擎 memory RPC，不修改内置 skill 安装行为。启动 gate 属于桌面与进程生命周期变化，实施时必须覆盖 gateway 自动重启、按需启动和延迟启动路径，不能只拦首次启动。

## 11. 分期与验收

### 第一阶段：可交付的手动迁移

一次完成个人记忆、笔记、附件、分类描述的导出导入，包含完整性预检、冲突预览、幂等、事务备份与恢复。维护模式属于本阶段必要条件，不能先上线有并发覆盖风险的导入再补。

最低验收集合：

1. Windows 导出 → macOS 导入，反向也成立；中文路径、空格、图片、分类与元数据可读。
2. 新设备导入后，笔记图片离线可见，下一轮对话能读取个人记忆；专家记忆未混入。
3. 同一个包导入两次，以及同内容重新导出后再导入，不产生重复副本。
4. 双设备同路径编辑：笔记保留两份且链接正确；记忆冲突只保留一份活跃内容。
5. 自动保存未完成、残留草稿、运行中任务和预览后文件变化均能阻止过期计划执行。
6. 缺图、外部文件、保留文件、不支持语法均有明确报告，不出现“成功但悄悄漏掉内容”。
7. 断电/崩溃模拟覆盖备份、安装附件、安装笔记、提交日志各阶段；重启先恢复，后允许普通使用。
8. 空间不足、文件占用、权限不足、哈希不符、恶意越界路径、大小写碰撞、Unicode 碰撞、超限压缩包均失败可解释。
9. 撤销不会覆盖导入后编辑，不删除共享附件或未参与本次导入的文件。

纯逻辑测试覆盖路径、引用改写、清单校验、冲突计划与幂等；事务使用隔离临时目录做故障注入验证。IPC/DOM/TSX 不做模拟单测，维护启动与跨平台交互做实际桌面验收。实施后按改动运行 `npm run check`，需要验证 Rust 测试时使用 `--with-tests`；若涉及 harness，按其区域约定执行。

### 第二阶段：更频繁的多设备使用

在手动迁移稳定后，再增加可选密码加密、选定分类导出、自动生成备份到用户选择的文件夹。用户可以把已生成的不可变包放入自己的网盘，但不直接让多个设备共享写入活动数据目录。

### 第三阶段：真正的双向同步

若使用方式变成每天在多台设备并行编辑，需要升级身份与版本模型：跨设备稳定 entityId、设备标识、共同基线/父版本、删除 tombstone、重命名追踪、冲突分支和保留期限。改造所有实际写入入口，含引擎与手工编辑发现流程，不能只改桌面保存方法。先把这个模型落地，再选择传输后端；首版的包格式可继续作为备份与传输载体，但不把路径哈希包装成完整同步协议。
