# 压缩复用 messages 以命中 prompt cache

## 背景

压缩慢的主因是 prefill：压缩请求把整段历史重新发一遍，网关约 3.5K tok/s，180K 上下文约 60s。

当前实现主动放弃了前缀缓存。`compaction.ts` 的 `completeSummarization()` 有三处：

1. `cacheRetention: "none"` —— 显式关闭缓存写入
2. 每次生成新的 `sessionId` —— 强制路由到新会话
3. `serializeConversation()` 把 N 条消息压平成 1 条巨型 user 文本

第 3 条是根本原因：序列化产出的 token 序列与主对话从第 0 个 token 就分叉，前缀缓存必然 miss。

体积可行性已实测确认，详见 `doc/2026-09-10-压缩复用messages与prompt-cache.md`：33 个真实压缩点中，复用 messages 的体积没有一次超过 200K 窗口（最大 198K），膨胀比中位数约 1.08x。

## 方案

新增 `compaction.reuseMessages` 设置，**默认 `true`**。开启时压缩请求改为：

- 复用 `messagesToSummarize` 的原始消息数组，不做 `serializeConversation()` 压平
- 末尾追加一条 user 消息承载摘要指令（原 `SUMMARIZATION_PROMPT` / `UPDATE_SUMMARIZATION_PROMPT`）
- 保留 `cacheRetention` 默认行为，复用主会话 `sessionId`，使前缀可被缓存命中

关闭时走原有的 `serializeConversation()` 截断路径，行为完全不变。

### 为什么默认开启

复用模式在支持前缀缓存的 provider（原生 anthropic）上是净收益。默认关闭意味着绝大多数用户拿不到这个优化，且需要手动发现并配置。默认开启、允许显式关闭，是更合理的取舍。

在不支持缓存的 provider 上，复用模式会多付膨胀出来的 prefill（1.1x-6x 不等），此时可通过设置显式关闭。

### 数据流

```
prepareCompaction()
  └─ messagesToSummarize: AgentMessage[]
       │
       ├─ reuseMessages=true  → convertToLlm() → 原样作为 messages
       │                        + 末尾追加 { role: "user", content: 指令 }
       │                        + cacheRetention 默认 / sessionId 复用
       │
       └─ reuseMessages=false → convertToLlm() → serializeConversation() 压平成单条 user
                                + cacheRetention: "none" / sessionId 新建
```

两条路径共用同一个 `SUMMARIZATION_SYSTEM_PROMPT` 与同一套摘要格式指令，摘要产出格式不变。

### previousSummary 的位置

复用模式下 `<previous-summary>` 不能再拼进那条巨型 user 文本。改为放进末尾追加的指令消息中，与摘要指令一起，保证前面的历史消息序列不被污染，前缀才能与主对话对齐。

## keepRecentTokens 默认值调整

`getCompactionKeepRecentTokens()` 默认值从 `20000` 改为 `8000`。

原因：压缩后的上下文 = 摘要 + 保留尾部。实测两个真实会话的最后一次压缩：

| | 摘要 | 保留尾部 | 合计 |
| --- | --- | --- | --- |
| 09-10 会话 | 3.3K | 23.8K | 27.1K |
| 09-09 会话 | 4.1K | 22.4K | 26.5K |

保留尾部几乎全是工具结果（09-09 那次 toolResult 占 20.5K，其中两条 bash 结果各 7309 / 7112 tok）。注意 `TOOL_RESULT_MAX_CHARS` 只作用于摘要 prompt，保留尾部是原样进上下文的。

`findCutPoint()` 从后往前累加到超过预算才切，且只能切在合法 turn 边界，所以实际值会略超预算（20K 预算 → 23.8K 实际）。调到 8000 后压缩后上下文约 11K。

代价：压缩后模型手边的真实上下文变少，更依赖摘要质量，可能更频繁地回头 `read` 文件。

## 配置

```json
{
  "compaction": {
    "reuseMessages": true,
    "keepRecentTokens": 8000,
    "thinkingLevel": "off"
  }
}
```

三项均为默认值，无需显式配置。在不支持前缀缓存的 provider 上建议设 `reuseMessages: false`。

## 验证

- `packages/coding-agent/test/compaction-summary-reasoning.test.ts`：断言两种模式下的请求形态差异（消息条数、`cacheRetention`、`sessionId` 复用与否）
- `npm run check`（changed-aware）
- 判断 provider 是否真的支持缓存，用 WARM/COLD 交替法实测，方法见 `doc/2026-09-10-压缩复用messages与prompt-cache.md`

## 不在本次范围

- 对保留尾部的工具结果做截断：会改变模型在正常对话中能看到的内容，风险高
- 压缩使用独立的小/快模型：实测同等 prompt 用 `deepseek-v4-flash` 快一个数量级，但涉及模型路由改造
- split-turn 两次摘要并行化
