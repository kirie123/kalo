# 自定义 Provider 的模型能力配置（2026-09-11）

## 问题

桌面端「添加模型 / 编辑模型」弹窗（`src/components/ProviderEditModal.tsx`）保存时只写两个字段：

```ts
providers[name] = { baseUrl, api, apiKey, compat?, models: [{ id, contextWindow }] };
```

而引擎的模型定义 schema（`kalo-harness/packages/coding-agent/src/core/model-config.ts` 的
`ModelDefinitionSchema`）支持 `reasoning` / `input` / `maxTokens` / `cost` / `samplingParams` /
`headers` / `thinkingLevelMap` 等。缺省项在 `provider-composer.ts` 的 `modelFromJson()` 里落默认值，
于是从 UI 建的模型全部退化为「无思考、纯文本、16K 输出」：

| 症状 | 直接原因 | 用户感受 |
| --- | --- | --- |
| 不思考 | `reasoning: definition.reasoning ?? false` | `settings.json` 里 `defaultThinkingLevel: high` 是摆设，`anthropic-messages.ts` 因 `!options.reasoning` 直接不发 `thinking` 块 |
| 读不到图 | `input: definition.input ?? ["text"]` | 粘贴截图被换成 `(image omitted: model does not support images)` |
| 输出被截短 | `maxTokens: definition.maxTokens ?? 16384` | 长回答/长代码提前断掉 |
| 手工字段被抹 | 保存时**整条重建** provider 对象 | 手改的 `authHeader`（Bearer 鉴权）、`headers`、`name`、`oauth`、`modelOverrides` 在 UI 编辑一次后消失 |

`pi --list-models` 是最快的判别方式：命中本问题的模型 `thinking` / `images` 列都是 `no`。

## 设计

### 1. 能力开关按 provider 共享

与现有「上下文上限（K）」的粒度保持一致：一个开关管该 provider 下的所有模型。理由是 UI 保持
「一个 provider 一张表单、模型列表就是一个多行文本框」，不引入表格编辑。

表单新增：

- **支持思考（reasoning）**：勾选后给该 provider 下每个模型写 `reasoning: true`。
- **支持图片（vision）**：勾选后写 `input: ["text", "image"]`，否则写 `["text"]`。
- **最大输出（K）**：写 `maxTokens`；留空表示删除该字段、用引擎默认值（与上下文上限同样的语义）。
- **Bearer 鉴权头（authHeader）**：provider 级，写 `authHeader: true`。网关只要
  `Authorization: Bearer` 而拒绝 `x-api-key` 时必须开（见
  `troubleshooting/anthropic-gateway-401-bearer-auth.md`）。

已存在的模型如果取值不一致（例如手工只给一个模型开了图），开关显示为未勾选并在提示里说明
「当前模型取值不一致，保存后统一写入」——保存即统一，不做隐式保留，避免「看起来勾了其实没写」。

### 2. 保存改为合并，而非重建

```
providers[name] = { ...上一版该 provider 的全部字段, ...本次表单管理的字段 }
```

表单管理的字段：`baseUrl` / `api` / `apiKey` / `authHeader` / `compat` / `models`。
其余（`name` / `oauth` / `headers` / `modelOverrides`）原样保留。

模型条目同样以既有条目为底再覆盖（保留 `name` / `cost` / `samplingParams` / `headers` /
`thinkingLevelMap`），只写表单管理的 `contextWindow` / `maxTokens` / `reasoning` / `input`。

顶层也只替换 `providers`，不再用 `{ providers }` 覆盖整个文件。

### 3. 纯逻辑抽到 `src/lib/provider-config.ts`

组件只做取值与渲染，写入逻辑（合并、能力字段、URL 归一化、K 值换算）全部为可单测的纯函数，
符合 `kalo-desktop/AGENTS.md`：`vite.config.ts` 的 vitest 不覆盖 TSX，所以组件里的逻辑无法测。

导出：

- `normalizeBaseUrl(raw, api)`：去尾部斜杠；OpenAI 系 API 且是裸 localhost（无路径）时补 `/v1`。
- `LOCAL_KEY_PLACEHOLDER`：本地服务占位 key（引擎拒绝无 key 的 provider）。
- `defaultContextK(id, cfg)` / `defaultMaxOutK(cfg)`：表单初值。
- `readCapability(models, key)`：返回 `"all" | "none" | "mixed"`，驱动开关初值。
- `buildProviderEntry(form, previous?)`：唯一写入路径，返回该 provider 的新条目。
- `sameModelIds(a, b)`：判断合并是否需要保留旧模型元数据（仅用于提示文案）。

## 关闭行为（点遮罩不关窗）

弹窗只有两个出口：**保存** 和 **取消**。点遮罩不关，只在首次误点时空弹一条 toast
「点「取消」或「保存」关闭这个窗口」（`backdropHintShownRef` 保证每次打开只说一次）。

第一版曾按「表单未改动才允许点遮罩关闭」来做，实测不够：判定一个 click 是否属于遮罩，本身就有坑——
`click` 事件的目标是**鼠标按下与抬起两个目标的最近公共祖先**，在表单里拖选文字、拖「模型列表」文本框
右下角的缩放把手（`resize-y`），只要抬手落在弹窗外，事件目标就成了遮罩，弹窗被当成「点击空白处」关掉，
半填的 provider 配置（含 API Key）无声丢失。

最后选择「一律不关」的理由：

1. 这张表单字段多（Base URL / Key / 模型列表 / 能力开关）、重填成本高，误触一次的代价远大于
   「点空白关窗」带来的便利；而「取消」就在右下角、只多一次点击。
2. 「看表单脏不脏再决定关不关」会让同一个动作在两种结果之间摇摆，用户无法预判；
   「关不关只由两个按钮决定」才是可预测的规则。
3. 遮罩 handler 用 `onMouseDown` 而不是 `onClick`：不需要再关心按下/抬起的配对，
   拖拽误触天然不会命中提示。

遮罩点击仍不穿透（`onClick` 上保留 `stopPropagation`），底层设置页不会同时被点到。

## 兼容性

- 既有 `models.json` 无需迁移：未写能力的模型在用户下次点开弹窗并保存后即被补齐。
- 不改引擎侧 schema、不改 sidecar 契约（`models.json` 本就是引擎的公开配置面），无需重建 exe。
- 手工维护的字段只要不在表单管理范围内就继续保留；此前「编辑一次 pz 就丢 `authHeader`」的坑同时修掉。

## 验证

- `npm test`（vitest）：`src/lib/provider-config.test.ts` 覆盖合并保留、能力写入、K 值空值语义、
  URL 归一化、mixed 判定。
- 人工：弹窗勾选「支持思考 / 支持图片」保存后，`pi --list-models` 对应行 `thinking` / `images`
  应变成 `yes`；`pi --print --mode json` 下能看到 `thinking_start` 事件。
- 人工：点遮罩不再关窗（首次误点出现提示 toast），只有「取消」/「保存」能关；
  在「模型列表」里拖选文字到弹窗外抬手，弹窗不关。
- 模型 ID 示例：`模型列表` 占位符给出的是示例 shape，不要写会过期的假 ID——曾写成
  `deepseek-v4-flash`，而引擎目录（`~/.kalo/agent/models-store.json`）里 deepseek 的模型是
  `deepseek-flash`；占位符现在写 `gpt-4o` / `deepseek-flash`。
