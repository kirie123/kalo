# era 依赖与按需安装

## 背景

era（[era-evolve](https://github.com/kirie123/era-evolve)）是一个独立开源仓库，Python CLI。kalo 的「演化」面板通过通用 `job_run` 起 `era serve`，读它写出的 `trace.jsonl`。

两条约束互相拉扯：

1. era 要留在自己的仓库里继续演进，kalo 不应该 fork 它。
2. kalo 必须能直接 `bun run dev` / `bun run build` 构建，不引入 Python 工具链要求。

现状是两条都没满足好：`era-run.json` 里有个 `eraBin` 逃生口，其余全靠「era 在 PATH 上」这个假设。这个假设在开发机上就是假的，导致一次真实运行以 1.5 秒「completed」、0 个节点收场，而面板只能事后从空 trace 反推原因。

## 三个改变判断的事实

### 一、era 不需要「安装」

era 是纯标准库（`argparse ast collections contextlib dataclasses difflib hashlib html json math os queue re shutil statistics subprocess sys tempfile threading time typing`，没有 ssl / sqlite3 / ctypes / tkinter），且有 `era/__main__.py`。所以：

```bash
PYTHONPATH=<era 仓库根> python -m era doctor
```

在开发机那个 **pip 已损坏的 3.10.0a5** 上直接验证通过。`pip install` / venv / pipx 这一整条路径不是必需的 —— 唯一的真依赖是一个 ≥3.10 的解释器。

### 二、解释器的三种常规发现途径都不可靠

开发机实测：

| 途径 | 结果 |
|---|---|
| `python` on PATH | `C:\Python27` → 2.7.10 |
| `py -0p` 最优项 | 3.10.0a5，alpha，pip 损坏 |
| 两者都没报告的 | `miniforge3/python.exe` → **3.12.8 + pip 24.3.1，完全可用** |

这台机器一直有健康的 Python 3.12，只是 PATH 里只暴露了 `miniforge3/Scripts/pip3`，`py` launcher 也没注册它。结论：任何解析器都必须同时探测 conda/miniforge/mamba 根目录，并且**主动拒绝** 2.x 与 prerelease，而不是「拿到 python 就用」。

### 三、安装器本身也可以是一条普通后台任务

[2026-08-18-era-evolve-panel.md](2026-08-18-era-evolve-panel.md) 立的原则是「era 就是一条普通后台任务」。这个原则可以再推一步：**装 era 也是一条普通后台任务**。已有的 `job_run` + `read_text_since` 足够把安装过程的日志实时流到面板上，不需要新的进程管理、新的 Rust 命令、新的协议。

### 四、把 era 装对，并不能让评测用对解释器

这是实现过程中才认清的一条，它单独决定了一处改动。

`--eval` 是 era **派生出去的一条 shell 命令**，里面的裸 `python` 是在打分那一刻按 PATH 解析的。所以「era 跑在一个健康的 3.12 上」和「评测脚本跑在一个健康的 3.12 上」是两件独立的事：era 在 3.12 上照样会用 PATH 上的 2.7 去给每个候选打分，脚本里任何 f-string 直接 SyntaxError，整轮演化「成功结束」而一个节点都没改进。

装 era 修不了它，`era doctor` 也查不出它（doctor 检查的是引擎，不是评测命令）。唯一的修法是在 kalo 侧把 eval 命令头部的裸解释器换成探测到的绝对路径 —— 且**闸门与运行必须换成同一条命令**，否则闸门量的不是 era 将要量的东西。

### 五、真正的目标是「clone 完能试用」

原始需求：别人 clone kalo 之后，应当很容易地构建并试用**包括演化在内**的全部功能。

这条把优先级重排了。装上 era 只是把「不能跑」变成「能跑」，用户手上仍然没有 seed 目录、没有 `eval.py`、没有一个已知会动的分数曲线 —— 而这些恰恰是演化的前提物料，也是最难自己造的部分。所以必须多一个**一键示例**：点一下就得到一个完整的、验证过的实验目录。同理，README 的构建步骤必须前置到最上面。

## 决策

**era-evolve 发布到 PyPI；kalo 侧在面板内按需用 uv 安装，构建流程零改动。**

```
uv tool install era-evolve==<pinned>
```

uv 会自带托管 CPython 下载，所以解释器问题和包安装问题被同一条命令解决。era 保持 100% 外置。

具体后果：

- `scripts/ensure-engine.mjs` **不加 era 阶段**，`bun run dev` / `bun run build` 一行不改
- 安装包体积零增长
- 构建期零下载、零联网要求
- 首次使用演化时才联网 —— 而 era 本来就要驱动 pi 打模型 API，离线跑不了，这个代价是免费的

### 为什么不是其他方案

- **vendor era 源码进 kalo**（git subtree，仿 `kalo-harness/` 对 pi 的做法）：离线安全、不依赖第三方基建，但 +15 MB 体积、多一份会漂移的副本、还得再解决解释器。在 era 已经能发 PyPI 的前提下，这些代价换不到东西。
- **era-evolve 出 PyInstaller release，kalo 构建时下载固定版本**：仓库边界最干净，但要在另一个仓库建 CI/release 流程，且首次构建强制联网 —— 违反约束 2。
- **git submodule**：不解决解释器问题，还往「直接 bun run dev」路径上加了 `submodule update --init`，与 kalo-harness 的 vendor 惯例也不一致。
- **移植成 TypeScript**：复制一个还在演进的研究代码库，等于放弃仓库分离。

## 改动

### 一、era 的位置：从实验规格搬到机器级设置

`eraBin` 现在在 `era-run.json` 里。那是**实验规格** —— 跟着实验目录走、会被 `era-experiment-designer` skill 重写、会被分享给别人。而 era 装在哪是**机器级**事实，跟实验无关。这就是这次踩坑的直接原因：向导生成的 spec 里没有、也不该有 `eraBin`。

- 新增 `kalo-desktop/src/features/era/locate.ts`：机器级配置读写（localStorage `kalo.era.bin` / `kalo.era.source` / `kalo.era.python`，与既有 `kalo.era.workspaces` / `kalo.theme` 一致，不引入新文件格式或 Rust 命令）+ 分层解析器：

  ```
  1. 用户显式设置（kalo.era.bin）
  2. 老 spec 里的 eraBin（只读兼容）
  3. PATH 上的 era
  4. uv tool 安装位置（~/.local/bin/era[.exe]）
  5. era 源码检出 + 探测到的 ≥3.10 解释器：PYTHONPATH=<src> <py> -m era
  ```

  顺序是刻意的：显式的压过发现的，**发现到的安装压过源码检出** —— 检出是开发者场景，悄悄优先它意味着另一个仓库里的一次 `git pull` 能改变 kalo 跑的是什么。

  解释器探测覆盖 `command -v python3/python`、`py -0p`、`uv python find`、conda/miniforge/mamba 根目录、各平台常规安装位置，并且**逐个执行** `python -c 'import sys; ...'` 拿版本，而不是看路径猜 —— 一个叫 `Python310` 的目录什么都不证明，而 `python -c` 在 2.7 上照样能跑，所以 2.x 是被检出并拒绝的，不是被误读的。按版本过滤：拒绝 <3.10 与 prerelease。

- `spec.ts`：`eraBin` 字段保留**只读兼容**（老 spec 里有就仍然尊重，优先级在显式设置之后），但 `serializeSpec` 不再写出它 —— 它是机器级事实，往回写会让它重新混进被分享出去的 spec 里。`EraLaunchOptions` 相应地把 `eraBin?` 换成 `eraCmd?`（已引好号、允许多词的前缀，因为源码模式下它是 `PYTHONPATH=… python -m era`），并新增 `evalCmd?` 覆盖位。
- 设置入口：不动全局设置页，就放在演化面板顶部的「运行环境」卡片里 —— 为一个 feature-local 的设置去改全局设置页的信息架构不值得。

### 二、按需安装：面板内的一条 job

演化面板在解析器返回「找不到」时，显示一个安装卡片而不是一段说明文字：

- 主按钮「安装 era」→ `jobStart` 跑 uv bootstrap，日志用 `read_text_since` 实时展示（与运行日志同一套读法，不用 `job_logs` 那个消耗式游标）
- uv 本身若不存在，同一条脚本先装 uv（官方 installer 脚本，一行）
- 版本**固定**：`era-evolve==<pinned>`，不用 latest —— trace 格式和 CLI flag 是 kalo 折叠逻辑的契约，浮动版本会让面板在用户毫不知情时坏掉
- 国内网络：脚本尊重 `UV_DEFAULT_INDEX`，卡片上给一个填镜像地址的输入框
- 装完自动重跑解析器 + 自检，成功则卡片消失

### 三、发射前自检

`era doctor` 就是为这件事存在的：成功 exit 0，失败非 0（`get_engine` 抛 `EngineNotFound` 是 2，引擎在但 `probe()` 跑不起来是 1）。判据用「非 0 即拦」，不要去区分具体码。

`startRun` 之前插一步：

```
<eraBin> doctor --agent-bin <kalo 自带的 pi>
```

必须带 `--agent-bin`，否则 era 用自己的默认查找逻辑，找不到 kalo 打包的 pi。非 0 就**不起运行**，直接把 stderr 呈现出来。

这把「0 个节点的幽灵运行」变成起跑前的明确报错，也顺手覆盖了「era 在但 pi 路径不对」这类现在完全看不见的情况。

已用 PyPI 构建产物实测：

```
era doctor --agent-bin <kalo 打包的 pi>
engine      : pi
found via   : --agent-bin
version     : 0.84.1
credentials : read by pi itself ... ERA passes no --api-key/--model/--provider
exit=0
```

顺带修一个相邻的坑，它现在有确凿证据了：`probe.ts` 的评测探针应当在 `--eval` 以裸 `python` 开头、而 PATH 上的 `python` 是 2.x 时给出警告。

证据是 **era 自己的测试套件在这台机器上是红的**：`tests/test_e2e_offline.py::test_search_improves_on_the_seed` 确定性失败（3/3）。根因不是 era 的 bug —— `examples/poly/seed/eval.py` 用了 f-string，而 `fake_pi` 内部的爬山用 `eval_cmd = "python eval.py"` 去打分，撞上 PATH 上的 2.7.10 直接 SyntaxError，于是一次都没改进成功。把 miniforge 前置到 PATH 后，同一个文件 24 passed。

也就是说：这个坑不是理论风险，它已经让 era 的示例、era 的测试、以及 kalo 里那次真实运行**同时**踩中过。探针告警的优先级应当和自检同级。

### 四、eval 命令的解释器重写

`locate.ts` 导出 `withPython(evalCmd, python)`：命令头部是**裸**解释器名（`python` / `python3` / `py` / `.exe` 变体）时，换成探测到的绝对路径；带斜杠或引号的一律不动（那是用户自己选的路径），不是 python 开头的也不动（`node score.js`、`./eval.sh`）。

两处调用同一个函数，这是关键：

- `runs.ts` 的 `startRun`：`evalCmd: withPython(spec.evalCmd, resolved.location.python)`
- `probe.ts` 的验证闸门：同样重写，并把重写后的 `effectiveEvalCmd` 显示在闸门上

闸门存在的全部意义是「你看到的基线分就是 era 将要拿到的分」。两边用不同的解释器，闸门就是个装饰。

找不到 ≥3.10 时不重写（保持原样交给 PATH），但闸门上出一条明确告警，把后果说完整：任何 f-string 会 SyntaxError，整轮演化一个节点都改进不了。

### 五、一键示例

新增 `example.ts` + `example/`（`eval.py` / `solution.py` / `era-fixtures.txt`，从 era-evolve `examples/toy/seed/` 原样取来，同作者同 MIT）。面板上「试跑示例」按钮：

- 写到 `~/.kalo/era-examples/tsp60/`，含 `seed/**` 与一份完整的 `era-run.json`（60 城 TSP，`budget: 8`）
- 用一条普通 job 里的 heredoc 写文件（现成路径，没有写文件的 bridge 命令），内容在写出时统一成 LF
- 目录已存在则**复用不覆盖**
- 预算 8 次扩展是真的会打 8 次模型；基线 ≈ -32900，第一次变异通常就推到 -6900 上下，曲线明显动 —— 试用要的就是「看见它动」

这一步是「clone 完能试用」这个目标里最关键的一环，也是原方案完全漏掉的一环。

## era-evolve 侧：发 PyPI

查过了：`era-evolve` 在 PyPI 上是 **404**（simple index 和 JSON API 都是），名字未注册，可直接用。`era` 这个名字已被占（`era 1.1`，一个 date/time 库），所以分发名只能是 `era-evolve` —— 但 console script 名不属于 PyPI 命名空间，装完照样得到一个 `era` 命令。

已完成的准备（`d:/project/era-evolve`，未提交）：

- `pyproject.toml`：补 `license = "MIT"` + `license-files`、`authors`、`keywords`、`classifiers`、`[project.urls]`；版本改为 `dynamic`，从 `era.__version__` 取，消掉与 pyproject 的重复；`build-system` 提到 `setuptools>=77`（PEP 639 需要，构建隔离安装，不约束本机版本）
- `.github/workflows/release.yml`：tag `v*` 触发。矩阵测 3.10 / 3.13（`requires-python` 声明的边界，此前没有任何东西验证这个声明）→ 构建 + `twine check --strict` → **tag 必须等于 `era.__version__`**（PyPI 不允许重传同版本，tag 写错了推第二次也救不回来，所以在这里拦）→ Trusted Publishing 上传。`workflow_dispatch` 可选 TestPyPI 彩排。
- 凭据：**零**。走 OIDC，仓库 secrets 里不放 API token —— 这也符合 era-evolve 的 `AGENTS.md` §1 对凭据的要求。

本地已验证：`python -m build` 成功；`twine check --strict` 两个产物 PASSED；sdist 内容干净（只有 `era/` + `tests/` + README/LICENSE，没夹带 `archive/` 或 run 目录）；干净 venv 装 wheel 后 `era --version` → `era 0.1.0`（dynamic 版本解析正确），`era doctor --agent-bin <kalo 的 pi>` → exit 0。

剩下只有浏览器里的一步：在 PyPI 建 pending Trusted Publisher（新项目首次上传必须先建），绑定 `kirie123/era-evolve` + `release.yml` + environment `pypi`。

- **E-6** README 前置构建步骤 + 「试一下演化」一节 ✅

E-1 + E-2 就能让开发机上的 V-0 跑通（指向 miniforge 的 3.12.8），不必等 E-5。

E-5 卡在浏览器动作上，且它挡住 E-4 的按钮：`ERA_PACKAGE = "era-evolve==0.1.0"` 和 `ERA_GIT_FALLBACK = "git+https://github.com/kirie123/era-evolve@v0.1.0"` 两条路径**现在都不通** —— PyPI 上还没有这个包，era-evolve 仓库也还一个 tag 都没有。在发布或打 tag 之前，安装按钮必然失败。对**这台**开发机没有影响（走的是源码检出那一路），但对「别人 clone 后能试用」这个目标是硬阻塞。

顺带：PyPI 对国内 clone 者的真正价值不在于「方便」，而在于它有稳定镜像，而 GitHub 经常没有。
