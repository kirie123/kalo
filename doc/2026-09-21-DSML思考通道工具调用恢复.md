# DSML 思考通道工具调用恢复

日期：2026-09-21
范围：`kalo-harness/packages/agent`（安全网）、`kalo-harness/packages/ai`（重试分类）
触发背景：通过 Anthropic-messages 兼容网关使用自带推理通道的模型时，工具调用会「静默蒸发」。

## 1. 现象

模型把**原生工具调用写进思考（reasoning）通道**，网关只转换**回答通道**里的调用标记，思考通道里的标记被当作纯文本透传。结果：

- 该轮没有任何结构化 tool call → 工具不执行；
- 没有 tool result、没有报错、文件不落地；
- 模型以为调用已经完成，继续往下走，于是出现后续步骤 `ENOENT`、`git diff` 为空、重复劳动。

对历史会话全量统计（记录见 §5）：思考通道内出现调用标记 **4013 处**，涉及工具 `bash 3150 / read 307 / write 189 / edit 161 / web_fetch 115 / agent 42 / memory_* 26 / todo_write 10 / ask_user 4 / grep 3`。同一条助手消息里「思考通道有标记、真实调用里没有同名调用」的组合大量出现。

### 标记形状

```
<|DSML| invoke name="write">
<|DSML| parameter name="path" string="true">a.ts
</|DSML| parameter>
</|DSML| invoke>
```

- 竖线是全角 `U+FF5C`（少数代理会规范化为 ASCII `|`）；
- `invoke` 后可能**有或没有**空格；
- 前面常有一行 `tool_calls` 包装标记；
- `parameter` 用同形包裹。

## 2. 方案（三层，本仓库实现前两层）

### 2.1 引擎安全网（`packages/agent`）

新增纯函数扫描器 `packages/agent/src/dsml-tool-calls.ts`：

- `findThinkingChannelToolNames(thinking)`：用
  `<[\uff5c|]DSML[\uff5c|]\s*invoke\b[^>]{0,200}?name="([^"\r\n]+)"` 扫描**思考文本**，
  跳过代码围栏（```）内的匹配（引用/示例不算），返回去重后的工具名。
- `findUnexecutedThinkingChannelToolCalls(narrated, executed, registered)`：只返回
  **已注册工具** 且 **同一助手消息里没有真正执行** 的名字。未注册的名字一律忽略，
  避免「模型只是在讨论某个工具」造成误报。

`packages/agent/src/agent-loop.ts` 在 `turn_end` 之前插入恢复块：

- 触发条件：`stopReason !== "length"`（截断场景交给既有 `failToolCallsFromTruncatedMessage` 路径）、
  存在未执行的思考通道调用、且恢复次数未达上限；
- 上限 `MAX_THINKING_CHANNEL_TOOL_NUDGES = 2`，每次 run 计数，防止模型反复「讲解」造成死循环；
- 动作：把一条 user 消息压入上下文并置 `hasMoreToolCalls = true`，让本轮继续：
  `Tool call(s) written inside your reasoning channel were not executed: <names>. Tool-invocation markup inside reasoning is plain text, not a tool call. Re-issue the missing call(s) as real tool calls now.`

这条消息与既有的两条继续消息（`Output token limit reached...`、`You provided reasoning but no visible output...`）同型，
都是 user 角色的注入文本 —— 只有 user/assistant/toolResult 会被送进模型。

### 2.2 重试分类（`packages/ai`）

`packages/ai/src/utils/retry.ts` 的 `RETRYABLE_PROVIDER_ERROR_PATTERN` 增加
`"this request is not supported"`：同一网关在**超大缓存上下文**上会偶发
`400 This request is not supported.`，同一请求重发即成功，属于瞬时拒绝，应进重试。
配额类 400（`Third-party apps now draw from your extra usage...`）仍然 fail-fast：
`NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN` 已覆盖 `insufficient_quota / billing / quota exceeded / out of budget`，
其判定顺序（先非可重试、后可重试）未改变。

### 2.3 网关侧（本仓库之外）

根治点在网关：思考通道的标记要么转换、要么剥离。引擎侧的安全网只是「不让调用静默蒸发」。

## 3. 影响面

- **与 provider 无关**：不改变任何请求体、请求头、鉴权或流解析；只在收到助手消息后读一次思考文本。
  正常 provider 不产生该标记 → 扫描结果为空 → 行为完全不变。
- **误报抑制**：未注册工具名、已真正执行过的同名调用、代码围栏内的内容都不触发。
- **可见性**：恢复注入的消息会进入会话记录，因此会像既有的继续消息一样在 UI 里显示为一条 user 气泡。
  这是沿用既有机制的副作用，不是新增的静默行为。
- **上限**：每次 run 最多 2 次，单轮不会因为恢复而无限循环。

## 4. 测试

单测（`packages/agent/test/dsml-tool-calls.test.ts`，9 例）：带空格 / 不带空格 / ASCII 竖线三种标记形态、
同名去重、代码围栏跳过、无 `name` 属性不匹配、未注册与已执行的过滤、空输入。

循环级（`packages/agent/test/agent-loop.test.ts` → `reasoning-channel tool-call recovery`，3 例）：

1. 思考通道只有标记 → 注入一次恢复消息，模型随后发出真实调用 → 工具真的执行（3 轮，恢复 1 次）；
2. 模型持续只讲解 → 恢复次数封顶为 2，循环结束（不做无谓的重试）；
3. 标记里的工具未注册 → 不注入。

重试分类（`packages/ai/test/retry-gateway-errors.test.ts`，2 例）：网关瞬时 400 判为可重试；
上游订阅配额 400 仍判为不可重试。

### 真机验证（pz 网关，2026-09-21）

模型 `deepseek-v4.1-flash`（当初的肇事模型）+ `reasoning: low`，走完整 `agentLoop` + 一个真实工具：

```
stopReasons: toolUse,stop
executed: ["live-ok"]
thinking blocks: 2   narrated names: []
nudges injected: 0
tool result: [{"type":"text","text":"echoed: live-ok"}]
```

即：正常链路的工具调用照常执行，扫描器没有产生任何误报，恢复逻辑一次都没触发 —— 满足
「改动不影响正常网关接口」的约束。

## 6. 观测点

排查时可 grep 会话记录里的这条前缀，判断安全网是否被触发过：

```
Tool call(s) written inside your reasoning channel were not executed:
```

## 7. 后续可选项

- 网关侧转换/剥离思考通道标记（根治）；
- UI 对这两类注入消息做归因标注（例如「引擎继续」），避免被当成用户发言；
- 若某模型频繁触发，考虑在其 provider 配置上默认关掉或降档推理通道。
