# Agent 循环中每轮 LLM 调用前检查压缩

**日期**: 2026-01-01  
**影响范围**: `kalo-harness/packages/coding-agent/src/core/agent-session.ts`（`_installAgentNextTurnRefresh` 方法）  
**动机**: 现有压缩检查在 `agent_end` 之后执行，在长时间多轮对话或用户中断时可能导致上下文已超限才触发压缩。需要在每次 LLM 调用前（`prepareNextTurn` hook）提前拦截检查，避免上下文溢出到 LLM。

---

## 问题分析

### 现有压缩检查时机（两处）

**A. `prompt()` 里，用户发送新消息前（行 1219-1221）：**
```typescript
const lastAssistant = this._findLastAssistantMessage();
if (lastAssistant) {
    await this._checkCompaction(lastAssistant, false);  // skipAbortedCheck=false
}
```
- ✅ 拦截时机：用户下次发消息时
- ❌ 盲区：用户不发消息期间，agent 多轮运行中上下文持续增长

**B. `_handlePostAgentRun()` 里，每轮 agent_end 后（行 1109）：**
```typescript
const msg = this._lastAssistantMessage;
this._lastAssistantMessage = undefined;
if (!msg) return false;
await this._checkCompaction(msg);  // skipAbortedCheck=true（默认）
```
- ✅ 拦截时机：每轮 LLM 调用结束后
- ❌ 盲区 1：`_lastAssistantMessage` 在 `message_end` 时赋值、`_handlePostAgentRun` 立即清空，如果 agent 运行多轮且中途没有 assistant 消息（纯 tool 调用），`msg` 为 `undefined` 跳过检查
- ❌ 盲区 2：`skipAbortedCheck=true` 默认跳过 `stopReason === "aborted"` 的消息

### 用户观察到的现象

**场景**：agent 长时间运行（多轮 tool 调用） → 上下文涨到 180K+ → 用户手动停止（stopReason=aborted） → B 处因 `skipAbortedCheck` 跳过检查 → 用户下次发消息 → A 处才检查到并触发压缩。

**根本原因**：压缩检查依赖 `agent_end` 事件，而 agent 多轮运行时（每轮 = LLM 调用 + tool 执行 + 可能的 continue）可能中间没有 assistant 消息或 assistant 被 abort，导致检查被跳过。

---

## 解决方案：在 `prepareNextTurn` hook 注入压缩检查

### Agent-loop 的 LLM 调用时序

```
agent.prompt() / agent.continue()
  ├─ turn_start
  ├─ LLM stream: message_start → message_update → message_end
  ├─ tool_execution_start → tool_execution_end（若干次）
  ├─ turn_end
  ├─ prepareNextTurn(nextTurnContext)  ← 下一轮 LLM 调用前的钩子
  ├─ shouldStopAfterTurn()
  └─ 循环或退出
```

`prepareNextTurn` 是 agent-loop 在每轮结束、下一轮 LLM 调用前的标准拦截点（agent-loop.ts 268 行），用于刷新 context/model/thinkingLevel。

### 改动：在 `_installAgentNextTurnRefresh` 注入压缩检查

**位置**：`agent-session.ts` 的 `_installAgentNextTurnRefresh()` 方法（548-571 行）

**before（只刷新 system prompt/tools）：**
```typescript
this.agent.prepareNextTurnWithContext = async (turn, signal) => {
    const previousSnapshot = await previousPrepareNextTurnWithContext?.(turn, signal);
    const previousContext = previousSnapshot?.context ?? turn.context;

    return {
        ...previousSnapshot,
        context: {
            ...previousContext,
            systemPrompt: this._systemPromptOverride ?? this._baseSystemPrompt,
            tools: this.agent.state.tools.slice(),
        },
        model: this.agent.state.model,
        thinkingLevel: this.agent.state.thinkingLevel,
    };
};
```

**after（新增压缩检查）：**
```typescript
this.agent.prepareNextTurnWithContext = async (turn, signal) => {
    // Check compaction threshold before each LLM call
    if (turn.message.role === "assistant") {
        const assistantMsg = turn.message as AssistantMessage;
        // Check with skipAbortedCheck=false to catch aborted responses
        // Compaction will run synchronously and reload agent state before LLM call
        await this._checkCompaction(assistantMsg, false);
    }

    const previousSnapshot = await previousPrepareNextTurnWithContext?.(turn, signal);
    const previousContext = previousSnapshot?.context ?? turn.context;

    return {
        ...previousSnapshot,
        context: {
            ...previousContext,
            systemPrompt: this._systemPromptOverride ?? this._baseSystemPrompt,
            tools: this.agent.state.tools.slice(),
        },
        model: this.agent.state.model,
        thinkingLevel: this.agent.state.thinkingLevel,
    };
};
```

### 关键特性

1. **每轮 LLM 调用前检查**：不依赖 `agent_end`，在 `prepareNextTurn` 拦截
2. **skipAbortedCheck=false**：即使 `stopReason === "aborted"` 也检查 threshold
3. **同步压缩**：压缩完成后 `agent.state.messages` 被重载，下一轮 LLM 使用压缩后的上下文
4. **防双重压缩**：`_checkCompaction` 的 `assistantIsFromBeforeCompaction` 检查（行 2019-2022）会跳过已被压缩的消息

---

## 防双重压缩机制

`_checkCompaction` 内部已有时间戳检查（行 2012-2022）：

```typescript
const compactionEntry = getLatestCompactionEntry(this.sessionManager.getBranch());
const assistantIsFromBeforeCompaction =
    compactionEntry !== null && assistantMessage.timestamp <= new Date(compactionEntry.timestamp).getTime();
if (assistantIsFromBeforeCompaction) {
    return false;  // 跳过已被压缩的消息
}
```

**流程**：
1. `prepareNextTurnWithContext` 调用 `_checkCompaction(turn.message, false)`
2. 如果触发压缩，`sessionManager.appendCompaction()` 添加 compaction entry
3. 该 assistant 消息的 timestamp < compaction entry timestamp
4. 后续的 `_checkCompaction` 调用（如 `_handlePostAgentRun` 里的）会在时间戳检查处短路返回 `false`

## 影响评估

### 用户可见行为

- **Before**：长时间多轮对话中，压缩在 agent_end 或用户下次发消息时才触发，中间可能超限
- **After**：每轮 LLM 调用前检查，上下文接近阈值（200K - 16K = 184K）时立即压缩

### 性能影响

- 每轮 LLM 调用前增加一次 `_checkCompaction` 调用（纯计算，< 1ms）
- 压缩本身是异步 LLM 调用（summarization），阻塞下一轮 LLM，但这是必要的（避免溢出）

### 兼容性

- 不改变压缩逻辑、阈值计算、事件流
- 防双重压缩机制已存在，无破坏性改动

---

## 文档影响

- **模块职责**：`_installAgentNextTurnRefresh` 从"刷新 system prompt"扩展为"刷新 + 压缩检查"
- **事件流**：`compaction_start` / `compaction_end` 可能在 `prepareNextTurn` 里触发（不只是 `agent_end` 后）
- **用户可见交互**：压缩气泡出现时机提前（不等用户发消息）
