# 产物呈现通道（present_files + show_widget）

## 背景与问题

kalo 目前**没有一等公民的「产物」概念**。前端要知道"模型产出了什么可查看的结果"，只有两条*被动推断*的路径：

1. **「编辑了 N 个文件」变更卡**（`kalo-desktop/src/lib/changed-files.ts` + `components/ChangedFilesCard.tsx`）：客户端从每次 `write`/`edit` 工具结果里累积出来的。刻意只认 `write`/`edit`——`bash` 产物、子 agent 内部调用都被排除（见 `changed-files.ts:9-11,74`）。
2. **git 驱动的右侧文件面板**（`components/FilePanel.tsx:132-141`）：一轮结束（`isStreaming` true→false）后 debounce 重读 `git status`。

两者都在"猜模型干了什么"，缺三样东西：

- **交付意图**：无法区分"顺手写的中间文件"和"这份 HTML 报告才是给用户看的成果"。
- **有序与聚焦**：无法表达"先展示哪个"，更没有"首个自动打开"。
- **非文件产物**：`bash` 生成的文件、在线链接（http/https）完全不在雷达上。

### 目标

新增一个由模型显式调用的呈现工具 `present_files`，把"哪些是最终产物、按什么顺序、首个自动打开"作为一次**单向交付声明**传给桌面端：

- 顺序即优先级，第一个为 primary，活时自动打开。
- 支持**本地文件**（HTML 走现有沙箱预览；其它类型出卡片 + 系统默认程序打开）与 **http/https 链接**（内置浏览器面板打开）。
- 产物栏与现有变更卡**并存**（对应 WorkBuddy 的「查看所有产物 / 查看所有变更」两栏），语义不同：产物 = 模型声明的交付物，变更 = git 探测到的全部改动。

## 机制选型：为什么不照抄 WorkBuddy 的"客户端执行工具"

WorkBuddy 把 `present_files` 设计成**客户端进程执行**的工具，原因是它模型侧运行在隔离沙箱、与前端无共享通道，且一个客户端可能开多个会话窗口，需要靠 `cwd` 参数把预览"认领"到正确的会话面板。

kalo 的运行时不同，两点差异决定了更简单的实现：

1. **sidecar 是同机子进程**：引擎与桌面端在同一台机器，引擎侧能直接 `stat` 本地文件拿到大小、判断存在性、按扩展名分类。不需要把这些推给客户端算。
2. **事件天然按会话分流**：引擎事件走 `pi-event:{sessionId}`（见 `kalo-desktop/src/lib/pi-bridge.ts:677-687`），`sessionId` 就是路由键。不需要 `cwd` 做会话认领。

因此 kalo 采用 **`todo_write` 范式**而非 `ask_user` 范式：

- `todo_write`（`kalo-harness/packages/coding-agent/src/extensions/todo/index.ts:98-106`）把结构化数据放进 `AgentToolResult.details`，顺着工具结果落进 session jsonl，**"reaches the desktop client unchanged"，且可从历史回放**。前端在 `chat-store.ts:1550-1552` 读 `details` 渲染。
- `ask_user`（`extensions/ask-user/rpc-provider.ts`）是**阻塞式 RPC 往返**：引擎发请求帧、parking 一个 waiter、等客户端回答再 resolve。这适合"必须拿到人的输入才能继续"，但产物呈现不需要等客户端——声明发出即完成。

`present_files` 走 `details` 通道：引擎侧解析路径、分类、`stat` 拿大小，返回 `details: { artifacts }`。这带来一个关键区分——

### 可回放的卡片 vs 仅活时的自动打开

`details` 落进 jsonl，意味着**重开历史会话时产物卡会原样复现**（就像变更卡、todo 卡一样）。但"首个自动打开预览"是一个**副作用**，只应在产物**当轮活时**发生——回放一个三天前的会话不该突然弹出预览面板。

所以前端分两层处理（详见前端章节）：

- **渲染产物卡**：纯数据驱动，活时与回放都做。
- **自动打开 primary**：只在"这条 `tool_execution_end` 属于当前正在进行的这一轮"时触发一次。

### `cwd` 的角色降级

WorkBuddy 用 `cwd` 做会话路由；kalo 有 `sessionId` 分流，`cwd` 在这里**只作解析相对路径的基准**，不作路由键。工具参数里的相对路径以引擎进程的会话 cwd 解析（与 `write`/`read` 等现有文件工具一致），不单独引入 `cwd` 参数。

## 契约：present_files 工具

### 新增内置扩展

`kalo-harness/packages/coding-agent/src/extensions/present-files/`，注册进同目录 `index.ts` 的 `builtInExtensions`（`hidden: true`，与其它 12 个一致）。

与 `ask_user` 一样，**无人值守/子 agent 场景下工具应缺席**：

- 子 agent（`noExtensions: true`）本就不加载它。
- 无人值守运行（`KALO_UNATTENDED=1`）下不注册——没有前端可呈现，声明无意义。

### 工具参数

```ts
present_files({
  files: string[],       // 交付物：本地路径或 http/https URL。顺序即优先级，files[0] 为 primary。
  explanation?: string,  // 一句话说明这批产物是什么，展示在产物栏标题下。
})
```

- `files` 非空，去重后保序；相对路径以会话 cwd 解析为绝对路径。
- 不接受目录（目录用变更卡/文件面板看）；对不存在的本地路径不静默丢弃，而是在该条目上标 `missing: true` 让前端显示为失效条目，同时在工具结果文本里回报，好让模型察觉写错了路径。

### 工具返回（details）

引擎侧对每个条目分类后，返回结构化 `details`：

```ts
interface ArtifactItem {
  kind: "file" | "url";
  path: string;              // 绝对路径（file）或原始 URL（url）
  name: string;              // 文件名 / URL 的可读标题（host + 末段路径）
  fileKind?: FileKind;       // 仅 file：由扩展名判定（html/markdown/pdf/image/...），前端据此选渲染方式
  bytes?: number;            // 仅 file：stat 拿到的大小，前端显示 "18.8 KB"
  missing?: true;            // 仅 file：路径不存在
  primary: boolean;          // 是否 files[0]
}

interface PresentFilesDetails {
  artifacts: ArtifactItem[];
}
```

`FileKind` 复用前端 `kalo-desktop/src/lib/file-kind.ts` 的同名判定逻辑；引擎侧需要一份等价的扩展名映射（放 `present-files/file-kind.ts`，与前端保持同一张表，避免两侧对 "html→sandbox 预览" 的判断漂移）。

工具结果的 `content`（模型读回的文本）用 JSON 回报实际呈现了哪些、哪些失效，例如：
`{"presented": ["career_analysis.html"], "missing": [], "primary": "career_analysis.html"}`。

### 前端类型镜像

`kalo-desktop/src/types.ts` 增加 `PresentFilesDetails` / `ArtifactItem` 的镜像类型（与其它 tool `details` 镜像并列）。事件流不新增消息类型——`present_files` 复用现有 `tool_execution_end`（`PiEvent`，携带 `toolName: "present_files"` 与 `result.details`），无需改 `pi-bridge.ts` 的命令/事件清单。

> 契约影响面小：不新增 RPC 命令、不新增 `pi-event` 事件种类，只新增一个工具及其 `details` 结构。`pi-bridge.ts` 头部契约清单需补一行说明 `present_files` 工具结果的 `details` 约定。

## 桌面端渲染

### 纯逻辑：lib/artifacts.ts

新增 `kalo-desktop/src/lib/artifacts.ts`（纯逻辑，可单测，位于 lib 层不碰 IPC）：

- `parseArtifacts(result: ToolCallRecord): ArtifactSummary | null`：从 `present_files` 的工具结果 `details` 解析出有序 `ArtifactItem[]`、primary、explanation。非 `present_files` 或无 details 返回 null。
- `ArtifactSummary`：`{ items: ArtifactItem[]; primary: ArtifactItem | null; explanation?: string }`。
- 提供 `sessionArtifacts(records)`：把一整个会话内多次 `present_files` 聚合成"查看所有产物"用的去重列表（后声明的同路径覆盖先前，保序）。

### 时间线产物卡：ArtifactsCard

- `kalo-desktop/src/lib/timeline.ts` 增 `ArtifactsEntry { kind: "artifacts"; summary: ArtifactSummary }`，与现有 `ChangesEntry` **并存**（不替换）。在 `tool_execution_end` 且 `toolName === "present_files"` 时推入时间线（`chat-store.ts` 事件分发处，紧邻现有 `accumulate` 逻辑）。
- 新组件 `kalo-desktop/src/components/ArtifactsCard.tsx`，仿 `ChangedFilesCard.tsx`：
  - 每条产物一行：图标（按 `fileKind` / url）+ 名称 + 大小；失效条目置灰标注。
  - 行为：点击 primary/任意条目→打开预览（本地文件走 `FileViewerModal`/`FilePreview`，url 走内置浏览器）；右键菜单复用 `ContextMenu` 的 `openPathItem`（"用默认程序打开 / 打开所在文件夹 / 复制路径"）与 url 的"复制链接 / 系统浏览器打开"。
  - 底部与变更卡并排："查看所有产物 (n)" / "查看所有变更 (m)"。

### 右侧「产物」栏

`components/FilePanel.tsx` 的右侧栏增加一个"产物"分区（对应截图右侧 `概览 > 产物` 列表），数据来自 `sessionArtifacts`。与既有"仅变更 N"模式并列，互不替代。

### 活时副作用：自动打开 primary

只在"这条 `tool_execution_end` 属于当前正在进行的这一轮"时触发一次（回放历史不触发）。
判据在调用路径上：只有 `chat-store` 的 live `tool_execution_end` 会调
`handleSpecialToolResult`，历史回放走 `buildTimeline` 里的 `parseArtifacts`，不经过它。

**归属路由（2026-09-30 修正）**：自动打开不是全局事件，而是**记到声明它的那个会话**的
文件区记忆里（桶键用该会话的 `sessionUid`，字段 `file-panel-memory.pendingArtifact`）。
面板只消费"当前会话"的那一条：

- 产物到达时该会话正在屏幕上 → 立刻打开它自己的预览（与旧行为一致）；
- 产物到达时看的是别的会话（后台会话跑出来的）→ 只写进那个会话的记忆，**不**弹到当前
  文件区；切回那个会话时，文件区按它自己的记忆把这份产物打开 —— 队列只消费一次，
  随即清空。

理由：`present_files` 是"这个会话的交付"，A 会话的产物出现在 B 会话的文件区是错位的；
待打开项跟着会话走，既不会漏（切回去还在），也不会串。（旧实现是全局事件总线，
`FilePanel` 订阅到就写当前会话的记忆——后台会话的产物会直接落到正在看的那个会话上。）

入队时就丢弃：`kind === "url"`（面板没有 URL 预览通道；卡片里点它走系统浏览器）与
`missing: true`（引擎 stat 不到文件，打开只会看到"文件不存在"）。

打开方式：本地文件（含 `fileKind === "html"`）统一走面板的 `openFile`（预览列），由
`FilePreview` 按类型分流（HTML 沙箱、图片、markdown、office...；HTML 本地资源内联、
脚本在沙箱内运行）；`relPath` 在打开的那一刻用面板自己的 git 状态算，所以 diff 标签
照常可用。

### 内置浏览器面板

用户要求 http/https 链接在 App 内的内置浏览器面板打开（非系统浏览器）。

- **实现**：Tauri webview（v2 支持多 webview；win32 用 WebView2，macOS 用 WKWebView）。新建一个受控 webview 面板承载外链，而非用 `<iframe>`——第三方站点普遍带 `X-Frame-Options: DENY` / `CSP frame-ancestors`，iframe 无法可靠嵌入。
- **双平台**：webview 的创建/销毁、导航、关闭在两平台等价；OS 差异（若有）收敛在 Rust 侧薄适配层，不散进业务逻辑。窗口 vs 内嵌面板的取舍在实现期确定，契约层不依赖它。
- **分期**：这是本设计里最大的新造件。建议**分两期**落地（见下），先让核心交付契约 + 本地文件闭环，内置浏览器随后接上；在浏览器就绪前，url 条目临时用系统浏览器 `openPath` 打开，卡片与"查看所有产物"不受影响。

## 系统提示 / 收尾硬规则

模型不会自发调用 `present_files`——必须有硬规则要求"凡产出了可查看的最终结果，收尾那一轮必须走 `present_files` 呈现"，否则"活干完了但什么都看不到"。

- 工具自带 `promptSnippet` + `promptGuidelines`（仿 `ask-user/index.ts:142-147`），进系统提示前缀：
  - snippet：`present_files(files) — 产出可查看的最终成果时，收尾必调，声明交付物；files[0] 自动打开`
  - guidelines：只放**最终交付物**（报告/网页/图表/数据文件），不是每个中间文件；最重要的放 `files[0]`；已经过时/被覆盖的旧产物不要再列。
- 系统提示注入点在 `kalo-harness/packages/coding-agent/src/core/system-prompt.ts`（由注册工具列表拼装），扩展注册即生效，无需单独改内置 skill。

## 契约：show_widget 工具（内联可视化通道）

`present_files` 交付的是**落盘的文件产物**；`show_widget` 是它的姊妹通道，交付**内联渲染的可视化**——模型直接把 SVG/HTML 片段作为工具结果传出，前端在沙箱 iframe 里当场渲染，不落盘、不进产物栏，只作为时间线里的一张卡片（图表、示意图、交互原型）。

### 新增内置扩展

`kalo-harness/packages/coding-agent/src/extensions/show-widget/index.ts`，注册进 `builtInExtensions`（`hidden: true`）。设 `KALO_UNATTENDED=1`（定时任务/无人值守）时不注册——可视化只对交互式会话有意义。两个工具：

- `read_me(modules)`：按需拉取设计规范（CSS 变量、配色、SVG/图表/UI 规则），不进系统提示，首次 `show_widget` 前调用。`modules` 取 `diagram|mockup|interactive|chart|art`，接受数组 / JSON 字符串 / 逗号分隔三种写法。
- `show_widget(title, widget_code, loading_messages)`：声明一个 widget。

### 工具参数与校验

- `title`：可视化标识，与用户语言一致，也用作下载文件名（引擎侧 sanitize 成 `[\p{L}\p{N}_]`）。
- `widget_code`：裸 SVG 或 HTML **片段**，不含 `<!DOCTYPE>/<html>/<head>/<body>`。
- `loading_messages`：1–4 条加载提示（JSON 数组字符串），渲染就绪前轮播。

引擎侧 `validateWidget` 是纯函数，硬性拦截：文档包裹标签、`localStorage/sessionStorage`（sandbox opaque origin 会抛 SecurityError）、`position:fixed`（高度按内容自适应）、`<form>`。SVG 分支额外要求恰好一个 `<svg>` 且 `viewBox` 以 `0 0 680 ` 开头（宽度固定 680）。`render_mode` 由 `widget_code` 是否以 `<svg` 开头推导。

### 工具返回（details）

`WidgetDetails { type:"widget", title, widget_code, loading_messages, render_mode }` 挂在 `AgentToolResult.details`，随会话 jsonl 落盘，支持历史回放。前端类型镜像在 `kalo-desktop/src/lib/widgets.ts`，`parseWidget` 做运行时校验（`toolName==="show_widget"` 且非 error 且 `isWidgetDetails`）。

### 桌面端渲染

- 时间线：`chat-store` 在 `show_widget` 的 execution_end（活时）与回放（settled）都 `parseWidget`，推一条 widget 时间线项；`TimelineItem` 分流到 `WidgetCard`；`WidgetCard` 未就绪显示 loading 动画，就绪后挂 `WidgetSandboxFrame`。
- 沙箱：`<iframe sandbox="allow-scripts">`（**无** `allow-same-origin`，故 opaque origin，storage 不可用），`srcDoc` 注入。CSP `default-src 'none'`，脚本/样式/字体/图片/连接仅放行 CDN 白名单（cdnjs、esm.sh、jsdelivr、unpkg），拦截其它域与 `javascript:`/`data:` 链接。
- 三阶段防闪渲染（HTML 模式）：`stream` 阶段 `sanitizeForStreaming`（剥脚本/危险标签、容忍半开 HTML）→ `widget:update` 增量 morph（CANVAS 节点跳过，保 GPU 内容）；`finalize` 阶段 `sanitizeForIframe`（保脚本）→ `widget:finalize` 先 dispose ECharts + 全量重建再执行脚本。SVG 模式静态注入，无流式更新。
- 高度：iframe 内 `ResizeObserver` 上报 `widget:resize`，宿主用 `shouldApplyHeight` 挡住连续微增（防无限增高），钳制 20–2000px。
- 交互回传：widget 内 `window.sendPrompt(text)` 与链接点击经 postMessage 冒泡给宿主（`widget:sendMessage` / `widget:link`）。

### 主题适配（2026-09-29 增补）

问题：引擎按 `read_me` 规范，widget 一律用宿主注入的 `--cb-*` 变量取色（`--cb-panel-bg-primary/--cb-text-primary/--cb-text-secondary/--cb-border-default/--cb-accent-primary`，见 show-widget 扩展 `getCoreDesignSystem`）。但沙箱 `<style>` 此前并未定义这些变量，浏览器回退到默认近黑色——暗色主题下 SVG 文字/轴线几乎不可见。

方案（纯前端，无契约变更）：`WidgetSandboxFrame` 把宿主主题 token 解析成 `--cb-*` 注入沙箱。

- 映射（`resolveThemeVars`，读 `getComputedStyle(document.documentElement)`）：
  - `--cb-panel-bg-primary` ← `--bg-card`
  - `--cb-text-primary` ← `--text`
  - `--cb-text-secondary` ← `--text-dim`
  - `--cb-border-default` ← `--border`
  - `--cb-accent-primary` ← `--accent`
- 注入点：`buildSandboxHtml` 把解析值写进沙箱 `:root{}`，并给 `body` 兜底 `color: var(--cb-text-primary)` + 系统字体栈（HTML widget 忘了设色时也可读）。
- 响应主题切换：宿主主题在 `<html>` 上切 `dark` 类（`applyTheme`）。`WidgetSandboxFrame` 用 `MutationObserver` 盯 documentElement 的 `class`，变化时把新解析值经 `widget:theme` postMessage 给沙箱，沙箱 `document.documentElement.style.setProperty` 逐个应用。沙箱同时缓存这份主题值，供截图时内联（见下）。

### 卡片操作菜单（2026-09-29 增补）

`WidgetCard` 头部右上角加 `...` 菜单（复用 `useContextMenu`/`ContextMenu` 的 `openAtRect`，与侧栏一致），三项：

- **复制代码**：`navigator.clipboard.writeText(widget_code)`（两种模式通用，无需 iframe）。
- **另存源码**：`save` 对话框（SVG→`.svg`，HTML→`.html`，默认名取 `title` sanitize）+ `writeFileText`（复用 `SvgBlock` 的既有路径）。
- **保存为图片**：把当前渲染结果导出 PNG 落到用户选定路径。

截图协议（宿主 ↔ 沙箱，postMessage 往返）：宿主发 `widget:capture { id }`，沙箱把 `#root` 内的 `<svg>`（或整个 `#root`，HTML 模式经 `foreignObject` 尽力而为）序列化为**自包含 standalone SVG**——把缓存的 `--cb-*` 内联进 SVG 的 `<style>:root{}`，否则隔离的 `<img>` 文档看不到宿主变量，导出图会掉色——再经 `<img>`→`<canvas>`（2× 缩放，先填 `--cb-panel-bg-primary` 底色）→ `toDataURL('image/png')`，回 `widget:image { id, dataUrl }`；失败回 `widget:capture-error { id, message }`。宿主 `WidgetCard` 持 `WidgetSandboxFrame` 的 `capture(): Promise<string|null>`（`useImperativeHandle`），拿到 dataURL 去前缀 → base64 → `save` 对话框（`.png`）→ `writeFileBytes`。

边界与降级：
- SVG 模式（截图/契约里的常见情形）自包含，可靠导出。
- HTML/canvas 图表经 `foreignObject` 是尽力而为；opaque origin 下若 canvas 被判 taint，`toDataURL` 抛 `SecurityError`，沙箱回 `widget:capture-error`，宿主 toast 建议改用「另存源码」。
- 折叠状态下 iframe 未挂载：菜单里「复制代码/另存源码」照常可用；「保存为图片」在未就绪时 toast 提示先展开。

### 新增桥接命令：write_file_bytes（契约变更）

已有 `write_file_text`（文本→选定路径）与 `save_attachment_bytes`（字节→固定 attachments 目录），缺「字节→用户选定路径」。为「保存为图片」新增：

- Rust `files::write_file_bytes(path, data_base64)`：base64 解码后 `fs::write` 到选定路径，自动建父目录，错误带路径（与 `write_file_text` 同构）。`main.rs` 注册 `#[tauri::command(async)] write_file_bytes`。
- 前端 `pi-bridge.ts::writeFileBytes(path, dataBase64)`。
- 双平台：仅落盘，无平台语义差异；路径由 `save` 对话框给出。

### show_widget 的双平台 / 测试 / 分期

- 双平台：widget 渲染全在 WebView（WebView2 / WKWebView）内，无路径/进程/文件系统语义，平台中立；无需窄适配层。

- 分期：P1 支持裸 SVG（无脚本，静态注入）；P2 加 HTML+JS 三阶段流式渲染器。

## 双平台评估（Windows / macOS）

- **路径解析**：`files` 里的相对路径以会话 cwd 解析；分隔符归一在引擎侧解析层处理（`\` 与 `/` 都接受），产出统一的绝对路径。前端 `file-kind` 判定已按 `/` 与 `\` 兼容（`file-kind.ts:53`）。
- **打开文件**：一律走已封装的 `files.rs::open_path`（根 AGENTS.md 指定的窄适配层），不自己拼平台命令。
- **内置浏览器**：WebView2（win）/ WKWebView（mac）差异收敛在 Rust 侧，业务逻辑平台中立。
- **stat 大小/存在性**：引擎侧 Node fs，跨平台一致。
