# 压缩使用独立的 thinking 等级（默认 off）

## 问题

用户反馈「主动压缩很慢」。排查后确认：压缩请求的 thinking 等级直接继承当前会话的 thinking 等级，没有任何降级。

调用链（`kalo-harness/packages/coding-agent/`）：

```
agent-session.ts:1899  compact(preparation, model, ..., this.thinkingLevel, ...)   // 手动压缩
agent-session.ts:2194  compact(preparation, model, ..., this.thinkingLevel, ...)   // 自动压缩
  └─ compaction/compaction.ts:createSummarizationOptions()
       if (model.reasoning && thinkingLevel && thinkingLevel !== "off")
           options.reasoning = thinkingLevel;
```

`~/.kalo/agent/settings.json` 的 `defaultThinkingLevel` 是 `high`，因此压缩摘要请求也是 high。

两条 provider 路径的代价不同：

**anthropic-messages 原生路径**（`models.json` 里配 `api: "anthropic-messages"` 的 provider）
`packages/ai/src/api/anthropic-messages.ts:859` 走 `adjustMaxTokensForThinking(base, model.maxTokens, "high")`，
默认预算表 `high: 16384`，即一次压缩允许烧掉 16K 思考 token 才开始写摘要。压缩的 `maxTokens` 本身只有
`0.8 * reserveTokens ≈ 13107`，思考预算比摘要正文预算还大。

**openai-completions 自定义模型**（如 `pz` 网关代理的 claude-opus-5）
`packages/coding-agent/src/core/provider-composer.ts:180,198` 对 `models.json` 里自定义的模型取
`reasoning: definition.reasoning ?? false`。用户的 `models.json` 未声明 `reasoning`，所以客户端根本不发
thinking 相关参数——但上游 Claude 仍会默认思考。实测（180K prompt 的压缩形态请求）：

| 请求形态 | 耗时（两次） | 响应中 reasoning_content |
| --- | --- | --- |
| 不带 thinking 参数 | 65.7s / 61.0s | 有（~660 字符） |
| `thinking: {"type":"disabled"}` | 58.8s / 57.3s | 无 |

小 prompt（约 2K）差距更明显：17.8s → 5.0s。

结论：thinking 不是压缩慢的唯一原因（prefill 才是大头，见「不在本次范围」），但它是一笔纯浪费——
压缩输出是固定模板的结构化摘要，几乎没有需要推理的决策点。

## 方案

新增 `settings.compaction.thinkingLevel`，默认 `"off"`，压缩与分支摘要不再继承会话 thinking 等级。

### 1. settings-manager：新增配置项

`packages/coding-agent/src/core/settings-manager.ts`

```ts
export interface CompactionSettings {
    enabled?: boolean;          // default: true
    reserveTokens?: number;     // default: 16384
    keepRecentTokens?: number;  // default: 20000
    thinkingLevel?: ThinkingLevel; // default: "off"
}
```

`getCompactionThinkingLevel()` 返回 `this.settings.compaction?.thinkingLevel ?? "off"`，
并入 `getCompactionSettings()` 的返回结构。

沿用既有的 global/project 合并语义（`deepMergeSettings`），项目级 `settings.json` 可覆盖全局值。

### 2. compaction：把 thinkingLevel 收进 CompactionSettings

`packages/coding-agent/src/core/compaction/compaction.ts` 的 `CompactionSettings` 接口同步加
`thinkingLevel: ThinkingLevel`，`DEFAULT_COMPACTION_SETTINGS` 补 `thinkingLevel: "off"`。

`compact()` 已经通过 `preparation.settings` 拿到整份压缩设置，因此**删除它的 `thinkingLevel` 形参**，
内部统一读 `settings.thinkingLevel`。这样调用方不可能再传错等级，
`generateSummaryWithUsage()` 与 `generateTurnPrefixSummary()` 的 `thinkingLevel` 形参保留
（它们是可独立调用的导出 API），由 `compact()` 传入 `settings.thinkingLevel`。

### 3. agent-session：不再传 this.thinkingLevel

`agent-session.ts` 的两处 `compact(...)` 调用去掉 `this.thinkingLevel` 实参。

### 为什么默认 off 而不是 low

压缩摘要的提示词（`SUMMARIZATION_PROMPT` / `UPDATE_SUMMARIZATION_PROMPT`）是逐节固定模板，
模型要做的是抽取+改写，不是推理。实测 off 与 high 产出的摘要结构一致、关键信息（文件路径、命令、
错误串）保留度没有可观察差异。需要更高保真度的用户可以显式配 `"low"` / `"medium"`。

### 配置示例

`~/.kalo/agent/settings.json`：

```json
{
  "compaction": {
    "thinkingLevel": "off"
  }
}
```

## 不在本次范围

排查中确认的其他慢因，单独立项：

1. **prefill 是主要成本**：实测该网关约 3.5K tok/s，46K prompt 约 20s、180K 约 60s。
   压缩默认在 `contextWindow - reserveTokens = 184K` 触发，每次整块重发约 160K 上下文。
2. **压缩主动放弃前缀缓存**：`completeSummarization()` 强制 `cacheRetention: "none"` 且
   `sessionId: uuidv7()`；`serializeConversation()` 又把历史压成一条全新的巨型 user 文本，
   与主对话的消息数组结构完全不同，缓存前缀天然对不上。
   注：对 pz 网关实测同一 180K 请求连发两次（58s / 64s），带 `cache_control` 也无提速、
   usage 不返回缓存字段，说明该网关侧不提供前缀缓存，这条优化只对原生 Anthropic 端点有意义。
3. **split-turn 两次摘要串行**：`compact()` 在切分 turn 时先后调用
   `generateSummaryWithUsage()` 与 `generateTurnPrefixSummary()`，两者无依赖，可并行。
4. **openai-compat 自定义模型关不掉上游 thinking**：`openai-completions.ts` 的 thinking 分支
   全部带 `&& model.reasoning`，`reasoning: false` 时一个参数都不发，上游默认思考无法抑制。
   要治本需要让 `reasoning: false` 也能显式下发关闭指令，但不同网关对未知字段的容忍度不一，
   需要单独评估。

## 验证

1. `npm run check`（changed-aware）。
2. 手工：`~/.kalo/agent/settings.json` 保持 `defaultThinkingLevel: "high"`，
   在长会话里触发一次压缩，确认摘要正常生成且结构完整。
3. 若要观察等级是否生效，临时把 `compaction.thinkingLevel` 设为 `"high"`，
   对比压缩耗时应显著变长。
